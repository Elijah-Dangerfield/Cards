These are bugs / polish items found playing the app or scanning the code. Cheap individually; collectively the V1 quality bar.

### Achievements — bot-vs-human split

**Locked design:** achievement grants follow the gameplay surface they fire from. **Bot games** run the engine client-side and always will — the client posts achievement unlocks to `POST /v1/me/grants/achievement/{id}` and that's the permanent shape (not a security gap to harden, just how bot achievements work). **MP achievements** wait for Phase 4.2 server-authoritative gameplay, where the server witnesses the hand and grants directly — no client POST. The registry already carries `AchievementMode.{BOTS, MULTIPLAYER, EITHER}` on every entry and `ClientGrantableAchievements.Default` (server-side) splits `clientGrantable` vs `serverWitnessed` so the two MP-only `*_MP` entries 403 on a client self-grant attempt today. The grant endpoint is also rate-limited via `ACHIEVEMENT_GRANT_LIMIT` (120/hour/IP, see `RateLimits.kt`) as of 2026-05-28. Remaining hardening: hand-count floor on the grant endpoint — genuinely blocked on server-side hand tracking, which is part of Phase 4.2 server-authoritative gameplay (there's no `hands_finished` signal on the server yet to gate against).

## B. Multiplayer hardening

**Architecture revisit landed 2026-05-27.** Decision: accept the eval's Option B (event-sourced game state, sequence-numbered events over the existing WS, snapshot-on-hand-end compaction, room membership persisted to Postgres). Transport split stays; managed realtime layers stay out of the game path. Full reasoning + alternatives in [docs/decisions.md](./decisions.md) entry **"2026-05-27 — Multiplayer: event-sourced game state + persisted room membership"**. The sub-items below are the migration path. Sequencing is **not strict** — phases can interleave once the foundation is in place — but B0 → B1 → B3 is the natural order for the durability fix.

> ⚠️ **2026-05-28 — Scope of the architecture is being reconsidered before §B1+ resumes. See the P0 below. Don't pick up §B1, §B2, §B4, or §B5 until that lands.**

- `[P0]` **Decide whether to keep the event-sourced multiplayer architecture or scope-cut to snapshot-only.** §B0's foundation shipped 2026-05-28 — `game_events` table + `GameEventEnvelope(v, type, payload)` carrier + `PostgresGameEventWriter` writing every emitted event inside the per-session mutex before the in-memory broadcast. Everything queued in §B1 / §B2 / §B4 builds on that model: snapshot compaction, event-tail catch-up on reconnect, event-keyed gameplay items like buy-in / re-buy / forfeit. **Open question raised in PR feedback:** for V1, the event log's *only* consumer is "rebuild server state after a crash." V1 doesn't ship hand history, doesn't ship spectator mode, doesn't ship replay-as-a-feature, and we're pre-launch with zero MP users. A single-row-per-session `room_sessions(state_jsonb)` table overwritten on every mutation accomplishes the V1 crash-recovery requirement in ~20 lines of Exposed + a couple migration steps, vs. the snapshot + compaction + replay machinery in §B1 / §B2 that probably runs to several hundred lines plus invariant tests. **Per-hand event volume:** ~15–30 rows per hand (HandStarted, BlindPosted ×N players, HoleCardsDealt ×N, StreetAdvanced ×3–4, ActionTaken ×4–30, PotAwarded, HandEnded). A typical session = thousands of rows; scaled to a real MP userbase, millions per day. We don't have a pruning policy yet — the decisions log says "keep all snapshots for V1, volume's nothing" which is optimistic. **The two paths:** **(a) keep event-sourced** — resume §B1 → §B2 → §B4 → §B5 in order, accept the complexity now because we want the future features (hand history, audit log, spectator hydrate, time-travel debugging) and we want them riding on the same foundation; **(b) scope-cut to snapshot-only** — rewrite §B1 as the single `room_sessions(state_jsonb)` table (overwrite per mutation, no compaction, no replay function), drop §B2 (reconnect just re-reads the snapshot — fast for a single-row read), radically simplify §B4 (gameplay items mutate `state_jsonb` directly instead of emitting event sequences), and the `game_events` table becomes either an optional audit log or gets dropped. The already-shipped `game_events` write path is forward-compatible with both paths — it stays load-bearing under (a), becomes an audit log under (b). **Hybrid worth considering:** snapshot-only as the source of truth + a rolling tail of the last ~50 events kept for animation replay on reconnect (so a brief disconnect can still re-play the last few actions visually); discard older events to keep table size bounded. **Action:** human picks (a), (b), or hybrid; land the decision in [`docs/decisions.md`](./decisions.md) so future maintainers don't relitigate; then either resume §B1 in order or rewrite §B1 / §B2 / §B4 / §B5 to match the cut shape. **Workers:** **don't pick up §B1+** until this resolves — the work shape depends entirely on which path lands.

### B0 — Foundation: event log primitives

- `[P0]` **Crash-mid-hand replay equivalence test for the persisted event log.** B0's producer landed 2026-05-28 (`PostgresGameEventWriter` + `GameSession`'s write-before-broadcast invariant + write-failure-rejects-action contract). ### B1 — Snapshot compaction + cold-start replay

- `[P1]` **Snapshot the materialized `GameState` at every hand-end checkpoint.** New `game_state_snapshots(session_id UUID, cursor_seq BIGINT, state_jsonb JSONB, captured_at TIMESTAMPTZ, PRIMARY KEY(session_id, cursor_seq))` with index on `session_id`. After each `HandComplete` event lands in `game_events`, the session writes the full `GameState` JSON snapshot at the same cursor (still inside the mutex so the snapshot/event-tail invariant holds). **Acceptance:** cold-start of a server process loads the latest snapshot per active session and replays the event tail past that cursor to reconstruct the in-memory `StateFlow`; restart mid-hand is recoverable. **Files / hints:** new migration; new helper alongside `GameSession.kt`. **Out of scope:** snapshot retention/pruning (keep all snapshots for V1 — the volume's nothing).

- `[P1]` **Bootstrap-from-Postgres path in `GameSessionRegistry`.** Today the registry is process-local and a restart loses every active session. After B1 lands a snapshot table, the registry's first read for a given `session_id` should hydrate from `(latest snapshot, replay events after cursor)` before returning the in-memory session. **Acceptance:** server restart leaves all open rooms reconnectable mid-hand; the existing 5-min reconnect grace continues to work for the disconnected player. **Files / hints:** `apps/server/src/main/kotlin/com/cards/server/game/GameSessionRegistry.kt`. **Out of scope:** the WS reconnect protocol change (B3) — this is server-side bootstrap only.

### B2 — WS reconnect protocol upgrade
