## fix(room): keep deal/reveal animations in real-chip games (GAME-8)

**Problem:** The unified global "Game speed" setting (`GameSpeed.animationScale`) paces solo practice, but it also drove a real bots-for-chips public game to Instant — a tester lost the card flips in a real game and intuited the speed should be practice-only.
**Approach:** Scoped the animation pacing, not the setting. Added `PlayPokerState.effectiveTableSpeed` (and a `realChipsAtStake` helper) that forces `GameSpeed.Normal` whenever real chips are on the line — a human MP game (`isRealMultiplayer`) *or* the public subsidized disclosed-bot table (`subsidizedBotTable`). `PlayPokerScreen` provides `TableTempo(state.effectiveTableSpeed)` instead of the raw `gameSpeed`. The setting still tunes solo + private practice-bot tables. Chose this over making the whole setting practice-only (would silently ignore a user's explicit Instant in practice MP, which is fine to honour) and over a per-animation minimum floor (more surface area, same outcome).
**Reviewer notes:** The reporter's room was a public bots-for-chips table, which is `practiceTierBotsOnly == true` — so `isRealMultiplayer` alone would NOT have covered it; `realChipsAtStake` adds the `subsidizedBotTable` arm specifically for that case. Bot think-time scaling (`botThinkScale`) is untouched and irrelevant here — these tables are server-driven. Test is `EffectiveTableSpeedTest` (4 cases: solo honours, human-MP forces Normal, subsidized-bot forces Normal, private-practice-bot honours).
**Deferred:** None.

## fix(lobby): validate join code in place, no flicker on a bad code (ROOM-5)

**Problem:** Typing a wrong room code on the PrivateJoin screen "looked like a navigation event" — the screen pushed the seated Lobby, the Lobby 404'd, then bounced back to PrivateJoin with the error. Two route batches for a typo.
**Approach:** Validated the code on the input screen instead of funneling through the Lobby first. New `PrivateJoinViewModel` attempts the join in place; a bad code (or full / not-joinable / over-balance / network) shows an inline error with zero navigation, and only a confirmed-good code navigates on to the seated Lobby (which re-attaches idempotently via the prefilled code — the server returns `alreadyJoined`). Made `PrivateJoinScreen` stateless (state + onAction) per the screen-content convention. Chose the in-place-validate-then-navigate shape over threading the joined `Room` object through navigation (heavy, non-serializable) — the one idempotent re-join on the success path is the documented `alreadyJoined` contract.
**Reviewer notes:** The Lobby's own `JoinCodeRejected` → bounce path is intentionally KEPT — it still serves the deep-link case (`cards://join/{code}` with a dead code, where there's no input screen behind it). For that bounce, `PrivateJoinViewModel` seeds the field + inline error from the assisted `rejectedCode` WITHOUT re-joining (the lobby already 404'd). Tests: `PrivateJoinViewModelTest` (bad code → inline error + no nav event + one join call; success → NavigateToLobby; deep-link seed → no re-join; uppercase/cap). All `:apps:integration` presence tests still green (they drive `LobbyViewModel` with `prefilledCode` directly, an unchanged path).
**Deferred:** MP-25 (showdown never shown) was investigated this cycle but NOT picked. The engine (`GameEngine.runShowdown`) correctly emits `HandEnded` with `revealedHoleCards` and advances River→Showdown→Complete in one step, and `GameSession.applyIntent`'s `handJustFinished` branch (which logs "Hand N finished" + fires `onHandFinished`) catches that same `street→Complete` transition — both the fold path and the showdown path look correct at every layer I can test. The case's only hard evidence is a *missing* "Hand 4 finished" Loki line for the one multiway-river hand, which can't be reconciled with the code paths without the runtime room log (room BY6HUV, session 555cc081, ~22:09:57Z). ## fix(lobby): joiner buy-in never regresses to $0 on a presence snapshot (MP-24)

**Problem:** A joiner who entered a real-buy-in room via PrivateJoin saw the lobby buy-in render as $0 on a post-#74 build. The HTTP join response carried the real stakes (server debited them), but the first socket lobby presence snapshot — which carries the converged member list with `buyIn = 0` — clobbered them via `LobbyViewModel.ConnectionUpdated`'s unconditional `room = conn.room`.
**Approach:** Added `Room.mergeStakesFrom(previous)` — a field-level counterpart to `preferRealOver` — and applied it in the VM's `Connected` branch (`conn.room.mergeStakesFrom(it.room)`). When the incoming snapshot is a placeholder (`buyIn <= 0`) but we already hold a real room, it keeps the new snapshot's members/status/presence and only carries forward the real `buyIn`/`smallBlind`/`bigBlind`. Chose the merge over the reverted `preferRealOver` approach (commit 8df4dbbf) because the latter drops the whole presence snapshot — including the converged member list — which is exactly what broke 11 `:apps:integration` presence tests; merging preserves member-list convergence. Chose the VM seam over seeding the socket's `lastRealRoom` from the repo because both the staged HTTP-join room and the incoming snapshot already meet in the VM, with no cross-module state handoff or socket→repo dependency.
**Reviewer notes:** Test-first: `LobbyViewModelTest.join_realBuyIn_thenPlaceholderPresenceSnapshot_keepsRealBuyIn` is red without the VM change (buy-in regresses to 0) and green with it; verified `:apps:integration:testDebugUnitTest` stays green (the regression the prior attempt caused). The socket-side MP-16 guard (`preferRealOver(lastRealRoom)` in `ReconnectingRoomSocket`) is untouched and still correct for the host rebound case; this is the missing joiner-side arm where `lastRealRoom` starts null so the socket guard can't help. Diagnosis matches the feedback case (room AS4UPA, session 016a8a61) exactly.
**Deferred:** None.

## feat(rooms): host felt + card back shown table-wide to every player (SHOP-3)

**Problem:** Felt + card back were per-player only — a host who bought a felt couldn't make the whole table see it, so there was no social pull to buy cosmetics.
**Approach:** Added two opaque fields — `feltProductId` + `cardBackProductId` — to the room across the full stack (server `Room`/`RoomDto`/`CreateRoomRequest`/route + `RoomsTable` column + V82 migration + `PostgresRoomStore` round-trip; client `Room`/`RoomDto`/`CreateRoomRequestDto`/`RoomRepository.createRoom`). **Directional call:** the table's look = the host's *already-equipped* felt + card back, resolved at create time in `LobbyViewModel` via a new shared `equippedTableCosmetics` helper (`:libraries:cards`), not a new in-create picker. The play surface reads them off the room snapshot through a new `PokerSession.tableCosmetics` flow (populated in `RemotePokerSession` from `RoomConnection.Connected.room`, constant-null for solo) and `PlayPokerViewModel` combines it with the local equipped flow so the host's choice wins per-slot, else falls back to the player's own. Server keeps the ids opaque (never maps to a style); the felt/card-back mapping stays client-only. Chose host-equipped over a dedicated create-screen picker (smallest honest read of "the host's selection already exists per-player; this makes it table-wide", one source of truth, no second UI to keep in sync); chose room-level over per-seat (it's one host choice for the whole table).
**Reviewer notes:** Tests: server `RoomRoutesTest` (cosmetics ride the create body onto the snapshot; blank → null) + `PostgresRoomStoreTest` (survive a restart); `:libraries:cards` `EquippedTableCosmeticsTest` (resolution rule); `LobbyViewModelTest` (host's equipped forwarded to `createRoom`, nothing-equipped → nulls); `PlayPokerViewModelTest` (host felt/card back override the player's own, per-slot fallback when host set only one). `mergeStakesFrom` now also carries the cosmetics forward across a placeholder presence frame, mirroring the stakes (so the look doesn't blink on a converged member-list snapshot). I deliberately did NOT flip `isPersonalCosmetic(felt/cardBack)` — a non-host's felt/back is still personal, so the shop's "Only visible to you" badge stays correct; the table-wide-ness is a property of being the host. Verified `:apps:server:test` (room routes/store/service), `:apps:compose:assembleDebug`, iOS Kotlin compile of room/lobby/rooms-impl, and `:apps:integration:testDebugUnitTest`.
**Deferred:** A dedicated felt/card-back picker inside the create-room screen (an explicit per-room override distinct from the host's standing equip) — noted in `docs/decisions.md` as a reviewer-triageable follow-up; nothing filed yet, reviewer please decide if product wants it (would be a SHOP-* backlog item).

## fix(rooms): reveal showdown off the Complete snapshot, not the event (MP-25)

**Problem:** A tester reached a multiway-river hand and "didn't see a showdown" — the table jumped River → Complete → next hand with no opponent hole-card reveal. The case theorised either the server not emitting a reveal or the client not holding Complete long enough.

**Approach:** Pulled the Grafana logs for room BY6HUV (session 607adee8): the fold-ended hands logged "Hand N finished" but the two showdown hands (1 + 4) did not — yet the client received `street=Complete` for them. I wrote a server-side repro first (`GameSessionShowdownTest`, scripted deck, heads-up check-down to river) and it PASSED — `GameSession.applyIntent` fires `onHandFinished` on a showdown exactly like a fold, so the server resolution path is correct (the missing log line is a renumber/reconnect artifact, not a GameSession bug). That localised the defect to the client: `TableUiState.fromGameState` gated the opponent-card reveal on `lastWinners != null` — i.e. on the transient `HandEnded` *event* arriving — even though the server already keeps in-hand seats' hole cards visible on the `Complete` *snapshot* (`GameStateScrub`) and scrubs folders to empty. So if the `HandEnded` event was lost, rolled out of the replay-16 event buffer, or raced by the next hand's snapshot, the snapshot alone never revealed the showdown. Fix: at `street == Complete`, drop `hideHoleCards` for opponents so the reveal comes off the authoritative snapshot, independent of the event. The existing `HandEnded`-driven `handResult` dialog/winner path is untouched — this only makes the *card* reveal robust to event loss.

**Reviewer notes:** Test-first. Client red→green: `TableUiStateTest.completeSnapshot_revealsInHandOpponentCards_evenWithoutHandEndedEvent` (was hidden, now revealed) plus two guards that the fix doesn't leak — `completeSnapshot_keepsFoldedOpponentMucked` (folders mucked → empty) and `midHandSnapshot_stillHidesOpponentCards` (reveal is Complete-gated, no mid-hand leak). End-to-end scenario guard in `PokerScenarioMpTest.showdownSnapshotWithoutHandEndedEvent_stillRevealsOpponentCards` pushes ONLY the Complete snapshot (no `HandEnded`) and asserts seat 1's cards show. Server guard `GameSessionShowdownTest` documents the showdown completion path is correct + marks the win as showdown, not fold. The reveal is safe because the server never puts a non-showdown opponent's cards on the wire — `scrubbedFor` only keeps cards for `isInHand` seats at Showdown/Complete; a folder's are already empty. Verified `:features:room:impl:testDebugUnitTest`, `:apps:server:test`, `:apps:integration:testDebugUnitTest`, `:apps:compose:assembleDebug`, and room-impl iOS Kotlin compile.

**Deferred:** The deck-scripting helper (`cards()` + a stacked-deck builder) is now duplicated in three test surfaces — `:apps:integration` `DeckScripting.kt`, `:features:room:impl` `ScenarioDecks.kt`, and now an inline copy in `GameSessionShowdownTest`. The existing TODO comment in those files says "unify into a shared gameplay-testing module if a third consumer appears" — that third consumer has now appeared. Filed to `docs/backlog.md` as a `:libraries:gameplay:testing` extraction; kept the inline copy this cycle to avoid a Gradle-module refactor riding on a bug fix. Reviewer: triage whether the extraction is worth a dedicated item.

## feat(billing): iOS StoreKit 2 client via a Swift coordinator (BILL-4)

**Problem:** `libraries/billing/impl/src/iosMain` was empty, so iOS release builds had no real IAP — only the Fake/NoOp fallback. BILL-4 was the last open todo item; two prior workers deferred it as needing interactive Xcode `.storekit` verification.

**Approach:** Built the whole code path (the deferral was about *runtime* verification, not buildability — the item's own acceptance says it's locally buildable). Mirrored the `AppleSignInCoordinator` seam exactly: a non-suspend, callback-shaped `StoreKitCoordinator` interface in `:libraries:billing` (commonMain) trading in flattened primitive shapes (`StoreKitProduct`/`StoreKitPurchaseResult`) so a Swift class satisfies it trivially with no `suspend`/sealed-type bridging; a `StoreKitBillingClient` in iosMain that selects Fake-in-debug / real-in-release like `PlayBillingClient`; an `AndroidStoreKitCoordinator` no-op so the Android graph compiles; the Swift `IOSStoreKitCoordinator` driving StoreKit 2; and the wiring through `IosAppComponent` + `iOSApp.swift`. The result→`PurchaseResult` mapping lives in commonMain and is the unit-tested seam.

**Approach (the load-bearing call):** **The signed JWS is the single `purchaseToken`.** StoreKit splits what Play unifies — the JWS is the server-validation proof (`/v1/billing/redeem` → `AppStoreReceiptValidator`), and a separate `Transaction` handle is what `finish()` consumes. The shared `BillingClient` has only one `purchaseToken`, passed to both `redeem` and `consume`. So JWS → `purchaseToken`, StoreKit `transaction.id` → `orderId` (the local idempotency key on the dark-launch credit path), and the Swift coordinator retains the unfinished `Transaction` keyed by its JWS for `finishTransaction(jws)`. One id end-to-end, zero new fields on the cross-platform contract. Rejected: adding a second consume-token field (reshapes the contract for one platform's quirk) and decoding the JWS client-side for the tx id (needless crypto; `transaction.id` is already in hand). Full rationale in `docs/decisions.md`.

**Reviewer notes:** Mapping is the tested seam — `StoreKitCoordinatorMappingTest` (8 cases: success→Apple tx, JWS≠orderId, already-owned, success-without-verified-tx downgrades to Failed not an unverified credit, cancel/pending/failed, product mapping). The Swift coordinator and the thin K/N wrapper aren't unit-tested (StoreKit needs a device or `.storekit` config — developer-gated). Verified: Android `assembleDebug` (no-op binding composes into the real graph), billing api+impl iOS Kotlin compile, `:apps:compose` iOS Kotlin compile + debug-framework link (SKIE exports `BillingStoreKitCoordinator`/`...Product`/`...PurchaseResult`/`...PurchaseStatus` — confirmed in the generated header + SKIE enum bridge, enum cases are camelCase `.userCancelled` etc.), `:apps:integration` tests, and `IOSStoreKitCoordinator.swift` **type-checks clean against the framework** (`swiftc -typecheck`, zero errors/warnings — the `@MainActor`-conformance warning is gone via an `actor`-isolated transaction cache). NOTE: a full `xcodebuild` of the iOS app currently fails on **pre-existing** errors unrelated to this change (`VirtuNativeAppleSignInButtonKind`, `PermissionStatus` "cannot find type" in `IOSNativeViewFactory.swift`/`PermissionManager.swift` — a stale SKIE module-resolution state in this checkout); I confirmed those reproduce with my files stashed out. A `Cards.storekit` test config ships at `apps/ios/iosApp/Cards.storekit` ready to attach to the run scheme.

**Deferred:** End-to-end purchase verification against the `.storekit` config (attach it to the run scheme's StoreKit Configuration, run a release build, buy a pack twice) is the developer-gated step — captured as QA `BILL-4` in `docs/QA.md`. The pre-existing iOS-app `xcodebuild` SKIE-resolution failure is environmental (not from this change) — reviewer may want to flag it for the human if it persists in CI.
