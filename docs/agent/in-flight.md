# In-flight (2026-06-23 cycle)

## fix(server): hard-delete users on account deletion

**Problem:** `DELETE /v1/me` called Supabase admin delete-user with no body, so GoTrue soft-deleted by default — the `auth.users` row stayed, the credential kept authenticating, and the design's `ON DELETE CASCADE` never fired (a tester re-logged-in after "deleting"). CARDS-1T.
**Approach:** `HttpSupabaseAdminClient.deleteUser` now sends `{"should_soft_delete": false}` as a JSON body on the DELETE, forcing GoTrue to hard-delete the row + cascade. Added a body assertion to the success test (the existing tests only checked URL/headers).
**Reviewer notes:** None — body shape matches the GoTrue admin API. Can't end-to-end verify against a live Supabase from here; covered by the MockEngine body assertion.

## feat(rooms): gate private room join on wallet balance

**Problem:** `POST /v1/rooms/{code}/join` had no wallet-vs-buy-in check (unlike matchmaking's find path), so a tester joined a room whose buy-in exceeded their chips and was silently demoted to spectator by escrow. CARDS-1G.
**Approach:** Server gate added to the join route — fetch the room, and if the caller isn't already a member and `room.buyIn > balance`, reject `400 insufficient_balance` (mirrors `MatchmakingRoutes`; re-joins skip the check since they already sat down). Client maps the code to a new `JoinRoomOutcome.OverBalance(message)` → `LobbyError.JoinOverBalance`, surfacing the server's message inline like `CreateInvalidMaxSeats` does (no new string resource needed). Tests on both sides.
**Reviewer notes:** The over-balance message is rendered server-side and shown verbatim (server-supplied copy is the AGENTS.md exception to the resources rule, same as `CreateInvalidMaxSeats`). Unknown codes still fall through to join()'s 404 — the gate only fires when the room exists.

## fix(room): land on Home when leaving a private MP game

**Problem:** Leaving a private multiplayer game dropped the player back into the dead lobby instead of Home. CARDS-1Y.
**Approach:** A private game pushes `PlayMultiplayerRoute` on top of its `LobbyRoute`, so the old `goBack()` (pop one) + `switchTab(Home)` left the lobby underneath. The leave `onBack` now branches on `route.kind`: Private pops the whole chain with `popBackTo(LobbyRoute(), inclusive = true)` (lands on the Home tab root), Public keeps the existing `goBack + switchTab(Home)` since it has no lobby beneath it. Verified both Private entry paths (lobby start + Home active-room banner) route through a `LobbyRoute`, so the pop target always exists.
**Reviewer notes:** Entry-point routing lambda — no VM, so not unit-testable here (it's pure `Router` calls). The `OpponentsLeft` event still intentionally routes a private game to `LobbyRoute(prefilledCode)` (lone player can re-invite); only the explicit-leave path changed.

## feat(room): notice when a non-last opponent leaves a live MP table

**Problem:** When one of several opponents left an in-progress MP game, the remaining player got nothing — no toast, no "X left the table". The two existing leave signals only covered the terminal cases (`opponentsLeft` last-human-standing, `roomClosed`); a mid-game leave with 2+ humans still present was unsurfaced (CARDS-1E).
**Approach:** Reworked `RemotePokerSession.collectConnection` to diff the human member *set* (id → name) across snapshots instead of just a count, and added a new `opponentLeft: SharedFlow<String>` to `PokerSession` carrying the leaver's display name. When a known human disappears while 2+ humans remain it fires the per-opponent notice; the terminal "last human standing" case still routes through the unchanged `opponentsLeft`. The VM forwards it as `PlayPokerEvent.OpponentLeft(displayName)`, and the MP entry point toasts "X left the table" (new `room_opponent_left` string, 👋). Chose a snackbar for the notice — the vacated-seat half already exists (`SeatView.seatEmpty` renders off the server's next snapshot, which already drops the member), so the only missing half was the notice; rejected adding a separate seat flag as redundant.
**Reviewer notes:** `opponentLeft` is `replay = 0` (a live notice, unlike the terminal `opponentsLeft`'s `replay = 1`) so a screen re-subscribe can't re-toast a stale departure. Defaulted on the interface to a never-emitting flow so `LocalBotsSession` + test fakes don't override it. Detection is unit-tested in `RemotePokerSessionTest` (non-last leave emits name + not the terminal signal; last leave fires terminal + not the per-opponent notice; baseline snapshot is silent). The snackbar wiring in the entry point is pure `Router`/`showSnackBar` calls (no VM), so it's preview/behaviour-covered rather than unit-tested, same as the existing quick-buy toast.

## fix(lobby): keep a bad join code on the input screen with an inline error

**Problem:** Joining a private room with an unknown/expired code routed the user somewhere clunky ("ewww") — the PrivateJoin screen pops itself on the way into the lobby, so a `JoinRoomOutcome.NotFound` left them stranded on the dead lobby spinner with a red error and no way to retry the code. CARDS-28.
**Approach:** When a *prefilled-code* join (the PrivateJoin → Lobby funnel) hits NotFound, the VM now emits a new `LobbyEvent.JoinCodeRejected(code)` instead of setting the inline `JoinRoomNotFound` error; the entry point pops the dead lobby and routes back to `PrivateJoinRoute(rejectedCode = code)`. `PrivateJoinScreen` grew a `rejectedCode` arg that pre-fills the field and shows an inline "No room with code X" error until the user edits a character. A *non-prefilled* join (no input screen behind it) keeps the original inline-error behaviour. Scoped strictly to NotFound — Full/NotJoinable/OverBalance aren't "wrong code" cases the input screen helps with (OverBalance just shipped its own inline handling this cycle).
**Reviewer notes:** `PrivateJoinRoute` became a `data class` carrying a nullable arg (was a bare `class`) — still a `class`, not a `data object`, so the iOS-navigator SIGSEGV rule holds (mirrors `LobbyRoute`, which is a `data class` with args). The bounce-back relies on `popBackTo` matching by route *type* not arg value — confirmed against the existing `PlayMultiplayer`→`popBackTo(LobbyRoute())` precedent (which pops the real `LobbyRoute(prefilledCode=…)` entry). Reused the existing `lobby_error_join_not_found` string (shared resources module) rather than adding a duplicate. VM bounce path is unit-tested; the screen's inline error is preview-covered (`PrivateJoinScreenPreview_RoomNotFound`).

## fix(rooms): coerce unknown room-enum values on the socket in release

**Problem:** `RoomSocketJson` set `ignoreUnknownKeys` but not `coerceInputValues`, so a future server enum *value* the client doesn't know (a 4th `RoomStatus`/`RoomVisibility`) threw `SerializationException` and the whole room snapshot frame was dropped — freezing the live room UI until the client shipped a matching enum.
**Approach:** Took the todo's recommended option (a): build-gated `coerceInputValues = !BuildInfo.isDebug`, mirroring `NetworkJson`. Release coerces an unknown status/visibility to the property default (`RoomStatusDto.Unknown` / `RoomVisibilityDto.Private`, both of which already existed for exactly this), so the frame still decodes; debug stays strict to catch contract drift loud. Unknown *discriminator* values still throw (no safe default for an undispatchable frame type) — unchanged, still dropped at the `ReconnectingRoomSocket` call site.
**Reviewer notes:** Tests run in debug where the production `RoomSocketJson` stays strict, so the new `RoomSocketWireFormatTest` case mirrors the release config in a local `Json` to pin the coerce — it can't exercise the production instance's release branch directly. The enum defaults this leans on landed in the 2026-06-23 HTTP-path fix; this just extends the same safety valve to the socket path.
