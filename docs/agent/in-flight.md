## feat(rooms): source MatchmakingRadar reduce-motion from the platform

**Problem:** `PublicSearchingScreen` hardcoded `MatchmakingRadar(reduceMotion = false)`; the accessibility setting was never read, so the looping radar always animated even for users who asked the OS to minimize motion.
**Approach:** Added a `@Composable expect fun isReduceMotionEnabled()` in `:libraries:ui` (mirrors the existing `CameraPreview` expect/actual shape) with three actuals — Android reads `Settings.Global.TRANSITION_ANIMATION_SCALE == 0` (the platform-standard probe; there's no dedicated flag), iOS reads `UIAccessibilityIsReduceMotionEnabled()`, JVM returns `false` (no desktop signal, preview-only). Wired the screen to call it. Chose the global-transition-scale probe over an `AccessibilityManager`-based listener because the radar only needs a one-shot read at composition, not a reactive stream.
**Reviewer notes:** Android `TRANSITION_ANIMATION_SCALE` is read once at composition, so a mid-screen toggle won't update until recomposition — acceptable for a transient searching screen. Verified `:apps:compose:assembleDebug` + `compileKotlinIosSimulatorArm64` both build. New primitive is a candidate for reuse by other looping DS animations (level-up confetti, etc.).

## feat(server): enforce per-turn time limit in multiplayer

**Problem:** Nothing stopped a multiplayer player from sitting on their action forever — `RoomSettings.turnTimerSeconds` (default 30) was carried but never enforced, so one AFK/stalling seat could freeze the whole table.
**Approach:** Added `TurnTimerDriver`, a per-session driver modeled on `ServerBotDriver`: it `collectLatest`s `GameSession.state`, arms a `delay(turnTimerSeconds)` whenever a **human** seat is on the clock, and on expiry submits an auto-action — `Check` when the seat owes nothing to the current bet, else `Fold`. Wired into `DefaultGameSessionRegistry.createSession`/`end` alongside the bot driver (same `botDriverScope` lifecycle). Scoped to human seats deliberately: bots already act in ~2s via the bot driver, so timing them too would only race for the same (nonce-deduped) apply. Deterministic nonce `timeout:<session>:<hand>:<seat>:<street>` + the session's existing `actingSeatIndex` re-check make a stale fire a safe no-op.
**Reviewer notes:** This is the server-enforcement half of the old "Per-turn time limit" item; I sliced off the client countdown and rewrote the todo (now P2) — no wire change is needed for it since `GameState.settings.turnTimerSeconds` + `actingSeatIndex` already reach the client. Verified with `TurnTimerDriverTest` (auto-fold facing a bet, auto-check when legal, leaves bot seats alone, no double-act when the player acts in time) — all green, full `:apps:server:test` green. One UX note for the reviewer: until the client countdown lands, an auto-fold/check arrives with no on-screen warning; 30s is generous, and the alternative (indefinite stall) is strictly worse, but worth knowing.
**Deferred:** The client-side visible countdown — left as the rewritten P2 todo bullet for a worker who can eyeball it in Studio.

## feat(social): add recent-opponents + friend-request client repositories

**Problem:** The recently-played-with shelf + add-friend were stubbed on the client — the server endpoints (`GET /v1/recent-opponents`, `GET /v1/profiles`, `POST /v1/friends/requests`) shipped but no KMP client existed to consume them (P0 "Recently-played-with — client wiring").
**Approach:** New `:libraries:social` (api) + `:libraries:social:impl` modules. `RecentOpponentsRepository` does the server's two-step resolve (bare ids → `/v1/profiles`), preserving newest-first order and dropping ids that don't resolve. `FriendRepository.sendRequest` maps the server's status codes onto a typed `SendFriendRequestResult` (403 → NotPlayedWith, 400 → SelfRequest, 429 → RateLimited). Both sit behind a faked `SocialApi` seam. Chose a fresh module over folding into `:libraries:identity` because the friend graph is its own concern and the remaining social items (inbox, presence, friends list) will extend these same repos.
**Reviewer notes:** DTOs declare `schemaVersion` so debug's strict (`ignoreUnknownKeys = false`) JSON doesn't throw on the server's version field. The `403` mapping conflates not-played-with with a blocked pair (the server returns 403 for both) — fine until the block UI exists. Full unit coverage (`RecentOpponentsRepositoryImplTest`, `FriendRepositoryImplTest` via MockEngine-built `ClientRequestException`); `:apps:compose:assembleDebug` green so the new bindings wire into the DI graph. Home wiring lands in the next commit.

## feat(room): surface the per-turn countdown ring on the table

**Problem:** Server-side `TurnTimerDriver` auto-folds/checks a human who stalls past `RoomSettings.turnTimerSeconds`, but the client showed nothing — an auto-action landed with no on-screen warning (the deferred client half of the per-turn-timer item).
**Approach:** New DS primitive `TurnCountdownRing` (`:libraries:ui` poker package) draws a depleting arc around the acting seat's avatar, blending to the danger color through the final quarter; it's self-contained (internal `Animatable` 1f→0f over the duration) and re-arms whenever its `turnKey` changes. `TableUiState.Active` now carries `turnTimerSeconds` (null on solo — suppresses the ring) + `turnSequence` (`GameState.lastSequence`); `fromGameState` gained a `turnTimerEnforced` flag that only `RemotePokerSessionFactory` sets true. Wired into the human seat (`PlayerArea`) and human opponents (`OpponentsRow`); bot seats keep the plain `PulsingActiveRing` since bots act fast server-side and aren't timed. Turn token is `handNumber to lastSequence` — chosen over keying on `actingSeatIndex` because a raise that returns action to the same seat keeps the same index but bumps the sequence, exactly when the server re-arms its own `collectLatest` delay; the alternative (key on acting-seat-index) would leave the ring stale on a re-raise-back-to-you.
**Reviewer notes:** Purely visual — server stays authoritative on the actual fold. No numeric seconds shown; the depleting arc IS the countdown (a number would collide with the avatar / blind marker / last-action pill that already crowd the seat). If you'd rather have a digit, it's an easy follow-up — anchor a small pill off the ring. Wants a Studio eyeball to confirm the ring reads well at the opponent avatar sizes (40–76dp packed, 56dp scrolling) and around the 56dp human avatar; verified `:apps:compose:assembleDebug` + `compileKotlinIosSimulatorArm64` build and added `TableUiStateTest` cases for the new plumbing (off by default, surfaces the setting + sequence when enforced) plus `@Preview`s for the human + opponent countdown. Edge: when the human flips their tile to the win-odds back face mid-turn the ring isn't visible (only the front face has the avatar) — acceptable, they'd flip back to act.

## fix(app): collapse the double banner when account setup is pending offline

**Problem:** A first-launch account creation that's pending because the device is offline stacked TWO top-of-screen strips — the generic offline banner and the `AccountSetupBanner` "finishing account setup" — eating vertical space restating one situation.
**Approach:** New `AppStatusBanners` host owns both the offline signal (`LocalAppState.isOffline`) and the account-setup status, and when both fire it renders a single scenario-specific line ("You can keep playing offline, and we'll finish creating your profile once you're back online") with no Retry affordance (only reconnecting resolves it, which `GuestAccountCreator` already auto-retries). Outside that overlap each banner shows standalone exactly as before. Lifted the once-failed gating into a shared `rememberAccountSetupStatus` so both the standalone banner and the combined host decide visibility off one source, and made the two content composables internal for reuse. `AppGuardBanner` stays separate (maintenance/upgrade, not a connection state). Chose "suppress both, show one combined" over "hide just the offline banner" because the merged copy reads better than the account-setup line alone, which doesn't mention you can keep playing.
**Reviewer notes:** Also externalized the offline banner's inline copy (it was an inline literal with an em dash — double AGENTS violation) to `app_offline_banner_message` ("Offline, some features unavailable." — comma, no em dash) while in the file. `OfflineBanner()` / `AccountSetupBanner()` public composables are now unused by the app (the host calls the content directly) but kept as the documented standalone API. Couldn't unit-test top-level composables without Compose UI tests; logic is a pure boolean fork on `isOffline && pending`. Wants a quick Studio/device eyeball of the three states (offline only, pending only, both → one banner). Verified `:apps:compose:assembleDebug` + `compileKotlinIosSimulatorArm64`.

## fix(splash): loop the boot-loading fan so it never reads frozen

**Problem:** On a slow/offline cold boot the post-splash `BootLoadingScreen` rendered `CardsFan(fanProgress = 1f)` statically — the "snapped to fully-fanned and held" look from the 2026-06-20 playtest — and `CyclingLoadingMessage`'s 5s default `startDelay` meant "Shuffling the deck" only appeared after a long hold.
**Approach:** `BootLoadingScreen` now drives `fanProgress` with an `Animatable` that loops fan-in (0.2f) → fan-out (1f) on `EaseInOutCubic`, matching the iOS `SplashOverlay` pulse — exactly the "animating 0 → 1 → 0 on loop" usage `CardsFan`'s own KDoc documents but the boot gate wasn't using. Dropped the caption start-delay default from 5s to 1.5s so the status text cycles during the wait (still long enough that a sub-second online boot never flashes it). The iOS `SplashOverlay` already animates its fan-out smoothly through a tween, so the only frozen surface was this gate.
**Reviewer notes:** Purely visual; verified `:apps:compose:assembleDebug` + `compileKotlinIosSimulatorArm64` build (Preview-deprecation warnings are pre-existing across the module). Wants an iOS cold-boot eyeball to confirm the splash→boot-gate handoff reads continuous (both now pulse the same fan, so there should be no snap). 1.5s caption delay is a judgement call — short enough to cycle on a real wait, long enough not to flash on a fast boot.
