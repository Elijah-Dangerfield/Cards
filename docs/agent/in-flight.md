# In-flight (worker handoff log)

## feat(config): JsonConfigValue<T> for structured (non-scalar) config

**Problem:** The config system only resolved flat dotted-path scalars (`FlagConfigValue`/`IntConfigValue`/…); variable-length structured data (the level ladder + reward table, future loot tables) couldn't be flattened into fixed scalar paths.
**Approach:** Added `JsonConfigValue<T>` in `:libraries:config` — resolves one path to its parsed config subtree, converts it back to a kotlinx `JsonElement` (`toJsonElement` inverse of the parse), and `decodeFromJsonElement` into a `@Serializable` model via a constructor-supplied `KSerializer<T>`. Decode failure or missing path falls back to the bundled `default` (soft-fail, so a malformed server value never bricks the client). Chose the `KSerializer` constructor param over reified `serializer()` so the base stays a plain abstract class with no inline/reified plumbing. Hidden from the QA dashboard by default (a JSON blob can't round-trip the per-key toggles, per the todo note). Pulled in `kotlinx-serialization-json` (runtime only — no compiler plugin needed for the base since it declares no `@Serializable` types).
**Reviewer notes:** Tests live in `:libraries:config:impl` commonTest (where the serialization plugin is already on) since `:libraries:config` itself has no test source set. Covered: nested-object decode, array decode, missing-path/empty fallback, undecodable-payload soft-fall-back, unknown-key tolerance, model-default for omitted optional field. The level-ladder todo's "Depends on: the JsonConfigValue config-lib extension" is now satisfied — left that item's wording untouched (curation surface).

## feat(server): persist server-witnessed finished-hand count

**Problem:** MP achievement grants want to gate on a real hand count, but the server didn't expose a per-user `hands_finished` count — even though it now runs the authoritative hand loop.
**Approach:** Sliced the "MP achievement grants — server-witnessed hand-count signal" todo to its foundational half: the server now *witnesses* and persists the count. New append-only `hand_finished_events` ledger (`V56`, mirrors the `xp_events` pattern: `(user_id, idempotency_key)` PK is the dedup boundary, key shape `<sessionId>:<handNumber>:<userId>`). `GameSession` gained an `onHandFinished` callback that fires once on the transition into `BettingRound.Complete` with the human seats (bots excluded); `DefaultGameSessionRegistry` wires it to the new `HandsFinishedRepository`, parsing seat userIds to UUIDs and skipping non-UUIDs defensively. Counter writes are best-effort (`Catching`) so a DB hiccup can't break gameplay. Deliberately did **not** add an HTTP endpoint (no client consumer — the client tracks its own local count; server-side gating will read the repo internally) nor a summary row (gating reads are infrequent, so `COUNT(*)` over the PK prefix is enough). Left the actual MP-achievement *gating* (server-side evaluation + the MP-achievement→product mapping those ids lack) as the remaining todo slice.
**Reviewer notes:** Two judgement calls worth a glance: (1) the registry's `handsFinishedRepository` constructor param is **last + defaulted to `NoOpHandsFinishedRepository`** so the ~17 existing positional/named test constructions stay valid — DI always resolves the real binding into it, so the default is dead code on the wired path (same shape as the existing `NoOpSessionSnapshotStore`). (2) hand-finished fires from `GameSession.applyIntent`'s completion transition only; it can't double-fire (post-`Complete` intents are rejected) and `hydrate` (snapshot replay) doesn't fire it — plus the idempotency key dedups a replay anyway. Tests: `GameSessionTest` (callback fires once / excludes bots / not on a non-completing call), `GameSessionRegistryIntegrationTest` (real-UUID counting + per-hand keying via `InMemoryHandsFinishedRepository`), `PostgresHandsFinishedRepositoryTest` (DB idempotency / per-user scoping / delete). Full `:apps:server:test` green. `deleteAllForUser` wired into the `DELETE /v1/me` cascade for parity (FK cascade already covers the auth-delete path).
