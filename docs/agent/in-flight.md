## feat(server): emit anon-orphan-count gauge via OTel metrics

**Problem:** `docs/todo.md` §C asked for a scheduled OTel gauge measuring how many orphan anonymous Supabase users have accumulated, so we can tell whether the [device-keyed backup sweep](docs/decisions.md) needs to come out of park. No metric existed; the server's OTel SDK was traces+logs only, no MeterProvider.
**Approach:** Wired a `SdkMeterProvider` into `buildOpenTelemetrySdk` (OTLP/HTTP exporter when `OTEL_EXPORTER_OTLP_ENDPOINT` is set, `LoggingMetricExporter` stdout fallback otherwise, 60s `PeriodicMetricReader`). Added a new `ServerMetrics` top-level object that mirrors `serverTracer`'s shape — no DI, registered from `installOpenTelemetry`. Sweep records the candidate count + the TTL it used on every run via `ServerMetrics.recordAnonOrphanCandidates(...)`; gauge callback skips emission while the sentinel -1 is set so a freshly booted server doesn't post a fake "0 orphans" before the first sweep.

**Key direction call:** I named the metric `cards.anon_orphans.over_ttl` and attribute the configured TTL (currently 30 days, env `ORPHAN_ANON_TTL_DAYS`), instead of the todo's literal `cards.anon_orphans.over_90d`. Rationale: the sweep already paginates the full anon-user pool with the TTL cutoff to find candidates for deletion; recording that exact list count is one Supabase listing per sweep. A literal 90d metric would require a second full paginated listing every sweep run (the Admin REST API doesn't expose count-only queries), doubling Supabase API cost for a metric that answers the same "are orphans piling up?" question. The TTL attribute keeps the metric meaningful if the env knob ever moves. The alternative (a second listing) is rejected as wasteful given V1 traffic; ship the TTL-attributed gauge now, add a separate 90d-fixed metric later if the operational story needs the dead-letter signal distinct from the sweep-incoming rate.

**Reviewer notes:** The `ServerMetrics` object pattern matches the existing `Tracing.kt` top-level shape (no DI), which I think is right at this scale — promote to DI when the metric set grows past a handful. Test layout: I merged the metrics assertions into `TelemetryTest` rather than standing up a parallel class, because `GlobalOpenTelemetry` is set-once per classloader and competing test classes on the global slot would race each other. The sweep-side test uses internal debug accessors (`ServerMetrics.debugLastAnonOrphanCount` / `…TtlDays`) rather than wiring a real meter — avoids the same global-slot conflict and keeps the sweep test scope on the sweep.

One thing worth a second look: the gauge is `ObservableLongGauge` with a callback that re-emits the cached value on every export interval. That means between daily sweep runs (24h) the line stays flat at the last-recorded value, which is the right behavior for "current orphan-pool size" semantics — but if the reviewer wants the metric to read as "events" instead (only emit when sweep runs), swap to synchronous `LongGauge.set` and the line will be sparse rather than continuous. Continuous is what I'd want for dashboarding; flagging in case the operational pattern disagrees.
**Deferred:** A literal `over_90d` dead-letter metric (rejected per Approach above; can land later if the TTL-based gauge ever shows a value that's hard to interpret). The `[P1]` "expand OTel span coverage on broadcast + per-recipient ws-send" item — context propagation through the publisher Flow chain is the meaty half; left untouched since this commit was already wide enough.
