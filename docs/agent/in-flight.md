## fix: attribute MP hand outcomes to the local seat, not seat 0

**Problem:** Folding a multiplayer hand still credited `SHOW_*` achievements ("show a straight at showdown") even though the player never reached showdown.
**Approach:** Root cause was `PlayPokerViewModel.humanSeatIndex` hard-coded to `0`. Solo always seats the human at 0, but MP allocates any seat — so every per-hand attribution (XP, achievements, win-odds equity) was computed against seat 0's outcome. A folded human at seat 1 inherited seat 0's showdown hand. Added `PokerSessionFactory.humanSeatIndex(state)` (solo: fixed seat; remote: match `localUserId`, `-1` when not seated so a missing match yields no credit instead of crediting the wrong seat) and resolved the real seat at the two attribution sites (`handleHandEnded`, win-odds equity). Also added the belt-and-suspenders `!summary.wasFold` guard on the `Criterion.ShowAtLeast` branch per the todo.
**Reviewer notes:** This also silently fixed the win-odds tool for non-seat-0 MP humans (it was reading seat 0's scrubbed/empty hole cards and giving up). The `-1`-when-not-seated contract is the safe default for spectators. Builder test simulates an over-sharing reveal map (folded human's cards present) to prove `wasFold` still suppresses credit.

## feat: route the level-up celebration to a full-screen destination

**Problem:** The level-up celebration was an overlay inside `HomeScreen` with two bugs: a full-screen `detectTapGestures` dismissed it on any tap, and the bottom nav bar stayed visible (the overlay lived inside Home's content while the app Scaffold kept drawing the bar).
**Approach:** Made it a routed destination (`LevelUpRoute` in `:features:home`, modeled on `BlockingErrorScreen`) — no bottom bar (not in `App.kt` `tabString()`), back swallowed, Continue is the only exit. Dropped the `detectTapGestures { onContinue() }` from the `LevelUpCelebration` DS component. Kept the existing derived gate (`HomeState.levelUpCelebration`); the Home entry point observes it via a remembered `ObserveWithLifecycle` flow and navigates, then fires `HomeAction.MarkLevelUpShown` (renamed from `DismissLevelUp`) **at navigate time** so the watermark advances immediately and the nav is idempotent — no re-fire when Home resumes behind the celebration. **Reviewer notes:** **Directional call — advancing the watermark at show-time, not on Continue.** This is race-free by construction (the only alternative, advance-on-Continue, reintroduces a navigate-on-resume double-push because the cache write is async and Home's composition is disposed on navigate so a `remember` dedup token doesn't survive). The accepted trade-off: a process death *while the celebration is on screen* won't re-show it (rewards are already granted; matches the welcome-dialog persist-at-emit precedent). Full rationale + rejected alternatives in `decisions.md` 2026-06-19. **Couldn't device-verify the nav transition / bottom-bar hide headless** — VM logic is unit-tested (`HomeViewModelTest`, gate→trigger→MarkLevelUpShown→watermark) and the whole client `assembleDebug`s, but the routed transition + no-bottom-bar wants a quick device eyeball. ## test: side-pot settlement over the wire via a 3-client table

**Problem:** Side-pot settlement had no end-to-end wire coverage. `WireAllInTest` only shoves heads-up with equal stacks (single pot, winner-take-all); a genuine side pot needs 3+ seats with unequal stacks, and the integration harness only seated two. (`docs/todo.md` §B6 "Buff the seams".)
**Approach:** Added `seatThreeAndConnect()` + a `Trio` table to the integration harness, then `WireSidePotTest`: hand 1 bleeds one seat short via a fold-out (controllable, no showdown — the integration deck is `Random.Default`, so nothing card-dependent), hand 2 has all three shove → a layered all-in (700/990/1310 → main + two side pots). Asserts card-independent invariants: chip conservation through the wire, and the short seat's settlement is bounded by its main-pot eligibility (`shortFinal <= shortEntering * seats`) — proving the wire honours side-pot eligibility. Roles bind by action order (not seat number) so it's position-robust; drivers read-and-act in one loop to avoid advancing the snapshot cursor past an un-acted turn (that deadlocks the wire). Ran 6× green across random decks + the full `:apps:integration` suite green.
**Reviewer notes:** **Directional call — assert an eligibility *bound*, not exact pot amounts.** With a non-deterministic deck I can't pin who wins, so the strong card-independent invariant is "the short all-in seat can never collect a side pot." I rejected seeding the server's deck (would require threading a `Random` through `GameSessionRegistry.createSession` into `GameSession` just for tests — invasive, and the existing wire tests deliberately stay card-independent). Removed the §B6 side-pot bullet from `docs/todo.md`; ticked the matching boxes in `testing-plan.md` Round 2 fan-out. No production code changed.

## fix: dedupe duplicate intent submission on slow ack / double-tap

**Problem:** `PlayPokerAction.Submit` fired `session.submit` fire-and-forget with no guard. On a slow network (or an impatient double-tap) the user taps an action twice before the resulting snapshot lands, sending the same intent twice — the open Round 5 "UI doesn't double-submit on accidental tap" box.
**Approach:** Added a per-decision dedupe in `PlayPokerViewModel` keyed on the live state's `(handNumber, lastSequence)` — the same identity the client's out-of-order guard uses. Two taps before the snapshot advances read the same token and the second is dropped. **Directional call on the token:** keyed on `lastSequence` (advances on every event), not `actingSeatIndex` (the same seat acts on multiple streets within a hand → would wrongly block a legit later action). The guard is cleared on a *rejected* submit so a corrected resubmit on the same turn (e.g. an illegal raise amount) still goes through; an accepted action advances `lastSequence`, so the next genuine decision carries a fresh token regardless. VM-private field, no state/UI surface change.
**Reviewer notes:** Server already rejects a duplicate (`not your turn`), so this is a UX/load improvement, not a correctness fix — worst case a redundant tap is silently dropped, which is the desired behaviour. Couldn't device-verify the slow-network feel headless; logic is unit-tested three ways (dedupe / next-decision-allowed / reject-then-retry-allowed). Extended `FakePokerSession` with a `submitError` injection and `stubGameState` with a `lastSequence` param to drive those. Did NOT also disable the action buttons while a submit is in-flight — the VM-level drop is sufficient for the box; a visible disabled-state is a reasonable follow-up polish (reviewer please triage).
**Deferred:** The 200ms-RTT latency *transport* simulation (the other half of that Round 5 line) is an `:integration`-tier add — noted inline in `testing-plan.md`, nothing filed yet.
