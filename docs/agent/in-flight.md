## fix(billing): map redeem 4xx to Rejected, not Unavailable (BILL-12)

**MONEY PATH — please eyeball.** Reproduced test-first (red at `expected Rejected / was Unavailable`, green after the fix) in `BillingRepositoryImplTest`.

**Problem:** `BillingRepositoryImpl.redeem` runs through `authedCall`, whose client has `expectSuccess`, so a 400 throws `ClientRequestException` at `client.post(...)` before the old `when(response.status){ BadRequest -> Rejected }` branch could run. `Catching` caught the throw and `getOrDefault(Unavailable)` collapsed a hard `receipt_rejected` into `Unavailable` — the user saw "chips on the way / payment went through" and the unfinished transaction was re-redeemed every launch. The `BadRequest -> Rejected` branch was dead code.
**Approach:** dropped the unreachable status `when` (the success block now just parses the 200 body into `Granted`) and map the failure in `getOrElse`: a `ClientRequestException` (4xx) is the server's definitive "no" on this receipt, so it becomes `Rejected` (honest failure dialog, no false-pending); everything else (5xx / timeout / unreachable) stays `Unavailable` so the launch-time redeemer can still recover a paid-for purchase. This matches `RetryPolicy`'s own transient-vs-permanent split (its default predicate already refuses to retry 4xx). Chose mapping-the-thrown-exception over disabling `expectSuccess` for this one call so the repo keeps the shared client contract the rest of the app relies on.
**Reviewer notes:** A rejected outstanding transaction is still deliberately left unfinished (not consumed) by `DefaultPurchaseChipPackUseCase.redeemOutstanding`, so it keeps being retried on each launch — that's intended and is exactly what lets BILL-11's server fix recover the stranded small/large packs once it lands. Added `ktor-client-mock` + explicit networking/ktor test deps to `:libraries:billing:impl` (main's `implementation` deps aren't on the test classpath in this KMP setup).

## fix(billing): accept receipts from the install's upgrade lineage (BILL-11)

**MONEY PATH — please eyeball.** Server-side pair to BILL-12; new trust model, so I also logged a decisions.md entry (2026-07-15). Reproduced test-first (validator rejects a lineage token under the old strict check, green after the widen).

**Problem:** `AppStoreReceiptValidator` pinned `appAccountToken == caller`. A StoreKit pack bought under a prior identity (AUTH-19 upgrade mints a new user id on the same device) carries the old id forever, so it was rejected as `apple_account_mismatch` → 400 `receipt_rejected` → stranded uncredited. The owner saw "only the medium pack works" because medium was re-bought fresh under the current id.
**Approach:** widened the accepted-account set from `{caller}` to the caller's install lineage — every user id sharing the caller's `install_id`, resolved server-side by a new `ProfileRepository.findInstallLineage(userId)` and carried on `PurchaseReceipt.accountLineage`. The validator accepts a token in `accountLineage + userId`. Chose server-derived lineage (from the caller's own profile row) over trusting the `X-Install-Id` header so a client can't inject a lineage it isn't part of, and over re-stamping the token on upgrade (StoreKit transactions are immutable — can't fix already-stranded packs, which is the whole population). `install_id` is the only anchor available: these upgrades create distinct user ids, and it's the same anchor the L1 orphan sweep already trusts. Empty lineage falls back to the strict binding, so nothing loosens by default.
**Reviewer notes:** Trust surface — an attacker who set their own `X-Install-Id` to a victim's install at `/v1/me` could join the lineage and redeem a victim's un-redeemed receipt. Narrow today (beta/sandbox only, grants to the attacker not the victim, idempotent per transaction id) and it's the same header-trust the orphan sweep already accepts, but it needs a real answer before real-money go-live (device-attested install id, or binding the lineage at upgrade time server-side). Flagged in the decisions entry too. Also: the `PostgresProfileRepositoryTest` lineage cases are Testcontainers — they compile locally but only run in CI (Docker wasn't available on this worker); the validator + route tests are pure-JVM and ran green here. Left the Google (`obfuscatedExternalAccountId`) path untouched — the field is available to it now but BILL-11 is Apple-only.
