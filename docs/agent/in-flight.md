## feat(catalog): pair REACH_LEVEL_25 with Felt Veteran title

**Problem:** The level-milestone capstone `REACH_LEVEL_25` ("Felt veteran" EPIC) was the only EPIC achievement without a cosmetic complement — every other EPIC in the registry already grants a title / emote pack / card back at unlock time, so the level-25 reveal felt thin.
**Approach:** Add an `unlock_only` `title_felt_veteran` product (server migration V35), wire `cosmeticRewardFor(REACH_LEVEL_25) → CosmeticReward("title_felt_veteran", "Felt Veteran title")` on the client mirror, `"REACH_LEVEL_25" → "title_felt_veteran"` in `ClientGrantableAchievements.Default`, and the display label in `titleForProductId`. The todo's recommendation floated "a card back rather than an emote pack" — I picked a title instead because the achievement name *is* "Felt veteran" and a title is one line in `titleForProductId` versus a new `CardBackStyle` enum value + `paletteFor` branch + `PlayingCardBack` renderer branch + draw layer for the card back path. Other level milestones (`REACH_LEVEL_5`, `REACH_LEVEL_10`) stay XP-only on purpose so the V35 capstone isn't diluted by a chain-of-three.
**Reviewer notes:** Departed from the todo's "card back" recommendation in favor of a title — flag if you'd rather I revert and ship the card back path; not married to the direction. Rewrote the §A catalog-gating bullet in `docs/todo.md` to reflect the V35 pairing + my reasoning so the next worker has the context.

## feat(shop): jump to just-unlocked item from redeem snackbar

**Problem:** After a cosmetic redeem the "Unlocked! X is yours." snackbar fires and the user has to navigate Profile → My Items themselves to actually equip the thing.
**Approach:** Add an action button on the `RedeemSucceeded` snackbar that calls `router.navigate(MyItemsRoute(highlightProductId = …))`. `MyItemsRoute` now carries an optional `highlightProductId`; `MyItemsScreen` reads it, scrolls the matching row into view, and pulses an accent border on the row for ~1.8s. Action label switches between "Equip" (for `Product.ChipOffer.isEquippable = true`) and "View" (avatar / emote packs that don't have an equip toggle — the row still surfaces the "Unlocked" badge). Chose this over a generic "View" for every case so the CTA copy reads honestly per the todo's "no equip target" caveat for non-equippables.
**Reviewer notes:** Per todo, AlreadyOwned + chips-added snackbars stay action-less even though the AlreadyOwned case arguably benefits from a "View" jump too — happy to extend if you want it. Highlight pulse + scroll-to is screen-side only (no VM state), so existing `MyItemsViewModelTest` cases pass unchanged; the new behavior would need a Compose UI test harness to assert on, which doesn't exist in this module yet. The DS chose accentPrimary border at alpha 0→1→0 over a background flash to avoid clipping the row's existing surface treatment.

## refactor(ds): swap raw 22.dp literals for D850/R850 in shop + cheat sheet

**Problem:** `ShopScreen.HeroProductIcon` hand-tuned `RoundedCornerShape(22.dp)` × 2 + a `padding(22.dp, 22.dp)` literal pair, and `HandRankingsCheatSheet` repeated the same `padding(22.dp, 22.dp)` shape on `CurrentHandCard` plus a `width = 22.dp` step-indicator literal. `Dimension.D850` already maps to 22.dp in the ladder so the padding literals were drift, and the corner-shape literal had no matching `Radii` token to point at — exactly the case AGENTS.md #6 calls out ("if you reach for `RoundedCornerShape(12.dp)`… add the missing token").
**Approach:** Add `Radii.R850 = Radius(CornerSize(DimensionResource.D850.dp))` to the Radii ladder so 22.dp corner radii have a token-shaped home (matches the existing D850 → 22.dp dimension naming). Then sweep the two feature callsites: `ShopScreen.HeroProductIcon` clip + border now use `Radii.R850.shape`; `FeaturedPackHero`'s padding and the cheat sheet's `CurrentHandCard` padding both lift to `Dimension.D850`; cheat sheet's StreetProgress active-step width also lifts to `Dimension.D850`. Dropped the now-unused `RoundedCornerShape` import from ShopScreen. Did not touch the four `:libraries:ui` internals (FeatureCard / BlindMarker / PermanentBadgeMarker / ChipCoin) that also use literal 22.dp — those are DS-internal callsites and a broader sweep belongs in its own commit if we want it.
**Reviewer notes:** No visual change — every literal lined up exactly with the existing D850 = 22.dp dimension or the new R850 = D850 token. `Radii.R850` slots between R800 and R900 in the ladder; the naming follows the existing irregular ladder (D850 / D750 / D950 etc. are already non-round-100 dimensions, so R850 matches that precedent). Open if you'd rather collapse `R850` into `Radii.Card` or one of the existing tokens — willing to revert if the position is "don't extend the ladder, snap to nearest" — but the AGENTS.md rule reads in the opposite direction so I went with extension.

## feat(catalog): pair BEAT_*_10 with five signature emote packs

**Problem:** The five `BEAT_*_10` per-bot achievements (Jane / David / Gina / Steve / Mike, RARE, bot-mode) carried XP-only — they were the largest unpaired achievement cluster left in the registry, and the V34 commit footer explicitly flagged them as deferred behind a "needs five new packs shipped together to avoid an inconsistent half-rollout" gate.
**Approach:** Ship all five in one commit (V36 inspector → V37 showstopper → V38 outsmarter → V39 marathoner → V40 tamer, ordered to match the registry's bot enumeration). Each pack is themed from the winner's vantage rather than the bot's — "out-analyzed the gatekeeper" / "out-showed the showman" / "outsmarted the trickster" / "out-waited the patient one" / "tamed the chaos" — so a player owning all five reads them as a coherent set of mastery flexes rather than five bot-knockoff packs. Pack icons paired narratively with each bot's medallion (🔍 vs 🧐, 🎤 vs 😎, 💡 vs 🦊, 🦥 vs 🐢, 🦁 vs 🤡) — same conceptual family, distinct glyphs so the unlock callout doesn't show one ambiguous icon. Each migration carries the same client-wiring trio as the prior eight emote-pack rows: `EmojiPackCatalog.PackEmojis`, `cosmeticRewardFor(...)`, `ClientGrantableAchievements.Default.clientGrantable`. Glyph collisions were checked against all 12 prior packs, all 5 sibling new packs, and every active achievement medallion icon in the registry (🧠 was the natural first pick for the outsmarter pack but is a registered medallion — swapped to 💡 in the same conceptual slot). I picked the five thematic names + glyph sets myself; the todo's only direction was "per-bot signature packs" so this is a directional call worth flagging.
**Reviewer notes:** The five pack names + emoji sets are my pick — happy to swap any of them if a name reads off. The strongest cases for revision are probably "Marathoner" (could also be "Endurer" / "Stoic") and "Tamer" (could also be "Ringmaster" / "Composer"). Glyphs are easier to swap one-at-a-time than pack names. Test coverage: `EarnableCosmeticsTest`, `EmojiPackCatalogTest`, and `GrantsRoutesTest` all pin every pack individually so a rename or remap on the server vs the client mirror trips loudly. Pack icon `🤓` (inspector slot 3) sometimes renders as "nerd face" on older system fonts — checked against the existing 12 packs and none reuse it, but it's the one glyph in the new five with the most font-rendering variance; willing to swap to ⚖️ (scales) or 🔬 (microscope) if the slightly inconsistent render is a concern. The 5-pack ship-together constraint resolves with this commit, so the §A catalog-gating bullet was rewritten to reflect the new 13-pack baseline; nothing on the todo blocks on this anymore.

## feat(profile): combine claim screen with email/password form

**Problem:** The Claim-Account screen showed three CTAs (Google / Apple / Continue with email) and the email tap routed to a second screen (`SignUpRoute`) that asked for email + password — one screen too many for the locked-design "single combined sign-up" shape.
**Approach:** Collapsed both into the existing `ClaimAccountScreen`: email + password + confirm-password fields at the top, big primary "Create account" submit, "or" divider, then the gated OAuth buttons (Google / Apple `Outlined` style so the form's primary submit reads as the dominant action). The `ClaimAccountViewModel` now owns the full email path — local validation (≥6 chars, match), the constructive `awaitingClaimConfirm` dialog (same dialog SignUp has, same `auth_sign_up_claim_dialog_*` strings reused), then `linkEmailIdentity` with the same `NotAnonymous → signUpWithEmail` fallback the SignUp VM does (covers the rare case of the session rolling over mid-flow). New `ClaimAccountEvent.NavigateToVerifyEmail(email)` event maps to `router.navigate(VerifyEmailRoute(email))` at the `ProfileFeatureEntryPoint` seam — same Verify Email screen the onboarding flow uses for fresh signups, so a guest who claims by email walks the same verification path as a fresh user. OAuth path is untouched per the todo's out-of-scope (link / conflict / switch-to-existing still go through the same `linkOAuthIdentity` / `signInWithOAuth` calls). The `SignUpRoute` still exists for the OnboardingFlow's "Create account" CTA off SignInScreen — only the claim entry point stopped routing through it. Reused existing string keys (`auth_field_email_label`, `auth_field_password_label`, `auth_sign_up_confirm_password_label`, `auth_sign_up_password_helper`, `auth_sign_up_password_mismatch_helper`, `auth_sign_in_oauth_divider`, `auth_sign_up_submit_button{_progress}`, `auth_sign_up_claim_dialog_*`) — the strings are conceptually identical across the two surfaces, sharing the key keeps a future voice-pass from having to fix two places. Removed two dead string entries (`profile_claim_provider_email`, `profile_claim_coming_soon`) that the new layout doesn't need — the email form is the always-available path, no "coming soon" copy needed when OAuth isn't enabled. Kept the confirm-password field even though the spec hinted at "same shape as most modern sign-up flows" (many of which drop confirm) — for a claim flow where a typo permanently binds guest chips/XP to the wrong email, the friction is worth it; same reasoning as the existing SignUp screen's confirm field.
**Reviewer notes:** I picked `ButtonStyle.Outlined` on the OAuth buttons (vs `Filled` previously) so the email "Create account" submit reads as primary — happy to flip back if you want OAuth visually co-equal. Kept the confirm-password field; willing to drop it if you want the modern-shape single-password flow per the spec hint, but I'd want a more visible password-reveal toggle if we do (currently the field is always masked). Reused `auth_sign_up_claim_dialog_*` keys across both surfaces; if the voice for the guest-claim dialog should differ between fresh-signup and from-Profile-Claim, the keys would need to split. `ClaimAccountViewModelTest` extended with 9 new email-path cases (below-min, mismatch, confirm-dialog gating, dismiss, success → NavigateToVerifyEmail event, EmailAlreadyRegistered, WeakPassword, InvalidEmail, NotAnonymous → fallback to signUpWithEmail, NetworkError) plus the FakeAuthRepository grew `linkEmailIdentity` + `signUpWithEmail` stubs (previously `error()`-stubbed since the prior VM didn't touch them). Inline VM error strings stay raw `String` for now — the in-flight note on the §A strings sweep flags the broader `OnboardingViewModel`/`SignUpViewModel`/`ClaimAccountViewModel` VM-error-string lift as needing typed `ErrorReason` or a `suspend` resolve before they can migrate, so the new error strings I added follow the same raw-String shape as the prior ones in this file.
