# In-flight log

## feat(sync): level-based runWhen sync triggers (ENG-20)

**Problem:** The sync coordinator was edge-triggered off the event bus's single replay slot — a fast launch could evict the sign-in event before the coordinator subscribed and never sync (the 07-09 vanishing-chips trigger half); reconnects never re-synced and auth-blocked syncs never retried.
**Approach:** Implemented `docs/plans/eng-20-runwhen-triggers.md` phases 1+2 as written: generic `runWhen(key, refireOn, retry)` in `:libraries:flowroutines`, `SyncTriggers` (activeAccount level + warm-fg/came-online edges), coordinator rewritten as one `runWhen` per syncer, PlayStyle contributed as a `UserScopedSyncer` (opponent-cache clear stays a listener), InAppMessage moved to its own no-retry `runWhen` pass (plan left syncer-vs-own-loop as my call: own loop, because its pass surfaces a dialog and must not ride the coordinator's retry/backoff), `AccountClaimed` deleted end to end.
**Reviewer notes:** One deviation forced by a test failure the plan predicted for connectivity but not foreground: the bus replays its last event, so a `runWhen` refire subscription picked up a *stale* pre-subscribe warm-foreground and double-fired at activation. Fix: added `AppEventBus.liveEventStream()` (replay-free sibling) and `AppEvents.live()`; `SyncTriggers.warmForeground` reads it. Also `SyncTriggers` takes `() -> AuthRepository` / `() -> AppEvents` providers to break a real KSP-detected DI cycle (dispatcher → listeners → InAppMessageManager → SyncTriggers → dispatcher). Behavior deltas stated in the plan apply: syncers refire on reconnect, failed syncs retry with backoff (5s ×2 → 2m cap, 5 retries), triggers coalesce, in-flight syncs cancel on sign-out/switch, and an *unauthenticated* boot no longer runs the in-app-message cached-dialog pass (messages are user-scoped; pre-auth there is nobody to address — old behavior surfaced cached dialogs even session-less).
**Deferred:**
- Phase 3 (bus replay 1→0, delete `ConnectivityEdgeDispatcher`/`ConnectivityRegained`, migrate identity's condition-shaped listeners) → appended to `docs/backlog.md`.
- Pre-existing user-switch clear window (old user's in-flight sync vs `clearFor`) → filed as ENG-21 in `docs/todo.md`. **Source:** worker-added this cycle from the plan's filed follow-ups, not human-curated.

## feat(billing): record StoreKit environment; segment sandbox mints (BILL-6)

**Problem:** TestFlight purchases always verify against Apple's sandbox (free chips), but were recorded identically to real money — the owner's two test buys minted 125,000 unpaid chips reading as revenue, and `iap.%` real-money gates (orphan-sweep protection) treated testers as paying customers.
**Approach:** `billing_transactions.environment` ('sandbox'|'production', V83) written from the receipt validator's verdict: Apple reads the decoded JWS payload's environment and verifies primary-then-sibling-environment (so flipping prod's `APPLE_STORE_ENVIRONMENT` to Production at launch keeps accepting TestFlight sandbox receipts — the "ideally" from the todo hint, shipped); Google counts `purchaseType = 0` (license testers) as sandbox; Dev validator is always sandbox. Wallet ledger reason splits: `iap.<product>` = real money only, `iap_sandbox.<product>` = test mints — chosen over a wallet_events environment column because every existing `iap.%` gate (hasIapSpend, install-sibling sweep) then gets the correct "testers aren't payers" semantics for free. V83 backfills all existing rows/reasons as sandbox (TestFlight-only distribution to date, both Fly apps on Sandbox). Updated the `cards-economy` Grafana dashboard: revenue stats (`Real purchases` / `Unique paying buyers` / `Chips sold (real IAP)`) filter `environment='production'`, purchases-per-day labels sandbox series, new `Sandbox chips minted` stat.
**Reviewer notes:** The dashboard's new environment-filtered panels will error until this branch merges and the servers run V83 (the column doesn't exist yet in prod/dev DBs) — self-heals on deploy. The bust→purchase conversion stat deliberately still counts sandbox buys (the tap is the behavioral signal; noted in its description). Launch-day flip of `APPLE_STORE_ENVIRONMENT` to `Production` on the prod Fly app is still the owner's task, but with the sibling fallback it's now about primary-order, not correctness.
**Deferred:** ECON-1 (ledger conservation check + starter-grant ledger rows) untouched — still in `docs/todo.md`.

## fix(wallet): ledger the starter grant; add conservation check (ECON-1)

**Problem:** Lazy wallet creation set the 10,000-chip starter balance without a ledger row, so the ledger couldn't explain the money — prod: 146,000 in balances vs 126,000 in the ledger.
**Approach:** Red-first `WalletLedgerConservationTest` pinning `SUM(wallets.balance) == SUM(wallet_events.delta)` across every mutation path (starter, billing redeem incl. replay, MP buy-in/cash-out, shop debit, rejected overdraft) — failed with the exact drift, then green after `createWithStarter` writes the `starter_grant` event in the same transaction. Switched both lazy-create inserts to `insertIgnore` (a caught constraint violation still aborts the surrounding Postgres transaction — the old catch-and-continue race path was subtly broken). V84 backfills missing starter rows keyed `(user_id, 'starter_grant')`. Added a "Ledger conservation drift" stat (red at any non-zero) to `cards-economy` as the alertable query.
**Reviewer notes:** Verified against prod before shipping: drift is 20,000 = exactly 2 wallets × missing 10,000 starter row, so V84 closes conservation to 0 on deploy. Audited every `WalletsTable` mutation — billing, table sessions, and the wallet API all already journal via `applyInCurrentTransaction`; the starter grant was the only leak. Pre-existing test assertions that counted ledger rows were updated to expect the (correct) starter row.
**Deferred:** A real Grafana *alert rule* (vs the red-threshold stat) needs a notification contact-point decision — owner's call; the drift query is on the dashboard and in the test either way. Nothing filed.

## fix(chips): derive balance from server snapshot + pending outbox (PROG-11)

**Problem:** The displayed chip balance was one mutable number: optimistic writes bumped it, then sync's authoritative overwrite stomped it — a grant landing mid-sync vanished until the next sync (the 07-09 incident's display half), and server-rejected events silently shrank the balance.
**Approach:** Spec-driven per the todo: subagent investigation first, plan written into the case file, then implemented. The `chips` row is now a pure server snapshot; displayed balance = snapshot + SUM(pending outbox deltas) (`combine` of two Room flows). `addChips`/`subtractChips` enqueue only; `setBalance` overwrites the snapshot (MP settle / IAP redeem now preserve pending grants instead of stomping them). Rejections (`InsufficientChips`) emit `ChipSyncRejection`, collected at App root into an error snackbar ("A purchase didn't go through, so we put your chips back.") — same pattern as profile-edit rejections. Red-first: the mid-sync-grant test failed 10,000≠10,500 against the old code.
**Reviewer notes:** `ChipsDao.applyDelta`/`insertIfMissing` and `WalletEventDao.countByKey` are deleted (obsolete under derivation — a duplicate key physically can't double-count). No Room migration: the `balance` column keeps its name with snapshot semantics; a pre-existing install's blended value self-corrects on the first sync (pre-launch posture). `RefusedServerOwned` deliberately stays silent (server mints those rewards itself; nothing user-visible was lost). New QA device test `PROG-11` covers the original repro end to end.
**Deferred:** None.
