# In-flight

## fix(room): stop MP showdown crash on duplicate cards (MP-4)

**Problem:** An uncaught `IllegalArgumentException: Duplicate cards in hand` killed the app on `PlayMultiplayerRoute` at showdown (CARDS-2Q) when an on-device `holeCards + board` merge produced a duplicate after a `StateSnapshot` landed over stale local cards.

**Approach:** Added `HandEvaluator.evaluateOrNull(...)` — same eval, returns null instead of throwing on a malformed set (wrong count / duplicate). Routed every on-device display + progression projection through it (`ShowdownRow`, `previewHandLabel`, `HandResultSummaryBuilder` x3, `PlayStyleHandSummaryBuilder`) so a transient desync degrades to "no hand shown" rather than crashing. Left the server-authoritative `GameEngine.runShowdown` and bot `HandStrength` on strict `evaluate` (engine cards come from one deck, so a dup there is a real bug we still want surfaced). Directional call: I made the evaluator non-throwing at the on-device callsites that can see a desynced set, rather than wrapping the whole render in `Catching {}` and showing a full unrecoverable-error screen — a single bad showdown row degrading to "—" is better UX than tearing down the whole table, and it kills the crash at its source for every callsite. The reporter asked for `Catching {}`; `evaluateOrNull` is the structurally-cleaner equivalent (no throw to catch). If the reviewer wants the explicit error-state screen too, that's a follow-on.

**Reviewer notes:** Regression tests pin the exact CARDS-2Q 7-card set returning null from `evaluateOrNull`, and `HandResultSummaryBuilder` absorbing a hole/board overlap without throwing and crediting no category. I did not add a `TableUiState.UnrecoverableError` variant — see the directional call above; the crash can no longer originate from these paths, so the error-state screen is unneeded for this bug.

## feat(config): gate social surfaces behind social.enabled flag (SOC-2)

**Problem:** Friends/social is descoped to V2, but the surfaces (Home FriendsStrip + recently-played-with shelf, Profile friend-requests inbox, at-table "Add friend") still rendered.

**Approach:** New `SocialEnabled` flag in `:libraries:social` mirroring the identity `GoogleSignInEnabled` precedent, default off, served from `InMemoryAppConfigSource` as `social.enabled=false`. Each surface reads the flag and skips rendering (not a disabled state) — Home gates the two strips in `HomeScreenContent` + skips the social fetches/collectors in `HomeViewModel`; Profile gates the inbox + its refresh; the room gates the player-card `onAddFriend` (passing null) via a new `PlayPokerState.socialEnabled`. The friend-request *action* plumbing stays intact (the button is hidden, the code path is dormant) so reviving in V2 is a config flip. Added `SocialEnabled.forTest(enabled)` so VM tests supply the flag without standing up an `AppConfigMap`. Directional call: I renamed the two affected VM constructor params to `socialEnabledConfig` to avoid a same-name clash with the `socialEnabled` state field at the construction site (Kotlin mis-resolved the `invoke()` otherwise); the alternative (qualifying every call) read worse.

**Reviewer notes:** Added `:libraries:config` as an `implementation` dep to home/impl + room/impl (main + test) — required so the `ConfiguredValue.invoke()` operator resolves at the call site, matching how onboarding/impl depends on both config + identity. `social.enabled` only lives in the dev `InMemoryAppConfigSource`; the production `PostgresAppConfigSource` omits it, which correctly falls back to the client default (off) — flip it on there in V2. New QA test `SOC-1` covers the hidden-by-default surfaces.

## fix(rooms): make room leave idempotent — 204 not 409/404 (MP-5)

**Problem:** `DELETE /v1/rooms/{code}/me` 409-looped for ~90s while a room settled after an opponent crashed (CARDS-2R) and 404'd on a re-issued leave once the membership was already gone (CARDS-34) — both surfaced as a dead back button.

**Approach:** Collapsed the leave route's HTTP projection so `LeaveResult.Success`, `RoomNotFound`, and `NotInRoom` all return 204 — the caller's goal of not being in the room is satisfied in every case. The service still returns the three distinct results (the in-memory store test on `NotInRoom` is unchanged); only the wire status changes. Directional call: fixed the contract server-side rather than patching only the client. The client already maps 404/409 to a success-equivalent and the lobby already treats them as `resetToIdle(error = null)`, so a client-only fix would leave the server emitting misleading `not_in_room` / `room_not_found` envelopes that any other consumer would have to special-case. The honest fix is the idempotent endpoint. Rejected a server-side pending-leave queue as over-built for an end-state no caller distinguishes.

**Reviewer notes:** Public API contract change, but a strict relaxation (more requests now succeed) and idempotent, so safe per the worker-prompt's "hard to undo" carve-out. Client `RoomRepositoryImpl.leaveRoom` keeps its 404→NotFound / 409→NotInRoom branches as defensive cover for an older server; they're now dead against this build but harmless. Decisions-log entry added (2026-06-24). No QA.md entry — backend-only, no user-facing string/UI; MP-3 (the pending MP QA section) is where the device-runnable leave scenario belongs. The two server cases the 409-loop produced (`memberFor` transiently null mid-settlement) aren't reproduced as a unit test here — the fix is at the projection layer and is correct regardless of *why* the service reports `NotInRoom`.

## fix(room): split practice-tier dialog body on subsidized chips (GAME-4)

**Problem:** The practice-tier explainer led with "the hand counts as practice" on every bot-stacked table, which contradicts the subsidized bots-for-chips line right below it ("beat them and you keep the chips you win") — one dialog read both no-stakes and real-chips at once (CARDS-2K).

**Approach:** The dialog already branched its *second* (bots-only) line on `subsidized`; the gap was the main body. Added `room_practice_tier_explainer_subsidized_body` and branch the body `Text` on the existing `subsidized` flag (the `forRealChips`/disclosed-bot signal already plumbed as `subsidizedBotTable` → `subsidized`). The subsidized variant keeps the true facts (XP halved, MP achievements locked, get-more-humans-for-full-credit) but drops the "counts as practice" framing and states the chips are real. Pure-practice tables keep the original body unchanged. Directional call: reframed the existing body rather than minting a whole second dialog — the half-XP / locked-achievements facts are identical on both table types, only the stakes framing differs, so a one-line resource branch is the smallest honest fix and matches how `StackExplainer` / the bust dialog already branch on `subsidized`.

**Reviewer notes:** Copy-only change behind a flag already in `PlayPokerState`. No new test — there's no VM logic, and the four `@Preview`s now cover all four (botsOnly × subsidized) combinations. No QA.md entry yet: there's no MP/room QA section (that's MP-3); the device-runnable "subsidized bots-for-chips dialog says chips are real" check belongs there when MP-3 lands.
