## fix(room): keep deal/reveal animations in real-chip games (GAME-8)

**Problem:** The unified global "Game speed" setting (`GameSpeed.animationScale`) paces solo practice, but it also drove a real bots-for-chips public game to Instant — a tester lost the card flips in a real game and intuited the speed should be practice-only.
**Approach:** Scoped the animation pacing, not the setting. Added `PlayPokerState.effectiveTableSpeed` (and a `realChipsAtStake` helper) that forces `GameSpeed.Normal` whenever real chips are on the line — a human MP game (`isRealMultiplayer`) *or* the public subsidized disclosed-bot table (`subsidizedBotTable`). `PlayPokerScreen` provides `TableTempo(state.effectiveTableSpeed)` instead of the raw `gameSpeed`. The setting still tunes solo + private practice-bot tables. Chose this over making the whole setting practice-only (would silently ignore a user's explicit Instant in practice MP, which is fine to honour) and over a per-animation minimum floor (more surface area, same outcome).
**Reviewer notes:** The reporter's room was a public bots-for-chips table, which is `practiceTierBotsOnly == true` — so `isRealMultiplayer` alone would NOT have covered it; `realChipsAtStake` adds the `subsidizedBotTable` arm specifically for that case. Bot think-time scaling (`botThinkScale`) is untouched and irrelevant here — these tables are server-driven. Test is `EffectiveTableSpeedTest` (4 cases: solo honours, human-MP forces Normal, subsidized-bot forces Normal, private-practice-bot honours).
**Deferred:** None.

## fix(lobby): validate join code in place, no flicker on a bad code (ROOM-5)

**Problem:** Typing a wrong room code on the PrivateJoin screen "looked like a navigation event" — the screen pushed the seated Lobby, the Lobby 404'd, then bounced back to PrivateJoin with the error. Two route batches for a typo.
**Approach:** Validated the code on the input screen instead of funneling through the Lobby first. New `PrivateJoinViewModel` attempts the join in place; a bad code (or full / not-joinable / over-balance / network) shows an inline error with zero navigation, and only a confirmed-good code navigates on to the seated Lobby (which re-attaches idempotently via the prefilled code — the server returns `alreadyJoined`). Made `PrivateJoinScreen` stateless (state + onAction) per the screen-content convention. Chose the in-place-validate-then-navigate shape over threading the joined `Room` object through navigation (heavy, non-serializable) — the one idempotent re-join on the success path is the documented `alreadyJoined` contract.
**Reviewer notes:** The Lobby's own `JoinCodeRejected` → bounce path is intentionally KEPT — it still serves the deep-link case (`cards://join/{code}` with a dead code, where there's no input screen behind it). For that bounce, `PrivateJoinViewModel` seeds the field + inline error from the assisted `rejectedCode` WITHOUT re-joining (the lobby already 404'd). Tests: `PrivateJoinViewModelTest` (bad code → inline error + no nav event + one join call; success → NavigateToLobby; deep-link seed → no re-join; uppercase/cap). All `:apps:integration` presence tests still green (they drive `LobbyViewModel` with `prefilledCode` directly, an unchanged path).

## feat(billing): Android PlayBillingClient + consumable consume() (BILL-3)

**Problem:** `libraries/billing/impl/src/androidMain` was empty, so Android release builds fell back to `NoOpBillingClient` and had no real IAP; chip packs are consumables but the interface only exposed `acknowledge`, which can't re-enable a re-purchase.
**Approach:** Added `BillingClient.consume(purchaseToken)` to the shared interface (Play `consumeAsync` / StoreKit `transaction.finish`) and routed `DefaultPurchaseChipPackUseCase` through it on both credit paths, since every chip pack is a consumable. Implemented Android billing in two classes: `RealPlayBillingClient` drives Play Billing v7 (connect/queryProductDetails/launchBillingFlow bridged from the `PurchasesUpdatedListener` via a `CompletableDeferred`, serialized by a Mutex; `setObfuscatedAccountId(userId)`; consume + acknowledge as KTX suspend extensions), and `PlayBillingClient` is the DI binding that picks Fake-in-debug / real-in-release exactly like `DevBillingClient` did — so dev shop iteration is unchanged and release gets live IAP.
**Reviewer notes:** Binding selection is build-type, not the BILL-5 flag: DI can't read a runtime flag, and keeping the Fake delegate in debug preserves the dev redemption flow (matches the existing `DevBillingClient` shape). `PlayBillingClient` declares `replaces = [DevBillingClient::class, NoOpBillingClient::class]` — replacing only Dev left `NoOpBillingClient` still bound and KSP failed with a duplicate `BillingClient` provider; the transitive replace isn't carried, so both must be named. `RealPlayBillingClient` is untested by unit tests (Play SDK needs a device / license testers — developer-gated); `DefaultPurchaseChipPackUseCaseTest` + `BillingAvailabilityImplTest` updated to assert the consume() routing and were the green guard. Verified `:apps:compose:assembleDebug`, billing iOS Kotlin compile, and billing impl unit tests.
**Deferred:** BILL-4 (iOS StoreKit client) sliced — `consume()` prerequisite shipped here; the StoreKit-2-is-Swift-only architecture call is now spelled out in the BILL-4 todo (inject a Swift impl via `IosAppComponent` like `AppleSignInCoordinator`, not a K/N binding). Left for a cycle that can build + verify Swift against an Xcode `.storekit` config.

## fix(lobby): joiner buy-in never regresses to $0 on a presence snapshot (MP-24)

**Problem:** A joiner who entered a real-buy-in room via PrivateJoin saw the lobby buy-in render as $0 on a post-#74 build. The HTTP join response carried the real stakes (server debited them), but the first socket lobby presence snapshot — which carries the converged member list with `buyIn = 0` — clobbered them via `LobbyViewModel.ConnectionUpdated`'s unconditional `room = conn.room`.
**Approach:** Added `Room.mergeStakesFrom(previous)` — a field-level counterpart to `preferRealOver` — and applied it in the VM's `Connected` branch (`conn.room.mergeStakesFrom(it.room)`). When the incoming snapshot is a placeholder (`buyIn <= 0`) but we already hold a real room, it keeps the new snapshot's members/status/presence and only carries forward the real `buyIn`/`smallBlind`/`bigBlind`. Chose the merge over the reverted `preferRealOver` approach (commit 8df4dbbf) because the latter drops the whole presence snapshot — including the converged member list — which is exactly what broke 11 `:apps:integration` presence tests; merging preserves member-list convergence. Chose the VM seam over seeding the socket's `lastRealRoom` from the repo because both the staged HTTP-join room and the incoming snapshot already meet in the VM, with no cross-module state handoff or socket→repo dependency.
**Reviewer notes:** Test-first: `LobbyViewModelTest.join_realBuyIn_thenPlaceholderPresenceSnapshot_keepsRealBuyIn` is red without the VM change (buy-in regresses to 0) and green with it; verified `:apps:integration:testDebugUnitTest` stays green (the regression the prior attempt caused). The socket-side MP-16 guard (`preferRealOver(lastRealRoom)` in `ReconnectingRoomSocket`) is untouched and still correct for the host rebound case; this is the missing joiner-side arm where `lastRealRoom` starts null so the socket guard can't help. Diagnosis matches the feedback case (room AS4UPA, session 016a8a61) exactly.
**Deferred:** None.
