## fix(telemetry): app.launched waits for the settled session_id (ENG-24)

**Problem:** `app.launched` fired from `GrafanaAppEvents`' DI init, before the first foreground rolls session #1 — every cold start's launch event carried the session tracker's pre-boot sentinel uuid, an orphan one-event session per boot in session-keyed funnels.
**Approach:** Kept the event's name + attributes intact (the observability suite's crash-free queries key on `app.launched`/`previous_exit`, so demoting it — the acceptance's other option — would silently break dashboards) and moved emission to the cold-boot foreground: a new `AppLaunchedEmitter` `AppEventListener` fires it when `isColdBoot`, which the dispatcher guarantees runs after the session tracker's ColdBoot handler. It's a separate class from `GrafanaAppEvents` because joining the listener set from a class that transitively depends on the dispatcher (config values → config repository → AppEvents) is a DI cycle — KSP caught exactly that on the first attempt. `docs/wiki/app-events.md` updated.
**Reviewer notes:** Two small semantic shifts: (1) `app.launched` now also fires in builds without Grafana credentials (it reaches logcat/Sentry breadcrumbs; previously it was skipped entirely when unconfigured) — harmless and arguably more honest; (2) a boot the user kills before first foreground no longer logs `app.launched` — consistent with "sessions start at foreground".
**Deferred:** None.

## fix(networking): quiet room sockets no longer die at 15s (MP-32)

**Problem:** Every quiet MP room socket dropped at almost exactly 15s and reconnected in ~450ms, strobing the "lost connection" banner through MP games (CARDS-9A).
**Approach:** The triage theory (server pings disabled) was wrong — the server has had `pingPeriod=15s` since the socket shipped. Actual cause, proven red-first in a new `:apps:integration` test: the debug-only Wiretap WS inspector wraps the raw OkHttp session in a plain `WebSocketSession`, which defeats Ktor's "engine session is already a `DefaultWebSocketSession`" fast path, so Ktor starts its own plugin-level pinger (`pingIntervalMillis=15s` in `NetworkClientImpl`) — and OkHttp's write loop throws `UnsupportedFrameTypeException` on the first outgoing `Frame.Ping`, killing the socket at exactly 15s. Fix: keepalive is now per-engine via a new `installWebSocketKeepalive` expect/actual — Android uses OkHttp's native `pingInterval` (works below any wrapper, and release builds gain real client-side keepalive they never had), iOS keeps the plugin-level pinger (Darwin maps `Frame.Ping` to `NSURLSessionWebSocketTask.sendPing`). Alternative rejected: dropping the client pings entirely and leaning on server pings alone — loses client-side dead-peer detection.
**Reviewer notes:** This means release/TestFlight builds were never affected (wiretap is stripped there) — the bug was dev/debug builds only, contrary to the todo's "affects every quiet MP table on both platforms". The regression test (`SocketKeepaliveTest`) deliberately runs ~19s of real wall-clock (the failure is a real-time ping-scheduler race; unreachable under virtual time) and mimics wiretap with a pass-through raw-session wrapper because the real plugin's DI can't bootstrap under host-JVM JUnit.
**Deferred:** Banner debounce (only show "lost connection" after a few hundred ms of downtime) — not needed once the keepalive is honest; noted here in case the reviewer disagrees. Nothing filed.

## fix(auth): never mint over a stranded account + mirror anonymous sessions (AUTH-19)

**Problem:** A TestFlight upgrade wiped the Keychain-stored Supabase session while the app's files survived; `GuestSessionHealer` silently minted a fresh guest over the cached account, stranding the owner's balance/XP, and his Apple-sign-in recovery attempt minted a third account (CARDS-9D).
**Approach:** Three layered fixes, each red-first. (1) The healer never mints when a cached server-backed profile exists — it calls a new `AuthRepository.markSessionUnrecoverable`, which runs the session-rejection teardown and routes to the existing SessionExpired recovery screen (retry / explicit sign-in / start-fresh). (2) `Reason.SessionExpired` is now sticky across re-resolves — before, one `retry()` decayed it to `None`, which re-armed the silent mint one foreground later (this was a live hole for server-rejected sessions too, not just AUTH-19). (3) `SecureSessionManager` mirrors **anonymous sessions only** to a file-backed `SessionMirrorStore` (survives upgrades like the rest of the app's files did) and restores from it when the OS store comes up empty; a claim clears the mirror, keeping claimed accounts Keychain-only. Alternative rejected: mirroring all sessions (weakens AUTH-16 for accounts that have a real recovery path). Decisions entry + QA `ONB-18` added.
**Reviewer notes:** The exact Keychain-loss mechanism on the owner's device is unproven (bundle id/keys were unchanged between builds; write statuses were silently ignored, so nothing was logged) — the iOS storage now logs every non-success SecItem status into the session log, so a recurrence will pin it. The healer's `MINT_FROM_PENDING`/`MINT_FRESH` log actions collapsed to `MINT`; the seeded-identity path died because seeding a new guest from a cached profile's name is exactly the silent-stranding behavior. `StrandedIdentityDetector` now stays quiet when the reason is a declared-dead session (user is on the recovery screen — not a heal failure).
**Deferred:** The stranded accounts themselves (087ac8d1… holds the owner's progression; 52f3f9c1/6f0a900c are the orphans) need a server-side admin merge — human-only, reviewer please surface in the PR heads-up. Longer-term account-linking nudge for beta testers stays in backlog.

## fix(progression): server-minted rewards trigger a wallet re-pull (PROG-12)

**Problem:** Chips earned in an MP session (the tester's 1000 = the level-3 reward) stayed stale until force-kill, on a build that already had PROG-11's derived balance (CARDS-98).
**Approach:** Root cause is ENG-9's server-side minting: level/achievement chips are credited on the progression/achievements sync endpoints, but the wallet sync — which fires on the same trigger edge, usually earlier — never learns about them until the *next* edge. Fix: the minting endpoints now return `walletBalance` (only when the request actually minted; replays signal nothing), and the client responds to non-null by issuing a fresh `ChipsRepository.sync()`. Red-first on both client repos (progression + achievements). Alternative rejected loudly: applying the returned balance directly via `setBalance` — a concurrent wallet sync whose server-side read predates the mint can arrive later and stomp it; a pull issued after the mint is ordering-safe (decisions entry has the full trade, including the deferred versioned-snapshot design).
**Reviewer notes:** The case's exact grant path is inferred (1000 chips = `LEVEL_CHIPS[3]`, and the reporter's XP crossed level 3 in that session's window) — the MP leave-settle path (MP-29) was already synchronous and shows no hole. If a second staleness report arrives with a different shape, the deferred wallet-revision design in the decisions entry is the follow-up. QA PROG-11 gained a no-restart freshness sub-bullet.
**Deferred:** Versioned wallet snapshot (`revision` column + monotonic `setBalance`) as the fully general fix for balance-writer races — documented in the decisions entry, nothing filed (reviewer please triage whether it deserves a backlog line).

## feat(telemetry): offline events survive to next launch + is_offline (ENG-25)

**Problem:** The client OTel pipe was at-most-once: a failed export batch was dropped on the floor, so everything emitted offline — including the reliability events that exist precisely to capture offline moments — was lost for good (verified in the 2026-07-11 drill). Records also carried no connectivity context.
**Approach:** Adopted the library's `exporters-persistence` disk buffer through the existing `processorFactory` seam: the chain is now batch → disk → OTLP (`durableLogRecordProcessor` in `DurableLogExport.kt`), where a batch is deleted only after Grafana acknowledges it and leftovers ship on a later launch; buffer lives under `FileManager`'s app-files dir (`telemetry/`), bounded by the library at 100 gzipped batches / 30 days. Added a background-flush hook (`TelemetryBackgroundFlusher`, an `AppEventListener`) so the RAM batch reaches disk + an export attempt in the grace period after backgrounding — without it the tail of every session (`app.backgrounded` itself) rode only in memory; it holds the tree via a settable reference because a listener whose deps reach the config system recreates the ENG-24 DI cycle. `is_offline` (from `AppState.isOffline`) now rides on every record, captured at emit time so buffered records describe the moment the event happened. Alternative rejected: hand-rolling our own spill-to-disk queue — the library module is small, matches our exact processor seam, and its file I/O is exception-contained; our own would be more code to distrust. The exporter keeps `FailSafeLogRecordExporter` + `Catching` end to end (the upstream crash history is why), now enforced inside `durableLogRecordProcessor` so no caller can compose the chain without it.
**Reviewer notes:** New durability test runs the real SDK + real file system across two simulated launches (~100ms wall clock, real-time flush cadence passed in as 50ms — same virtual-time-unreachable reasoning as MP-32's socket test). Cross-launch record identity goes through the library's protobuf round-trip; the test asserts attributes (`hand_number`, `session_id`, emit-time `is_offline=true`) survive it. The buffer sits in files-dir (not platform cache dir) deliberately — an OS cache purge would silently delete the exact records we promised to keep; noted in the docs pass.
**Deferred:** Warn+ forwarded logs now also gain durability by construction (same pipe). No follow-ups filed. (The MetricKit `previous_exit` slice landed in the follow-up commit below, closing ENG-25 entirely.)

## feat(telemetry): real iOS previous_exit from MetricKit (ENG-25)

**Problem:** `app.launched`'s `previous_exit` was real on Android but hardcoded `unknown` on iOS — iOS crash/ANR/OOM rates were invisible in the launch funnel.
**Approach:** A Kotlin/Native MetricKit subscriber inside `IosPreviousExitProvider` (`platform.MetricKit` interop): each `MXAppExitMetric` payload's foreground exit counts classify to the most severe reason (crash > anr > oom > clean), persist to `NSUserDefaults`, and the next cold start reports the value exactly once before clearing (`LatestExitReport`, common code, unit-tested). Consume-once is the load-bearing call — re-reporting a day window on every launch would multiply one crash by the user's launch frequency. Deliberate divergence from the todo's hint: implemented in Kotlin iosMain rather than Swift-through-`IosAppComponentFactory` — same ObjC runtime conformance, but it keeps the whole feature in `:libraries:telemetry:impl`, needs no Xcode-side change, and is verifiable by the KMP toolchain in this environment (the Xcode project can't be compiled here, per BILL-7's note). Also diverged from the hint's "derive from the delta": MetricKit counts are per-24h-window aggregates, not monotonic counters, so each payload is self-contained and classified directly. Decisions entry records both calls; `docs/wiki/app-events.md` documents the day-granular semantics for dashboard readers.
**Reviewer notes:** MetricKit never delivers payloads on the simulator, so end-to-end verification needs a real device + a day of wall clock — the classification and consume-once state machine are unit-tested, the subscriber compiles for both iOS targets, but the actual payload delivery path is untested by nature. Worth a TestFlight-cycle sanity check of `previous_exit` values in Loki once this ships. Also for the record: this cycle ran concurrently with a docs-focused peer that edited `docs/todo.md` / `docs/decisions.md` / `docs/wiki/app-events.md` / this file mid-cycle; my first commit (9c4e1f46) picked up its (verified-accurate) doc edits alongside my code, and its reslice of ENG-25 into a MetricKit-only bullet is what this commit closes out.
**Deferred:** A per-run clean-exit-marker heuristic (Sentry-style watchdog detection) blended with MetricKit would give per-launch granularity — rejected as more machinery than beta needs; documented in the decisions entry, nothing filed.
