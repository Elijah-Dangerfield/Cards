# In-flight

## fix: attribute MP hand outcomes to the local seat, not seat 0

**Problem:** Folding a multiplayer hand still credited `SHOW_*` achievements ("show a straight at showdown") even though the player never reached showdown.
**Approach:** Root cause was `PlayPokerViewModel.humanSeatIndex` hard-coded to `0`. Solo always seats the human at 0, but MP allocates any seat — so every per-hand attribution (XP, achievements, win-odds equity) was computed against seat 0's outcome. A folded human at seat 1 inherited seat 0's showdown hand. Added `PokerSessionFactory.humanSeatIndex(state)` (solo: fixed seat; remote: match `localUserId`, `-1` when not seated so a missing match yields no credit instead of crediting the wrong seat) and resolved the real seat at the two attribution sites (`handleHandEnded`, win-odds equity). Also added the belt-and-suspenders `!summary.wasFold` guard on the `Criterion.ShowAtLeast` branch per the todo.
**Reviewer notes:** This also silently fixed the win-odds tool for non-seat-0 MP humans (it was reading seat 0's scrubbed/empty hole cards and giving up). The `-1`-when-not-seated contract is the safe default for spectators. Builder test simulates an over-sharing reveal map (folded human's cards present) to prove `wasFold` still suppresses credit.

## feat: orphan-anon sweep preserves accounts above level 1

**Problem:** The L1 install-id orphan sweep (`DefaultOrphanInstallSweep`) could delete a superseded anon account that had earned real XP — only inventory / live-room / IAP gates protected it.
**Approach:** Injected the server `ProgressionRepository` and added an XP guard to `verifyCandidate`: a candidate with `total_xp >= 100` (level 2+ on the client `N²×100` curve) is preserved. A missing progression row reads as 0 XP (level 1, still deletable). ## feat: route the level-up celebration to a full-screen destination

**Problem:** The level-up celebration was an overlay inside `HomeScreen` with two bugs: a full-screen `detectTapGestures` dismissed it on any tap, and the bottom nav bar stayed visible (the overlay lived inside Home's content while the app Scaffold kept drawing the bar).
**Approach:** Made it a routed destination (`LevelUpRoute` in `:features:home`, modeled on `BlockingErrorScreen`) — no bottom bar (not in `App.kt` `tabString()`), back swallowed, Continue is the only exit. Dropped the `detectTapGestures { onContinue() }` from the `LevelUpCelebration` DS component. Kept the existing derived gate (`HomeState.levelUpCelebration`); the Home entry point observes it via a remembered `ObserveWithLifecycle` flow and navigates, then fires `HomeAction.MarkLevelUpShown` (renamed from `DismissLevelUp`) **at navigate time** so the watermark advances immediately and the nav is idempotent — no re-fire when Home resumes behind the celebration. Reward rows are passed as aggregated route args (`chipsRewarded: Long`, `xpBoostRewarded: Boolean`, since `LevelReward` isn't `@Serializable`); the route screen reconstructs the display rows.
**Reviewer notes:** **Directional call — advancing the watermark at show-time, not on Continue.** This is race-free by construction (the only alternative, advance-on-Continue, reintroduces a navigate-on-resume double-push because the cache write is async and Home's composition is disposed on navigate so a `remember` dedup token doesn't survive). The accepted trade-off: a process death *while the celebration is on screen* won't re-show it (rewards are already granted; matches the welcome-dialog persist-at-emit precedent). Full rationale + rejected alternatives in `decisions.md` 2026-06-19. **Couldn't device-verify the nav transition / bottom-bar hide headless** — VM logic is unit-tested (`HomeViewModelTest`, gate→trigger→MarkLevelUpShown→watermark) and the whole client `assembleDebug`s, but the routed transition + no-bottom-bar wants a quick device eyeball. The entry-point wiring follows the existing welcome-dialog/`BlockingErrorScreen` patterns.
