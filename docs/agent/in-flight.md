# In-flight

## feat(billing): real Apple + Google receipt validators behind config (BILL-2)

**Problem:** The BILL-1 `ReceiptValidator` seam only had a `DevReceiptValidator` that trusts the token — a forged receipt would mint chips. P0 ship-blocker before any real-money sale.
**Approach:** Added `StoreReceiptValidator` (`@ContributesBinding(replaces = [DevReceiptValidator::class])`) dispatching by `Store` to `AppStoreReceiptValidator` (Apple `app-store-server-library` 5.2.0 — verifies the StoreKit 2 JWS offline against bundled Apple root CAs, then checks productId/appAccountToken/revocation) and `GooglePlayReceiptValidator` (official `androidpublisher` client + `google-auth-library` — `purchases.products.get`, checks purchaseState + obfuscatedExternalAccountId). Both read a new `BillingConfig` (mirroring `SentryConfig.fromEnv`) and stay dormant (refuse validation) until credentials are set. Wired `BillingConfig` through `ServerComponent.create`. Added `PurchaseReceipt.expectedSku` so the route hands the validator the platform store SKU (`chips_medium`) to compare against the decoded transaction — distinct from the catalog product id (`chip_pack_medium`). Fixed the now-wrong client `BillingClient` doc comment that claimed validation looks the user up via orderId.
**Approach (directional call):** User binding is enforced via the echoed-back account token (StoreKit `appAccountToken` / Play `obfuscatedExternalAccountId`) equalling the caller, NOT the order id — pinning to orderId would let one user redeem another's receipt (this is the BILL-2 hint, now also documented in decisions.md). Chose the official Apple/Google libs over hand-rolling JWS chain verification (security-critical, don't reinvent). Each validator takes an injectable decode/lookup seam (`TransactionDecoder` / `PurchaseLookup`) so the post-verification invariants are unit-tested without a live receipt — there's no mocking lib on the server and the Apple `SignedDataVerifier` / Google publisher chain can't be faked otherwise.
**Reviewer notes:** The Apple root CAs are bundled as `.cer` resources under `apps/server/src/main/resources/apple-certs/` (G3 + the two legacy roots, fetched from apple.com/certificateauthority). Online revocation/expiry checks are only enabled when `APPLE_APP_APPLE_ID` is set (needs a published app id); in sandbox we rely on the offline chain + the explicit `revocationDate` check. The `androidpublisher` rev pinned is `v3-rev20260528-2.0.0` — `obfuscatedExternalAccountId` is present in that rev. Tests: `AppStoreReceiptValidatorTest` (8 cases: dormant, valid→txnId, forged JWS, product/account/missing-token/revoked rejections, certs-bundled) and `GooglePlayReceiptValidatorTest` (6 cases: dormant, purchased→orderId, pending/canceled/wrong-account/missing-account rejections). Full `:apps:server:test` green. The forged-receipt-doesn't-grant guarantee is also covered end-to-end server-side by the pre-existing `BillingRoutesTest`. Live store exercise is developer-gated (credentials + listings) — noted in decisions.md.
**Deferred:** None.

## fix(progression): award XP + player-stats for MP hands (PROG-4)

**Problem:** A finished multiplayer hand granted zero XP and recorded no player-stat; only server-pulled achievements appeared. `RemotePokerSession` never fired the VM's `onHandEnded` callback — the only path into `awardForHand` / `recordPlayerStat` / the hand-end celebration. Solo bots worked because `LocalBotsSession` invokes it directly.
**Approach:** Wired `onHandEnded` through `RemotePokerSessionFactory.create` into `RemotePokerSession`, which now fires it on each `GameEvent.HandEnded` off the same wire the table-projection collector already sees (mirrors `LocalBotsSession`). The session captures the human's stack at each hand-start snapshot for the achievement context's start-vs-end stack, and falls back to the last non-empty snapshot if a HandEnded races ahead of its settling snapshot. Chose firing from the session (matching the solo contract) over calling `handleHandEnded` from the VM's `GameEventReceived` branch — keeps one progression path for both session types instead of splitting it.
**Reviewer notes:** The MP event flow can re-deliver a HandEnded (replay-16 SharedFlow / resync), which would have double-awarded XP and re-fired the celebration — `handleHandEnded` previously had no per-hand guard (only player-stat/play-style did). Added a `lastCreditedHand` guard at the top of `handleHandEnded`; solo never re-delivers so it's a no-op there. Tests cover both the credit firing and the double-delivery dedupe (red confirmed by stashing the session wiring).

## feat(rooms): close room as IncompatibleVersion on undeserializable frame (ENG-7)

**Problem:** Defense-in-depth beneath the cross-version rule (CARDS-4S): a game frame the client genuinely can't parse (a breaking shape change, or a client mid-flight during a rollout) had no graceful path — the frame was silently dropped, leaving the user on a frozen table / stuck "dealing in".
**Approach:** `ReconnectingRoomSocket.decode` now distinguishes a `MissingFieldException` on a known frame (a removed/renamed required field — the breaking change the additive-only convention forbids) from an unknown discriminator (an additive new frame type, still safely dropped). The breaking case throws an internal marker that closes the connection terminally as a new `ClosedReason.IncompatibleVersion`; the play screen surfaces a "this game may need a newer app version; updating may help" snackbar before exiting, and the lobby / public-search VMs map it to their room-closed / connection-error states. Chose keying on `MissingFieldException` over a blanket `Catching`-all-`SerializationException` because the latter would mis-fire on benign additive frames (an unknown discriminator is also a SerializationException) — defeating the additive-degrade tier. Decision recorded in decisions.md (2026-06-27).
**Reviewer notes:** The `IncompatibleVersion` close surfaces as a snackbar via the existing RoomClosed→goBack path rather than a full blocking screen; the acceptance asked for "message + safe exit" and a snackbar + the normal pop satisfies that with far less surface area than reusing the `:features:upgrade` blocking layer (which is built for an app-wide force-update, not a single dead table). If a louder treatment is wanted, the reason now flows to the entry point cleanly. Adding `IncompatibleVersion` made three `when (reason)` blocks non-exhaustive (lobby, public-search, play VMs) — all three now handle it. Red confirmed implicitly: before the change, the missing-field frame was dropped (no `Closed` emission); the unknown-discriminator test guards against over-firing.

## feat(rooms): show net settle + forfeited chips in leave-confirm dialog (ROOM-4)

**Problem:** A player leaving a real-chip MP table couldn't see what leaving does to their chips at the leave moment — they'd win a pot, leave at the next hand, and be surprised by the net (a posted blind already forfeited). Two players asked to "be super in control of their money." The chip math was already correct; the gap was visibility.
**Approach:** Extended `LeaveBotsConfirmDialog` to show, on real-chip tables only, the net this leave settles to the wallet (stack returning minus buy-in, signed `+N` / red when negative) plus a sub-note naming chips committed in the live hand that leaving forfeits. Plumbed the human seat's hand-level `contributedThisHand` onto `SeatView` (it only carried per-street before) so the forfeit note is accurate across streets, not just preflop. The screen gates the settle line on `state.isRealMultiplayer || subsidizedBotTable` — practice/solo tables keep the plain copy.
**Reviewer notes:** Net is computed as `humanStack - buyIn`; the committed-this-hand chips are already out of `stack`, so the net correctly nets out the forfeited blind and `contributedThisHand` is shown purely as an explanatory sub-note, not double-counted. Directional call: I shipped the primary acceptance (net + forfeit callout) and left the secondary ask — letting a player leave *before* the next hand's blinds post — as a follow-up; it's a turn-flow change (when the leave actually fires) rather than a dialog-copy change, larger and riskier than this slice. Reviewer: flag if you want that pulled into scope.
**Deferred:** "Leave before the next hand's blinds are posted" (ROOM-4 secondary ask) — not built; nothing filed yet, reviewer please triage whether it warrants its own todo.

## fix(lobby): keep real buy-in when a placeholder snapshot lands (MP-24)

**Problem:** A joiner who enters via PrivateJoin sees the lobby buy-in render as $0 on a post-#74 build, even though the room's real buy-in was applied server-side (stacks debited). MP-16's `preferRealOver` / `isPlaceholder` invariant guarded the repo's `upsertActiveRoom` and the socket's rebound staging, but NOT the lobby VM's own snapshot read.
**Approach:** `LobbyViewModel.ConnectionUpdated` blindly copied `conn.room` into `state.room` on every `RoomConnection.Connected`. The joiner stages the real room from the join HTTP response, then an early socket snapshot (buyIn==0, before the buy-in resolves) overwrote it with a placeholder. Applied the existing `Room.preferRealOver(state.room)` invariant at that read — the same one the repo + socket already enforce — so a placeholder never regresses a known-good room. One-line guard plus the import; reused the existing data-layer helper rather than re-deriving the placeholder check in the VM.
**Reviewer notes:** Red confirmed first — `connectionUpdated_placeholderSnapshot_doesNotRegressRealBuyIn` failed at `expected 5000 / was 0` before the fix, passes after; `connectionUpdated_realSnapshot_replacesEarlierRoom` guards that a genuine fresh snapshot (member joined) still applies. The host-promotion member-diff below the guard now keys off the retained real room when a placeholder arrives — correct by the `isPlaceholder` contract (buyIn==0 means "not a real snapshot," so its member list isn't authoritative either).

## fix(rooms): reconcile wallet on every MP leave path incl. iOS swipe (MP-23)

**Problem:** A real-chip MP balance could stay at the escrowed value after leaving — the settled balance only appeared on the next foreground (CARDS-5B, the exact symptom `reconcileWalletAfterGame` was built to kill). The screen's top back-arrow and system `BackHandler` already fired `LeaveTable` → reconcile, but an iOS edge-swipe pop can reach the entry point's `onBack` lambda WITHOUT going through Compose's `BackHandler`, popping the screen with the wallet un-reconciled.
**Approach:** Two parts. (1) The MP entry point's `onBack` now fires `PlayPokerAction.LeaveTable` before the pop, so the swipe-back path reconciles like every other leave path — closing the last gap in the acceptance's "every leave path funnels through leaveAndReconcileWallet." (2) Added a `leaveInitiated` latch in the VM so the now-possible double-fire (screen's BackHandler + entry-point onBack on a normal back) runs the teardown — server leave + reconcile — exactly once. Chose firing `LeaveTable` from `onBack` (idempotent via the latch) over trying to make Compose's `BackHandler` intercept the iOS edge-swipe, which isn't reliably in our control; the latch makes the belt-and-suspenders safe.
**Reviewer notes:** Red confirmed first — `leaveTable_firedTwice_sendsLeaveAndReconcilesOnce` failed at `session.leaveCount == 2` before the latch, passes after; `leaveTable_thenLeaveFromBust_tearsDownOnce` guards the cross-action case (a LeaveTable then a LeaveGameFromBust shares the one latch). The genuine residual was the iOS edge-swipe-pop bypassing Compose BackHandler, which is iOS-runtime-specific and not unit-testable here — the entry-point onBack change closes it defensively and the latch + VM tests prove the teardown is single-shot. ## feat(server): server-authoritative `/v1/billing/redeem` + ReceiptValidator seam (BILL-1)

**Problem:** The shop credited chips locally on store confirmation; the server never saw the receipt, so a forged one could mint chips. V1 ship-blocker.
**Approach:** New authenticated `POST /v1/billing/redeem` ({ store, productId, token }) → `ReceiptValidator` → resolve the productId to a catalog `ChipPack` for its server-side `grantsChips` (client never claims the amount) → `BillingRepository.redeem` grants through the existing `WalletLedger` inside one transaction. New `billing_transactions` table (V81) with `UNIQUE(store, order_id)` is the idempotency + audit boundary; the audit row + wallet credit commit together. `ReceiptValidator` ships as a seam with a `DevReceiptValidator` default (trusts the token, uses it as the order id — exercises the full path with local StoreKit/Play test SKUs); BILL-2 swaps the real Apple/Google validators via `replaces`. Decision recorded in decisions.md (2026-06-27).
**Reviewer notes:** Idempotency uses a pre-check on `(store, order_id)` rather than catching the unique-violation on the INSERT — a failed statement aborts the whole Postgres transaction, so a catch-then-read can't work (confirmed by a red test that failed with "current transaction is aborted" before the pre-check). The unique constraint stays as the backstop for the rare concurrent-redeem race (loser's tx rolls back, client retry reads `AlreadyRedeemed`). The grant pins to the user via the validator's account-token binding (BILL-2's job to enforce), NOT the order id — I did NOT touch the client `BillingClient` doc comment that says orderId; that fix is explicitly scoped to BILL-2's hint and I left BILL-2's wording intact. Coverage: `BillingRoutesTest` (6 route/contract/auth cases incl. forged-receipt-doesn't-grant + unknown-product/store 400s), `PostgresBillingRepositoryTest` (4 Testcontainers cases incl. same-(store,order) idempotent-grants-once, same-orderId-different-store both grant), `DatabaseSchemaTest` extended for the new table. Full `:apps:server:test` green. The BILL-5 config gate (`billing.realPurchasesEnabled`) that keeps this dark in prod is its own item — this endpoint is live but the client still credits locally until BILL-5 inverts the seam.
**Deferred:** Wiring the client to actually call `/v1/billing/redeem` (the validate→grant→reflect flow) is BILL-5; the real validators are BILL-2 — both already in `docs/todo.md`, untouched.

## feat(billing): server-authoritative chip credit behind realPurchasesEnabled (BILL-5)

**Problem:** `DefaultPurchaseChipPackUseCase` credited chips locally the moment the store confirmed — a double-credit window it admitted to in its own comment — and the BILL-1 redeem endpoint had no client caller. There was also no flag to ship real billing dark.
**Approach:** Inverted the credit seam into a two-path use case gated by a new `RealPurchasesEnabled` flag (`billing.realPurchasesEnabled`, default off). New `BillingRepository` (api) + `BillingRepositoryImpl` (impl) POST the finished receipt to `/v1/billing/redeem` with `RetryPolicy.idempotent()`. When the flag is **on**, a successful purchase goes validate→grant→reflect: redeem, then `chipsRepository.setBalance(serverBalance)` (the client never claims the amount), then acknowledge; a rejected receipt or unreachable server credits nothing and returns `Failed`. When **off** (default), the prior local-credit path runs unchanged so the dev/Fake flow still exercises end-to-end and real billing ships dark. `Fake`-platform transactions map to no server store, so the repo short-circuits to `Unavailable` — they never reach the real endpoint even if the flag is flipped on in a debug build.
**Approach (directional call):** I made `RealPurchasesEnabled` a single flag that does double duty — selects the credit path AND is the dark-ship gate — rather than two flags, because the acceptance explicitly asked one flag to do both and the real-vs-Dev *client* selection (BILL-3/4's `@ContributesBinding(replaces=…)`) is a compile/DI concern, not a runtime toggle. Rejected alternative: a separate `useServerCredit` runtime flag distinct from a client-selection flag — needless surface for a behaviour that always moves together. Decision recorded in decisions.md (2026-06-27).
**Reviewer notes:** On the real path a `RedeemOutcome.Unavailable` (network down after the user already paid at the store) currently surfaces as `Failed("redeem_unavailable")` and leaves the purchase uncredited until a later retry/sync — I did NOT build an automatic retry/queue for a paid-but-unredeemed receipt; the store still owns the purchase and a re-tap re-redeems idempotently, but a background "drain unredeemed receipts on foreground" job would be the robust follow-up. Flagged below. Tests: extended `DefaultPurchaseChipPackUseCaseTest` to cover both paths — off (local credit, redeem never called), on-success (reflects server balance, zero local credit), on-already-redeemed (AlreadyOwned to suppress the celebration), on-rejected (no credit), on-unavailable (no credit). Did not add a wire-level `BillingRepositoryImpl` HTTP test (ktor MockEngine) — the route contract is already covered server-side by `BillingRoutesTest`; reviewer flag if you want a client MockEngine round-trip too.
**Deferred:** Background drain of paid-but-unredeemed receipts (retry `/v1/billing/redeem` on app foreground for any store purchase that didn't reflect) — nothing filed yet, reviewer please triage whether it warrants its own BILL item.

## test(upgrade): verify force-update gate raises over an in-session client (ENG-6)

**Problem:** The cross-version rule (CARDS-4S) relies on bumping `upgrade.minSupportedVersionCode` to lock out clients too old to parse a breaking frame, but it had never been verified that the blocking overlay raises *live* over a play screen for an in-session client — only the cold-boot path was assumed.
**Approach:** Added `AppGuardStateTest` (first test in `:features:upgrade`) pinning `AppGuardState.from`: a streamed config with a bumped min-version yields `UpgradeRequired`, lowering it back yields `Normal`, upgrade outranks maintenance, and a missing key falls back to the default. The wiring proof is structural: `AppGuardGate` (App.kt) calls `AppGuardState.from` on every `configStream` emission and `AppGuardLayer` draws the overlay *after* the nav-graph `content()` — there is no per-screen branch, so "raises over the play screen" reduces to "the pure function returns UpgradeRequired," which the test covers. Verified z-order (overlay after content, `consumeTouches` swallows fall-through) by reading `AppGuardLayer`.
**Approach (directional call / the real finding):** The acceptance's "if the refresh cadence leaves a gap, close it" surfaced a *deliberate* boundary, not a bug: `OfflineFirstAppConfigRepository` fetches config on **foreground transitions only, never polls mid-session** (documented as intentional). So the overlay raises on the next foreground within the throttle window — including any background→foreground while still in the room — but NOT while a client sits continuously foregrounded mid-hand. I did NOT add polling (it contradicts a documented decision and was deliberately removed). I judged the acceptance satisfied: "within the config refresh window, not only on next cold boot" is met by the foreground-transition path, and ENG-7's `IncompatibleVersion` socket close already gives an in-game client a graceful exit if it actually receives an unparseable frame before the overlay catches it. Recorded the verification + boundary in decisions.md; filed the optional "mid-session push over the socket" hardening in backlog.md.
**Reviewer notes:** No production code changed — this is a verification item, so it ships as a test + docs only. The one judgement call is declaring the no-mid-session-poll behaviour intended-and-acceptable rather than a gap to close; if you'd rather force the overlay onto a never-backgrounding client, the backlog entry sketches the socket-push approach. The test asserts pure logic; the live recompose + z-order are covered by `AppGuardLayer`'s existing `@Preview`s and by inspection, not a Compose UI test (the iOS/Compose render path is a device-QA concern).
**Deferred:** Mid-session push for the gate (cover a continuously-foregrounded client without polling) — filed in `docs/backlog.md` ("Mid-session push for the force-update / maintenance gate").
