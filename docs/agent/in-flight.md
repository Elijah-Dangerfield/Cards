## feat(home): surface active-room rejoin/forfeit on cold launch

**Problem:** Server endpoint `GET /v1/me/active-rooms` and `RoomRepository.getActiveRooms()` both landed earlier in the week, but nothing client-side consumed them — a user whose previous session left a seat warm via the `disconnectedAt` grace timer had no in-app way to discover the ongoing game or release it.
**Approach:** Wired `HomeViewModel` to query the endpoint on init + on `Refresh`, expose `activeRooms: List<ActiveRoomSummary>` in state, and handle a `Forfeit(code)` action that optimistically drops the room then calls `leaveRoom` (re-hydrating from the server only on `NetworkError`/`Unknown` so silent leaves stay silent). Surfaced via a new `ActiveRoomBanner` DS-composed card above the hero on `HomeScreen` with a `Stay`/`Forfeit` confirm dialog. Home was the right home for this (vs. `AppLaunchGate`) because rejoin navigates to `LobbyRoute(prefilledCode = code)` which is reachable from the same router; gating at launch would have meant building a second nav surface for one banner.
**Reviewer notes:** Couldn't verify on a real device — creating an MP room currently flips into `Reconnecting` immediately (per the open repro at the bottom of §C in `docs/todo.md`), so the rejoin flow can't be exercised end-to-end yet. The slice is unit-tested against the four meaningful outcomes (Success, NetworkError, optimistic-drop happy path, NetworkError rollback) but a human should re-verify once the MP path itself is working.
**Deferred:**
- The forfeit success-path doesn't surface a snackbar yet ("your stack came home — N chips returned to your wallet" per spec §5.6). Left as a follow-up; the `leaveRoom` response doesn't carry the returned chip count today and wiring it requires a server change. Reviewer: please triage whether to file this in `docs/todo.md` under the orphan-room policy bullet or leave it inside that same bullet.

## feat(ui): chip-themed dialog bubble factory + bust-dialog migration

**Problem:** `docs/todo.md` flagged that chip-related dialogs (rebuy / bust / chip rewards / soft-bust / tip-the-dealer) should wear a chip-gold `$` bubble instead of the generic emoji one, and asked for a `dialogChipBubble(...)` factory alongside `dialogEmoji(...)`.
**Approach:** Added `dialogChipBubble()` in `Dialog.kt` next to `dialogEmoji(...)` — returns a `DialogEmoji` configured with a `$` glyph, casino-gold solid fill (`PokerPalette.ChipGold`), circle style. Routes through the same `DialogEmoji` / `EmojiBubble` chokepoint so geometry, notch, and ring stay in lockstep. Migrated the one existing chip-themed dialog (`BustDialog` in `HandResultDialogs.kt`, previously `💸`) as the first callsite. Made the executive call to ship factory-only rather than building the spec's "sibling primitive" with a separate render path — `$` already renders cleanly at the shared `H1100` typography (visible in the existing `PreviewEmojiBubble_CircleAccent`), and a true sibling would have added a `BubbleAdornment` sealed type + `topAdornment:` Dialog param for one current callsite. Documented the call inline on the factory and in `docs/todo.md` so a future reviewer can reverse it if a chip dialog ever needs a glyph that doesn't share the unicode path.
**Reviewer notes:** Visual change is single-screen (bust on bots). Eyeball the new `PreviewDialog_ChipBubble` preview in the Studio pane to confirm the gold-on-dark bubble reads as "chip" rather than "alert" — the dialog body still uses `surfacePrimary`, so the gold-vs-surface contrast is what carries the chip vibe.
**Deferred:**
- The four remaining chip dialogs in the spec (rebuy / chip rewards / soft-bust grant / tip-the-dealer) aren't built yet, so there's nothing to migrate. The TODO entry now points new dialog work at `dialogChipBubble()` — no separate backlog item needed.
