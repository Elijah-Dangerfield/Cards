## feat(achievements): show "Earned" on the medallion front, not the XP reward

**Problem:** The Achievements grid renders the same "+X XP" reward label on every tile regardless of whether the user has earned it — so an earned tile and a locked target=1 tile look near-identical at a glance, undercutting the prestige signal the page is supposed to carry.
**Approach:** In `AchievementMedallion.kt`'s front layout, swap the reward label for the string `"Earned"` whenever `isEarned`. Locked quantitative tiles (`target > 1`) keep `"$progress / $target"` (the chase number); locked one-shot tiles (`target == 1`) keep `"+X XP"` (the "what you'd get" preview). The XP / chip reward number isn't lost — the medallion back still shows `+X XP · +Y chips`, accessible by tapping. Collapsed three near-identical Text branches into one `when` for the label.
**Reviewer notes:** No tests landed — the medallion has only `@Preview` coverage and the change is a pure label swap. Build + tests passed on Android; haven't yet exercised on iOS or hardware. The `Earned: {date}` caption from the todo bullet was deliberately deferred (needs a KMP relative-date formatter; out of scope for the at-a-glance fix). The "greyscale silhouette + lock glyph" alternative locked treatment also deferred — current alpha+gradient still reads as "faded but visible," which I judged a feature (the user can see the icon they're chasing) rather than a bug, but a designer might disagree.
**Deferred:** (a) "Earned: {date}" relative-date caption on the back — needs a small KMP date-format helper, no obvious home yet. Left as a comment in the todo bullet. (b) Locked-tile "greyscale silhouette" treatment — design call, left as a comment in the todo bullet.

## feat(achievements): show relative earned date on the medallion back

**Problem:** Follow-up to the front-side "Earned" label commit earlier tonight — the medallion back still said only "Earned" with no indication of *when*. The spec calls out "Earned: {date}" specifically as the prestige caption.
**Approach:** Added a tiny self-contained relative-time formatter `formatEarnedAgo(earnedAtEpochMs, nowEpochMs)` in `AchievementMedallion.kt` that returns "today" / "yesterday" / "Nd ago" / "Nw ago" / "Nmo ago" / "Ny ago" using bare `kotlin.time.Clock` arithmetic (no kotlinx-datetime dependency needed). Wired into the back-side header so it now reads "Earned · 3d ago". Composable-facing overload reads `Clock.System.now()`, test-facing overload takes `nowEpochMs` so the unit test pins behavior at exact bucket boundaries.
**Reviewer notes:** New `FormatEarnedAgoTest` covers each bucket transition (today/yesterday/d/w/mo/y) and the future-time clamp. The format is intentionally short ("3d", "2w") so it fits next to "Earned · " on the small medallion back without wrapping; can be loosened to "3 days ago" if a designer prefers the long form. Contradicts the deferral note I wrote in this same in-flight log earlier — that's because I overstated the difficulty of the formatter when deferring; the inline implementation is ~15 LOC.
**Deferred:** Locale-aware relative time (kotlinx-datetime + ICU) — way out of scope for a single-locale English V1. Backlog if/when localization is in play.

## feat(profile): optimistic Edit Profile writes with rollback

**Problem:** Edit Profile's save path awaited the `PATCH /v1/me` roundtrip before reflecting the new name / avatar / background color anywhere in the UI. On a slow / lossy network the user was stuck on the modal for the whole roundtrip; offline it was effectively broken. The todo bullet at `docs/todo.md` "Edit profile → Writes" specifically called for an optimistic-with-rollback flow surfacing a snackbar on failure.
**Approach:** Two coordinated changes. (1) In `SupabaseIdentityRepository.updateProfile`, snapshot the prior Identity from `_state.value`, write the optimistic merge (new name / avatar / clear-or-set background) to `IdentityCache` + `_state.value` *before* hitting `profileApi.patchMe(...)`; on `Catching { ... }.fold { onSuccess -> keep server identity, onFailure -> restore the snapshot to cache + state }`. The mutex around the whole call keeps concurrent saves serialized so two-in-a-row reads can't tear the snapshot. (2) In `EditProfileViewModel.Submit`, replaced the `appScope.async { ... }.await()` + inline-error-state pattern with a fire-and-forget `appScope.launch { ... }` that maps every non-success outcome to a global `showSnackBar(...)` call. `sendEvent(EditProfileEvent.Saved)` fires immediately after dispatching the launch — the screen pops without waiting on the network. The local Identity flips at the same instant, so Profile screen / nav drawer / wherever-else-binds-Identity all reflect the new value within a frame.
**Reviewer notes:** Snackbar copy reads as a single sentence ("Couldn't save — that name is already taken.") because the screen is gone by the time it fires; multi-line copy with a "Try again" would need a button-action wire-up the snackbar slot can already accept but isn't worth wiring for V1 (user re-enters Edit Profile, sees the old name pre-filled, can edit again). The repo-level mutex held through the network call means a SECOND `updateProfile` while a first is in flight queues behind it — acceptable here since the only realistic caller is `EditProfileViewModel.Submit` which itself can only fire once per VM lifetime. Repo-level tests still don't exist for `SupabaseIdentityRepository` (noted in todo.md §D as a separate gap); the new `submit_emitsSavedImmediately_withoutWaitingOnNetwork` test pins the VM-side contract, and the existing teardown test still pins that the network call survives VM cancellation. Did not migrate the `isSubmitting` state out of `EditProfileState` — the screen still reads it for the "Saving…" button label that briefly shows in the frame between Submit dispatch and the Saved-driven nav pop. Removing it cleanly would mean reworking the Save button's enabled / label logic for a transient that's now never-observed; the existing field is harmless.
**Deferred:** `IdentityRepository` interface didn't grow a separate `applyOptimistic + commit + rollback` triplet — the optimistic-with-rollback semantics live entirely inside `updateProfile`. If a future caller (background sync, batch profile edit, multi-field write-through) needs to compose multiple optimistic writes, that's the time to lift the snapshot pattern up; for V1 the single-call shape is fine. The Reads half of the todo bullet — "drive the avatar picker from the local DB; reconcile in the background" — is still open; deferred, the bullet was kept in `docs/todo.md` with only the Writes half marked landed.
