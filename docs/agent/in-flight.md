## fix(auth): give slow email signups a retryable timeout error (AUTH-20)

**Problem:** A slow/timed-out `POST /auth/v1/signup` (built-in Supabase email sender under repeated signups) hit the 10s client timeout and surfaced as the generic "Sign up failed" with no retry guidance — the tester saw "signup failed? no idea why."
**Approach:** Two parts. (1) Root cause: raised the Supabase auth client `requestTimeout` from supabase-kt's 10s default to 30s, sized for the confirmation-email round trip (the client only installs Auth, so this touches auth calls only). (2) UX: a request timeout now maps to a distinct, retryable `Timeout` outcome/error with honest copy ("That took longer than expected. Give it another try.") instead of the dead-end `Unknown`. Chose a dedicated `Timeout` variant over folding into `NetworkError` because "Check your connection" is misleading when the connection is fine and the *server* is slow — the honest message is different and steers the user to retry rather than diagnose their wifi. Applied to the sign-up + anonymous-guest link-email paths (both drive the create-account flow and hit the same slow round trip). The `Profile → Claim account` flow consumes the same two outcomes, so it got the parallel `ClaimAccountError.Timeout` branch + copy. Verified the raw `HttpRequestTimeoutException` (supabase-kt rethrows it un-wrapped; it's an `IOException`, so `Catching {}` keeps it) reaches the mapper and previously fell to `Unknown`.
**Reviewer notes:** `HttpRequestTimeoutException` is a Ktor class (unlike the supabase-kt `RestException`/`HttpRequestException` the other mappers key on), so it IS synthesizable from commonTest — the new repo-level mapping tests construct it directly, which the existing "belongs in a separate file" caveat couldn't do for the supabase exceptions. 30s is a judgement call: long enough for a slow built-in-SMTP send, short enough not to hang the UI forever; revisit once custom SMTP (Resend) lands and the send is fast/decoupled.
**Deferred:** `signInWithEmail` still buckets a timeout as `Unknown` (sign-in sends no confirmation email, so it's far less likely to time out) — left as-is for a focused commit; reviewer please triage whether to extend `Timeout` there for consistency. Nothing written to backlog.

## fix(auth): detect Supabase already-registered fake-success on sign-up (AUTH-21)

**Problem:** Signing up with an already-registered email flashed "check your email" for ~1s then dropped into the app. Supabase's anti-enumeration returns a fake success (HTTP 200, a user object with an EMPTY `identities` array, no exception) for an existing email, so `signUpWithEmail` returned `VerificationRequired` and the client routed to VerifyEmail instead of saying "already registered, sign in."
**Approach:** Fixed at the root — the `SupabaseAuthGateway` seam. `signUpWithEmail` now returns a projected `GatewaySignUpResult` (`VerificationSent` / `EmailAlreadyRegistered`) instead of `Unit`; `RealSupabaseAuthGateway` reads the returned `UserInfo.identities` (empty on a non-null user = Supabase's documented obfuscation signal, populated on a real new signup) to decide. The repository maps `EmailAlreadyRegistered` → `SignUpOutcome.EmailAlreadyRegistered`, which the existing `SignUpViewModel` / `ClaimAccountViewModel` branches already surface as the inline "that email is already in use, try signing in" error next to the visible "Sign in" button — no VerifyEmail flash, no drop into the app. Chose the gateway seam over VM-level guessing because the signal (empty identities) only exists on the raw supabase response; detecting it anywhere downstream is impossible.
**Reviewer notes:** Scoped deliberately to the fresh-signup (`signUpWith(Email)`) path, NOT the anonymous-guest claim path (`linkEmailIdentity` → `updateUser`). The empty-identities signal can't be reused there: anonymous users ALWAYS have empty identities, so the same check would flag every guest claim as "already registered." The claim path already maps a thrown `RestException` ("user already registered" / "taken") to `EmailAlreadyRegistered`, so its already-registered case is covered separately. A new user tapping "Sign up with email" from the landing has no session yet, so they take the fresh-signup path this fixes. Verified red-first: `signUp_obfuscatedAlreadyRegistered_mapsToEmailAlreadyRegistered_notVerification` failed before the repo mapping, passes after. iOS + Android test compile both green.
**Deferred:** None.

## fix(billing): finish terminally-rejected StoreKit receipts to break the replay loop (BILL-13)

**Problem:** On a fresh install, StoreKit auto-replays the tester's prior unfinished orders. Their `appAccountToken` is a prior anon identity that matches neither the new anon userId nor its install-lineage, so `/v1/billing/redeem` returns `receipt_rejected`. The client left every rejected transaction unfinished (BILL-7's "preserve evidence" rule) — so Apple replayed it every launch AND, because a stuck unfinished consumable is what StoreKit hands back on the next buy of the same SKU, it shadowed every new purchase → "every single purchase failing."

**Approach:** Split a *terminal* receipt rejection (will never validate for this identity — forged / account or product mismatch / revoked) from a *retryable* one (validator unconfigured, store API unreachable). Server: `ReceiptValidation.Invalid` gains `retryable` (terminal is the safe default; only the unconfigured + `google_lookup_failed` paths set it true); the redeem route answers a retryable Invalid with **503 `receipt_unavailable`** and a terminal one with the existing **400 `receipt_rejected`** (Sentry capture now fires only on terminal). Client: a 400 `receipt_rejected` maps to a new `RedeemOutcome.RejectedTerminal` (any other 4xx stays `Rejected`, 5xx/503 stays `Unavailable`); on terminal, `DefaultPurchaseChipPackUseCase` **finishes/consumes** the transaction in both the interactive and launch-drain paths so it stops replaying and stops blocking new buys. Chose terminality-at-the-source (a domain flag the validator sets) over the client string-matching reasons, because only the validator knows whether a refusal is transient — and mis-labeling unconfigured as terminal would finish (strand) a genuinely paid purchase.

**Reviewer notes:** This is the highest-leverage SLICE, not the whole item. It fixes the *failure loop* (acceptance part 1): purchases work again because the stuck receipt is cleared. It does NOT recover the chips the user already paid for on the stuck order (acceptance part 2) — for `apple_account_mismatch` the entitlement is discarded (`purchase.discarded` event), because on a fresh install both the anon userId and the install_id rotate, so there's no server-side link back to the prior purchaser. Safely crediting across an unlinkable identity needs the AUTH-19 identity-churn design (device-stable purchaser link surviving reinstall) — too large/risky for one clean commit, and crediting on a bare replayed receipt would reopen the "one user redeems another's receipt" hole. Rewrote BILL-13 to describe that remaining gap (kept the ID). Tradeoff is acceptable pre-launch/sandbox: the alternative is a permanently broken shop. Note: IAP is gated to non-anon users interactively, but the launch drain runs for anon sessions too, which is how the tester's replays hit a fresh anon id. Tests red→green: client `on_terminalRejection_finishesTransaction…` + `redeemOutstanding_terminalRejection_finishesStuckTransaction…` (+ non-terminal-stays-replayable guards), repo `redeem_badRequestReceiptRejected_isTerminal…` / `…OtherCode_isRejected…` / `…serviceUnavailable_isUnavailable`, server `redeem_retryableRejection_returns503…`. Server + billing tests, Android assembleDebug, iOS billing compile all green.
**Deferred:** Cross-install entitlement recovery (acceptance part 2) — rewritten into BILL-13 in `docs/todo.md`, reviewer please scrutinise the identity-link direction.
