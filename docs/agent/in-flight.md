## fix(server): deconflict player-stats endpoint path from /v1/me/stats (PROG-1)

**Problem:** The PROG-1 server slice (commit `3a18d0b4`, this same cycle) registered `GET /v1/me/stats` for the new player-stats snapshot, but that exact path was already taken by the lifetime distinct-opponents read in `meRoutes` (live, wired into `LifetimeStatsRepositoryImpl`). Two identical `get("/v1/me/stats")` registrations under the same auth block collide — Ktor attaches both to one routing node and the later registration (`meRoutes`, installed after `playerStatsRoutes` in `Application.kt`) wins, leaving the new player-stats GET unreachable. The PROG-1 client half can't fetch its snapshot until this is resolved.
**Approach:** Moved the new endpoints to their own namespace — `GET /v1/me/player-stats` and `POST /v1/me/player-stats/sync` — rather than touch the pre-existing `/v1/me/stats` lifetime read, which shipped first and is already in production client code. Picked `player-stats` over collapsing the two endpoints into one merged DTO because the lifetime distinct-opponents count is a server-derived read with no client write-ahead, whereas player-stats is the idempotent sync surface; merging them would entangle two unrelated read-path policies. Only the route paths + their doc comments changed; the repo, DTOs, migration, and tests are untouched (no test asserted the old path).
**Reviewer notes:** No route-level test exists for the player-stats endpoints yet (only the Postgres repo integration test + the MeRoutes fake), so this rename had nothing to update there. The PROG-1 client repo (still open) should target `/v1/me/player-stats`. Worth a glance: confirm no other in-flight branch hard-codes `/v1/me/stats` for the new snapshot.

## test(progression): pin degraded-play XP replay-once on claim (AUTH-2)

**Problem:** AUTH-2 asked to reconcile local bot-play progress when a degraded (`Profile.Fallback`) account is finally created: replay the pending local XP/chips deltas onto the server total **once**, never re-grant the provisional starter.
**Approach:** Investigation found the behaviour is already built and wired end-to-end — both `ChipsRepositoryImpl` and `ProgressionRepositoryImpl` are `AppEventListener` multibindings whose `onAccountClaimed` flushes their idempotent outbox (`wallet_events` / `xp_events`) and reconciles to the server's authoritative balance/total; the starter is server-seeded in `findOrCreate` and never granted client-side (`setBalance` only hydrates), so it structurally can't be re-granted. The one genuinely-missing piece was a test proving the XP half (the todo's "riskier half") survives the full degraded-play → claim path. Added `degradedPlayDeltas_replayOnceOnClaim_andDoNotDoubleApply` to `ProgressionRepositoryImplSyncTest`: pending local deltas flush exactly once on `AccountClaimed`, the total reconciles to the authoritative value, and a second claim re-posts an empty/replayed batch without double-applying. Removed AUTH-2 — its acceptance ("replay pending local deltas once, never re-grant the starter") is now satisfied and pinned.
**Reviewer notes:** This is a verify-and-close, not new behaviour — I shipped a test, not a feature, and removed the bullet because the feature it describes was already implemented across prior cycles and is now covered. If you'd rather AUTH-2 stay open until the *chips*+XP combined claim path is pinned in one test (chips already has its own `ChipsRepositoryImplSyncTest` + the `onAccountClaimed` coverage, just not a single cross-repo test), reinstate it — but I judged the two independent per-repo suites + the shared dispatcher fan-out sufficient. The "degraded play stays purely local, doesn't write the server-bound ledger" clause is satisfied in practice by the outbox: degraded play writes to the local outbox only, and `authedCall` can't reach the server until auth exists, so the rows replay idempotently on claim rather than being suppressed — the better design than a separate write-suppression path that could drop deltas. `:libraries:cards:impl:testDebugUnitTest --tests ProgressionRepositoryImplSyncTest` green.
