## test(config): pin MapOverrides.applyOverrides path merge

**Problem:** `MapOverrides.applyOverrides` (the `internal` extension `OfflineFirstAppConfigRepository` calls on every cache read at [`OfflineFirstAppConfigRepository.kt:83`](../../libraries/config/impl/src/commonMain/kotlin/com/cards/libraries/config/impl/repository/OfflineFirstAppConfigRepository.kt) to thread QA-menu overrides into the resolved server config) had no direct test. The repo test exercises the wider pipeline but never asserts the merge shape directly — a regression in the tail-recursive `setValueRecursive` path-builder would silently corrupt every `ConfiguredValue<T>` resolution. The interesting corner is the deliberate copy-on-write of inner maps in [`MapOverrides.kt:44`](../../libraries/config/impl/src/commonMain/kotlin/com/cards/libraries/config/impl/MapOverrides.kt) — JSON-deserialized child maps come back read-only on Kotlin/Native, so a naive `put` would crash mid-override.
**Approach:** Added [`MapOverridesTest`](../../libraries/config/impl/src/commonTest/kotlin/com/cards/libraries/config/impl/MapOverridesTest.kt) (7 cases) co-located with the impl, same package so `internal` symbols are reachable. Pins (1) empty-overrides returns the receiver unchanged (`assertSame`), (2) single top-level override applies and unrelated siblings survive, (3) nested dot-path into an empty parent builds the whole branch chain, (4) nested override into an existing nested map preserves siblings at every level, (5) the K/Native read-only-inner-map corner — passing a `Map.of`-shape read-only inner map doesn't throw and *the receiver's inner map remains untouched* (defensive against an in-place mutation regression), (6) last-write-wins when two overrides share a path, (7) multi-branch overrides all land in the same pass. Verified locally via `:libraries:config:impl:testDebugUnitTest` — 7/7 pass.
**Reviewer notes:** The K/Native edge case isn't perfectly reproducible from JVM-side test code (we can't materialize a true Native-read-only map cross-target), so the test stands in with `mapOf(...)` and asserts the receiver isn't mutated rather than asserting the put-on-read-only would have thrown. That's the contract worth pinning anyway — "the merge doesn't mutate inputs" — and it's the property the K/Native crash bug would have violated.
**Source:** worker-hydrated this cycle (not human-curated). Lane A — verifiable gap: `applyOverrides` is internal, no test mentions it, and the K/Native copy-on-write is exactly the kind of subtle invariant that drifts silently.
