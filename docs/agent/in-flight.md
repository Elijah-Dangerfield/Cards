# In-flight

## feat(room): notice for a mid-game joiner waiting to be dealt in

**Problem:** Joining an in-progress public/MP table seated the player as a seatless spectator with no indication they were waiting for the next hand boundary — the table read as stuck/empty (feedback CARDS-22).
**Approach:** A seatless local member is the signal — `RemotePokerSessionFactory.tableFor` already derives `humanSeatIndex = -1` for a mid-hand joiner, so I plumb a `waitingToBeDealtIn` flag onto `TableUiState.Active` (set only when `humanSeatIndex < 0`, so solo sessions — always seated — never trip it) and render a slim "You'll be dealt in next hand" notice under the top bar, mirroring the existing `PracticeTierLabel`. Chose this over a new server frame because the seatless snapshot the server already sends is a sufficient, self-clearing signal — the notice disappears the moment the next hand seats them.
**Reviewer notes:** This is the client half of the CARDS-22 pairing; the server-side B7 stall (the joiner actually being dealt in) is untouched and still open in `docs/todo.md`. The notice will also show briefly for any other seatless-member case (e.g. a forfeited member downgraded to spectator) — which is correct framing, not a bug. Covered by two `RemotePokerSessionFactoryTest` assertions + a screen preview.

## feat(ui): slam-in entrance + confetti for the level-up celebration

**Problem:** The level-up reveal landed flat — the dial scale+faded in on one spring with a single start-of-anim haptic, no payoff on arrival.
**Approach:** Reworked the entrance in `LevelUpCelebration.kt` into a "slam in" — a fast fade, then a scale that dips (anticipation), overshoots past full via `keyframes`, then settles on a `MediumBouncy` spring — with a two-beat haptic (a light `TextHandleMove` tick as it launches, a heavy `LongPress` impact on the slam landing). Confetti was a genuinely missing DS primitive, so I added `ConfettiBurst` in `:libraries:ui`: a single-`Canvas`, frame-clock-driven paper spray (no per-particle composables) themed off chip-gold + both accents, one-shot and self-limiting. It fires the instant the dial lands. Kept the feel baked into the DS component per the todo, not the host. Used only `LongPress`/`TextHandleMove` haptics since those are the multiplatform types already in repo use (no `Confirm`/`GestureEnd` reliance).
**Reviewer notes:** Confetti physics are eyeballed, not tuned against Studio — worth a glance in the `LevelUpCelebration` previews (which render a frozen mid-flight frame) and the new `ConfettiBurstPreview`. `ConfettiBurst` is generic and reusable; the achievement-unlock surface is the obvious next adopter (not done here). Animation timing is untestable in unit tests — verified by compile + assembleDebug + previews only.

## feat(rooms): refresh active rooms on foreground + reconnect

**Problem:** Home's active-room banner reads from `observeActiveRooms()`, a client-side projection updated only by *this device's* create/join/leave — so a room closed off-device (host elsewhere, server-side forfeit/grace expiry) wasn't reflected until the next explicit `getActiveRooms()`.
**Approach:** Made `RoomRepositoryImpl` an `AppEventListener` (multibinding) that re-pulls the authoritative `GET /v1/me/active-rooms` snapshot on the two edges where the projection is most likely stale — warm foreground (skips cold boot, which loads the banner itself) and connectivity-regained — fired off `AppCoroutineScope`, best-effort. Chose the per-edge refresh over a full WS-pushed source because the existing snapshot endpoint + the established `AppEventListener` precedent (`GuestSessionHealer`) ship the acceptance criterion ("reflects off-device changes without a manual refresh") with zero server work; the live-while-open WS push is the bigger lift and pairs with the unbuilt online-presence signal, so I sliced it out and rewrote the todo to describe that remaining gap.
**Reviewer notes:** This catches off-device changes when the user *returns* to the app, not live while Home stays open (that's the remaining sliced item). Verified no DI cycle (`:apps:compose:assembleDebug` green) — networking doesn't reach `AppEventBus`, so unlike `GuestSessionHealer` no lazy providers were needed. Added 3 tests (warm-foreground refresh, cold-boot no-op, connectivity refresh); converted `RoomRepositoryImplTest` to `CoroutineTest` for `dispatchers`.
**Deferred:** The live WS-pushed active-rooms source is now the rewritten `docs/todo.md` item (still P1) — reviewer, the slice direction is mine.

## feat(server): admit non-member read-only spectators to Open/Public tables

**Problem:** The room socket rejected any subscriber who wasn't a room member (`RoomSocketRoutes` closed with "not a member"), so B4's pure non-member spectator — a seatless watcher of a matchmaking-discoverable table — couldn't exist.
**Approach:** Replaced the membership gate with an `isSpectator` branch: a non-member is admitted to an Open/Public room and gets the existing scrubbed-for-everyone game view (`scrubbedFor(-1)`, already correct for a seatless viewer), while a Private (code-only) friend room stays closed to non-members. Spectators are read-only — every gameplay frame from them is bounced at the drain loop with a rejected `IntentAck` ("spectators cannot act") before any escrow / start-hand orchestration runs — and they carry no seat, so I skip `markConnected`, the mid-hand-join queue, and the disconnect reaper for them (those all no-op on a non-member anyway; skipping keeps it explicit and off the path). Chose to gate at the drain loop rather than inside each session method because the session's seat-resolution would reject it regardless, and bouncing early keeps the escrow/funding paths untouched.
**Reviewer notes:** Server-only slice — there's no client entry point that opens a spectator socket yet (public-room discovery + "watch" UI is the out-of-scope client half, now the rewritten B4 bullet). The B4 section and the dependent orphaned-room (B0a) bullet are updated to reflect the seatless-subscriber auth now existing. 4 new `RoomSocketRoutesTest` cases: spectator admitted to Open + sees snapshot (not seated), Private still rejected, spectator intent rejected-ack, spectator close leaves members untouched. Full `:apps:server:test` green.

## fix(server): advance server-dealt all-human tables at hand end (B7/CARDS-25)

**Problem:** Open/Public tables are server-dealt — the client hides the Start / next-hand control and `handleStartHand` rejects non-Private starts. But `ServerBotDriver.maybeAdvanceBotTable` only auto-advanced *mixed* (human+bot) tables. The moment a server-dealt table converged to all-human (every matchmaking bot trimmed or busted out), nothing dealt the next hand: the server wouldn't (no bot to drive it) and the client couldn't (no next-hand control exists for a server-dealt table). The table stalled permanently after a hand finished, every seat's control inert — the B7 / CARDS-25 freeze.
**Approach:** Taught the driver that a table is `serverDealt` (set per-startHand by the registry, the only layer that knows the room's visibility — `dealFundedHand` passes `visibility != Private`). `maybeAdvanceBotTable` now falls back to the lowest-seat *human* as the advancer when there's no bot but the table is server-dealt — exactly as a bot stands in on a mixed table. A host-run Private all-human table still leaves `serverDealt` false, so it keeps tapping next-hand at its own pace (unchanged). Chose threading a single `serverDealt` flag through `startHand` over plumbing `RoomVisibility` deep into the driver, and over a route-layer advance trigger (which would race the driver's advance and risk double-deals). The root cause is the missing dealer for a server-dealt all-human table, independent of *how* it got there — so this also covers the mid-game-join → bot-trim path the todo flagged as the prime suspect.
**Reviewer notes:** Pinned two ways. Deterministic unit test `ServerBotDriverTest.serverDealtAllHumanTable_autoAdvances_withoutNextHandTap` (zeroed delays) is the load-bearing proof; the existing `allHumanTable_doesNotAutoAdvance_atHandEnd` still passes (it leaves `serverDealt` false → Private behaviour unchanged). Full-wire `MatchmakingPlayTest.serverDealtAllHumanTable_advancesConsecutiveHands_withNoNextHandTap` plays 3 consecutive hands on an Open two-human table with no next-hand tap. I deliberately exercised the all-human path via an Open table rather than the bot-trim-down path: over the real wire, trim cadence + bot-fold randomness made a trim-to-all-human test flaky, and the fix is identical for any route to all-human. To keep the wire test fast I added two defaulted test-only seams on `DefaultGameSessionRegistry` — `mixedNextHandDelayMs` (settle delay, prod 4s) and `botThinkDelayMsOverride` (a scalar, kept scalar so `:apps:integration` needn't see the `:libraries:bots` types) — both wired to the driver and shrunk to 50ms / 0 in `InProcessServer`. Removed the now-resolved B7 P0 from `docs/todo.md`; the separate P1 "mid-game joiner isn't dealt in at the next boundary" is an untouched, distinct seat-allocation gap and stays.
**Deferred:** The B7 P1 mid-game-joiner-not-dealt-in remains (different path — `queueJoiner` / seat allocation on join, not the advance gate). Left in `docs/todo.md` as-is.
