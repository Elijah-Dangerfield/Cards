## feat(telemetry): bind Sentry user to identity state

**Problem:** `AppTelemetry.setUser(...)` existed but had no callers — every Sentry crash attributed to "unknown user," even though `identity.userId` is stable per install for anon users.
**Approach:** New `TelemetryUserBinder` in `libraries/cards/impl`, multibound as an `AppEventListener` so it's eagerly initialized via the dispatcher set. On `onColdBoot`, it launches a single `appScope` collector against `IdentityRepository.state`, filters to `SignedIn`, dedupes by `(userId, displayName)` and forwards into `Telemetry.setUser`. `onSignedOut` clears the user. Picked the listener pattern (vs. an `AppViewModel`-owned observer) so the wiring lives next to the other identity-dependent bootstrappers (Chips/Inventory/Equipment sync) and is discoverable from the multibinding set rather than from `:apps:compose`'s graph.
**Reviewer notes:** Email field is null — `Identity` doesn't carry email and the profile API isn't exposed here. If the bug-report email pickup item lands later it can teach `Identity` to carry email and this binder will pick it up automatically. The `if (job != null) return` guard in `onColdBoot` is defensive — the dispatcher dispatches `ColdBoot` once per process by design, so it's belt-and-suspenders.

## fix(viewmodel): route Leave + Forfeit through AppCoroutineScope

**Problem:** `LobbyViewModel.Leave` and `HomeViewModel.Forfeit` ran their `leaveRoom(code)` POST inside `viewModelScope` via `SEAViewModel.handleAction`. If the user popped the screen mid-call (the realistic path — that's what triggers Leave/Forfeit) the VM died and the in-flight HTTP request was cancelled, leaving the server-side seat hanging until the WS heartbeat eventually GC'd it. Lobby's own error string ("Your seat will free up.") was the code admitting the race.
**Approach:** Both VMs now inject `AppCoroutineScope` from `:libraries:flowroutines` (already SupervisorJob + Default-dispatched, single-bound) and wrap the leave call as `appScope.async { rooms.leaveRoom(code) }.await()`. The async job is parented to appScope, so VM teardown only cancels the awaiting continuation — the underlying HTTP request still completes. No new abstraction; the todo's parenthetical literally said "or `AppScope` `CoroutineScope`" was acceptable. New `leave_serverCallSurvivesViewModelTeardown` test in `LobbyViewModelTest` pins the survival contract (gates `leaveRoom` on a `CompletableDeferred`, cancels `vm.viewModelScope`, completes the deferred, asserts `leaveFinished == 1`). AGENTS.md → "SEAViewModel Pattern" gains a "Fire-and-forget actions outlive the screen" subsection.
**Reviewer notes:** Sticking with `AppCoroutineScope` rather than introducing a separate `BackgroundScope` type avoids a synonym — the existing scope already has the right semantics (SupervisorJob, app-lifetime, DI-bound, Default dispatcher) and is already used by `ChipsSyncBootstrapper` / `InventorySyncBootstrapper` / `SignedOutLocalDataCleaner`. If a future case needs a different cancellation policy (e.g. a Main-bound scope), introduce the new type then.
**Deferred:** Other "must reach the server" actions called out in the todo (end-of-session telemetry writes, etc.) — not migrated in this commit; left a follow-up bullet in `docs/todo.md` § Engineering / structural.

## feat(identity): carry account email; pre-fill bug-report + feedback forms

**Problem:** `Identity` didn't carry the user's email even though Supabase had it, so the optional email field on bug-report and feedback always started blank — even for claimed users — and `TelemetryUserBinder` left `email = null` on every Sentry user. The Telemetry binder explicitly noted "email is left null today because Identity doesn't carry it"; the prior cycle's commit left an open todo bullet to wire this once `Identity` learned `email: String?`.
**Approach:** Added `email: String? = null` to `Identity` (default keeps every existing constructor call compiling untouched). `IdentityCache.IdentityRecord` round-trips it (kotlinx-serialization default = null, so existing on-disk caches load without migration). `SupabaseIdentityRepository.bootstrapProfileLocked()` and the `updateProfile` success path read `supabase.auth.currentSessionOrNull()?.user?.email` — Supabase is the source of truth; the server's `/v1/me` doesn't return email and adding a column for it would be pure duplication. `TelemetryUserBinder` now forwards `resolved.email` into `setUser(...)` and includes email in its `distinctUntilChanged` predicate so an email-only change still re-emits. `FeedbackViewModel` and `BugReportViewModel` seed `initialStateArg` from `identityRepository.currentIdentity?.email.orEmpty()` (synchronous read of the StateFlow's current value, no awaitIdentity / launch in init — falls back to blank during the brief cold-start race window before identity resolves, matching the "anon users still get a blank field" todo line).

## feat(home): collapse multi-active-room state down to the newest

**Problem:** A user is only ever supposed to be in one active room — anything else is the system failing to clean up after an app crash, force-quit, or network blip. `HomeViewModel.loadActiveRooms()` was passing through whatever the server returned, so a fleet of stale memberships would render as a stack of `ActiveRoomBanner`s racing for the user's tap. The todo's `# C` bullet calls this out as a "needs to be recovery, not a normal state" gap.
**Approach:** New `reconcileToSingleRoom(rooms)` helper inside `HomeViewModel`: 0–1 rooms pass through unchanged; for 2+, sort by `createdAtEpochMs` desc, keep the newest in state, and fire `appScope.launch { roomRepository.leaveRoom(code) }` for each stale room — fire-and-forget under the app-lifetime scope so the cleanup completes even if the user navigates away from Home immediately. Warning-level KLog so the steady-state rate is visible if/when it becomes non-zero. Two new tests: `activeRooms_multiple_keepsNewest_andLeavesOlderOnes` pins the keep/leave decision with three rooms varying createdAtEpochMs, `activeRooms_singleRoom_doesNotIssueAnyLeave` pins that the steady state still doesn't trigger any cleanup. Existing `forfeit_optimisticallyRemovesRoom_andCallsLeave` test simplified to a single-room setup — its old two-room setup is now incompatible with the new reconciliation, and the "only the targeted room is removed" assertion only meaningful in a world where multi-room is normal.
**Reviewer notes:** Server-side fix (WS heartbeat + ping-pong-driven eviction so multi-room can't happen in the first place) is still open — see the rewritten `docs/todo.md § C` bullet. This client-side reconciliation is the belt-and-suspenders, not the fix. The "sit out vs. fully remove" product call on what eviction should do is also still open and explicitly tagged for human input in the bullet — neither half was attempted here.
**Deferred:** None for this commit. The server-side heartbeat slice is captured in the same `docs/todo.md` bullet (still under § C) so the reviewer / next worker can pick it up; it's not a deferred-by-me item but a parallel open one.
