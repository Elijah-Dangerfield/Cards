## fix(lobby): full-screen retry state for a failed room creation

**Problem:** When `rooms.createRoom(...)` failed, the lobby left the user on the "Setting up your table…" spinner with a small red error line and no way forward — the create surface had already popped (CARDS-2E).
**Approach:** Added a `LobbyState.createError` derivation (a Create* error with no room and not mid-create) that drives a new full-screen `CreateErrorContent` in `LobbyScreen` — title + message + a primary **Try again** (re-fires `LobbyAction.CreateRoom`, which the VM can do because it still holds the create args) + a secondary **Go back**. Chose in-place retry over routing back to the popped `PrivateCreateRoute` because the args are already captured and retry is the common intent; the join-error fix (CARDS-28) routes back only because a bad *code* must be re-typed, which doesn't apply to create. Aligns visually with `BlockingErrorScreen`.
**Reviewer notes:** Retry shows the spinner again while in-flight (`createError` goes null when `creating` flips true) then re-renders the error if it fails again — intended. Not exercised by a Compose UI test (none in this module yet); covered by VM-level tests on the `createError` derivation. The "room not found" join treatment stays inline as before — only the create paths get the full-screen state.

## test(integration): pin the two-client same-nonce dedup race over the wire

**Problem:** The last open Round 2 fan-out box in `testing-plan.md` — `twoClientsRace_sameIntent_serverDedupesViaNonce` — had no integration-tier coverage; only single-client nonce idempotency was pinned (unit tier).
**Approach:** Added `NonceRaceTest` + a `GameplaySession.submitWithNonce(intent, nonce)` helper so a test can drive an explicit shared nonce. Realized the race as the **same** acting client resending one nonce twice concurrently, NOT two distinct users: the server records a nonce only for an *accepted* intent (after seat-ownership validation), so a second user's duplicate is a legitimate wrong-seat rejection that never burns the nonce — making "two distinct users, same nonce → both accepted" not a real contract. The same-actor resend is the actual reconnect-resend idempotency case, so that's what the box should mean; documented this reasoning in the test KDoc and the testing-plan note. Verified non-flaky 5x under `--rerun-tasks`.
**Reviewer notes:** I reinterpreted the plan's box wording (it said "both clients ... same nonce") to the same-client resend because the two-distinct-user version is provably flaky against the real server (confirmed: it fails ~2/3 when the non-owning user's frame is processed first). If you'd rather the box stay open for a genuine two-user variant, the realistic one would require the server to dedup *before* actor validation — a server change, not a test. Flagging the wording reinterpretation for your call.

## feat(matchmaking): pick-a-table chooser over the candidates endpoint

**Problem:** Find auto-joined the first server match (`PublicSearchingScreen` seated silently). The read-only `GET /v1/matchmaking/candidates` endpoint existed but no client surface consumed it — the owner-approved direction is "show the matches and let the user pick which to join."
**Approach:** Added the client `MatchmakingApi.candidates` (idempotent GET) + `MatchmakingRepository.findCandidates` → `CandidatesOutcome`, then grew `PublicSearchingViewModel` a `SearchPhase.Choosing` rather than a separate screen/VM/route. On Start it browses candidates: non-empty → the chooser lists tables (buy-in, seats taken/max, real-human count) and re-polls every 5s so new tables surface; empty (or emptied-out) → it falls straight through to the existing find-and-wait search, so the honest bot fallback is reached identically. Picking a table joins it by code (`joinRoom`, carrying the existing over-balance gate) and reuses the same socket-observe → Playing → hand-off path. **Direction call:** phase-in-the-existing-VM over the todo's literal "new route + screen" because the chooser shares the connect/handoff/leave/bot-fallback plumbing with the search and the empty-result paths must converge anyway — documented in `decisions.md` 2026-06-24. Rejected joining via `findOrJoinPublic` (could seat at a *different* table than the one tapped) in favour of join-by-code.
**Reviewer notes:** The "Start a fresh table" button on the chooser routes through a new `StartFreshTable` action (not `PlayBots`, which needs a held room code the chooser doesn't have yet) → fall-through to the genuine wait. The candidates affordability/range checks mirror `find`'s server-side fences; the authoritative debit stays the sit-down escrow. No Compose UI test (module has no harness) — covered by VM-tier tests (chooser shown without seating, join-by-code + handoff, over-balance error, empty → fall-through, start-fresh) and repository-tier wire-mapping tests (200 ordered/empty, 400 insufficient/invalid, 401). Build + both test files green.
**Deferred:** Showing humans-vs-bots split more richly, or a "you're already seated here" marker for a table the caller is in (the server includes it per its KDoc) — nothing filed; reviewer please triage if wanted.

## feat(profile): friend-requests inbox with accept/decline + empty state

**Problem:** The friend graph's inbound half had no client surface — the server's `GET /v1/friends/requests` + accept/decline routes existed (and the Profile "friend-via-play empty state" item was gated on the inbox landing on `ProfileScreen.kt`), but `FriendRepository` only exposed the outbound `sendRequest`. So there was no way to see or action a pending request, and the play-to-friend empty-state copy had nowhere to live.
**Approach:** Grew `FriendRepository` (`:libraries:social`) with the inbox half: `observeIncomingRequests()` (a `StateFlow<List<FriendProfile>>`), `refreshIncomingRequests()` (same two-step ids→`/v1/profiles` resolve the recently-played-with shelf uses), and `accept`/`decline` returning a typed `RespondToRequestResult`. Accept/decline drop the actioned row from the flow optimistically (and treat a 404 "already gone" as success). Added a `FriendRequestsSection` to `ProfileScreen` (avatar + name + Accept/Decline per row; the friend-via-play empty-state copy when empty), gated to non-anonymous accounts since a guest has no friend graph. The EntryPoint observes the inbox and refreshes keyed on the authenticated id. Closed both Profile todo items (the empty-state item fully; the inbox item sliced down to the remaining Home-badge wiring).
**Reviewer notes:** Accept/decline are fire-and-forget through `viewModelScope` (here the EntryPoint's `rememberCoroutineScope`) — the optimistic row-drop happens inside the repo before the await, so the UI updates even if the user pops the screen, but a *failed* respond won't restore the row until the next `refreshIncomingRequests` (next Profile entry). That matches the inbox's "reconcile on entry" model; flagging in case you'd want a re-add on failure. The Home `FriendsStrip` pending-requests badge is still on fake data — left as the rewritten todo bullet (the count is now trivially available from `observeIncomingRequests().size`, but routing the tap into the Profile inbox is its own small slice). Repo tier fully tested (resolve/order/drop-unresolved/empty/refresh-failure-keeps-last + accept/decline optimistic-drop, 404-as-success, network-failure-keeps-row); section has `@Preview` for populated + empty; no Compose UI test (module has no harness).

## feat(room): add-friend affordance on the at-table player card

**Problem:** The tap-an-opponent player card (`PlayerProfileSheet`) had no way to friend a human opponent — the friend graph's only friending path is a played-with opponent, and you're literally at the table with them, but the at-table surface never exposed it.
**Approach:** Added a `Friend` section to `PlayerProfileSheet` (a `ListSection` with an "Add" / "Sent" `ButtonSecondary`) shown only for a human opponent — `userId != null && !isBot && !seatEmpty && !isMePlayer`; the screen passes `onAddFriend` only for that case, so bots / empty seats / your own self-card never render it. The VM gained `PlayPokerAction.AddFriend(userId)` → `FriendRepository.sendRequest`, mirroring Home's recently-played model exactly: optimistic flip to Sent on tap (tracked in `state.friendRequestSentIds`), kept on a Requested/Accepted result, un-flipped via an internal `FriendRequestFailed` action only when the server rejects (not-played-with / rate-limited / network). A `requestedFriendIds` guard makes a double-tap idempotent. Chose to reuse the Home send-and-flip pattern over inventing a new friend-state query because `FriendRepository` has no "are we already friends" read — the inline Sent state is the honest feedback, same as the Home tile.
**Reviewer notes:** `FriendRepository` is a new dependency of `:features:room:impl` (added to both commonMain + commonTest). No snackbar on failure — the button silently un-flips, matching the Home tile (which also has no failure toast); reviewer flag if you'd want explicit failure copy. The "view full profile" half of the original todo stays blocked on a stranger-profile route that doesn't exist — sliced the bullet down to that and dropped it to P2. Covered by three MP-scenario tests (sends + flips, server-reject un-flips, double-tap idempotent) and two `@Preview`s (Add / Sent); the four other `PlayPokerViewModel` test constructions got the new `friendRepository` param via a new `FakeFriendRepository`. Build + full `:features:room:impl` suite + `:apps:compose:assembleDebug` green.
