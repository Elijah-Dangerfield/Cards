## fix(game): clear stale per-seat action pill on new hand (GAME-33)

**Problem:** The previous hand's action badge (e.g. "Folded") lingered on a seat once the next hand was dealt, so every hand after the first showed a stale, misleading label.
**Approach:** `lastActionBySeat` was only cleared on the `HandStarted` event, which rides a flow independent of the `game_state` snapshot and can lose the race — the new-hand snapshot projects with the old pill map before the event clears it. Moved the clear into the snapshot-application path (`GameStateUpdated`), keyed on the authoritative `handNumber` change, mirroring the pre-fold retirement that already sits there for the same reason. `HandStarted` still clears too (harmless, idempotent). Older/out-of-order snapshots never reach the VM (dropped at the `RemotePokerSession` layer), so the clear only fires on genuine forward hand progression.
**Reviewer notes:** Red-first repro is `PokerScenarioMpTest.newHandSnapshot_clearsStaleActionPill_whenHandStartedLosesTheRace` (fold pill on hand 1, new-hand snapshot with no preceding HandStarted, assert pill gone). Added a `noSeatPill` assertion helper. Sentry CARDS-B1 resolved.

## feat(room): add in-game share button for the room code (ROOM-19)

**Problem:** After a game started the room code was only reachable by tapping the center cards, so mid-game invites were undiscoverable.
**Approach:** Added a share `IconButton` to the play-screen `TopBar`, wired through a new `onShareRoom` callback on `PlayPokerScreen`. Only the MP entry point supplies it (solo bots pass null → no button), and it reuses the exact lobby share plumbing — `Router.shareText` with `RoomInvite.linkForCode` and the same `lobby_in_room_share_message` copy — so the invite URL and text can't drift from the lobby's. New DS `Icons.Share` and a `room_top_bar_share_a11y` string. I chose reusing the lobby string over a new room-namespaced duplicate to keep one source of voice; the alternative (a `room_*` copy) would have been cleaner by naming convention but risked the two invite messages drifting.
**Reviewer notes:** New preview `PlayPokerScreenPreview_MpWithShare` renders the button. QA sub-bullet added under MP-1B. ID ROOM-19 is fresh (prior max was ROOM-18). Sentry CARDS-B3 (owner request) resolved.

## feat(game): review prompt at genuine peaks — net-positive SessionEnd + MP-win trigger

**Problem:** The review-prompt triggers asked at soft spots: bot-mode `SessionEnd` fired on any non-bust leave regardless of outcome, and a real-chip multiplayer win — the strongest positive moment — never asked at all.
**Approach:** Gated the bots-mode `SessionEnd` ask on a net-positive session (`sessionHandsWon > sessionHandsLost`), and added a new `ReviewTrigger.MultiplayerWin` fired from the `MatchOverResolved` handler when the local player won a real-chip MP match (`state.isRealMultiplayer`). Extracted a `requestReviewPrompt(trigger)` helper so all three call sites share the Catching-wrapped path. The eligibility gate (install age + cooldown) in `RealReviewPromptCoordinator` is untouched.
**Reviewer notes:** I defined "net-positive" as hands-won > hands-lost because the VM has no running session chip-net (rebuys make a chip delta ambiguous); a chip-P/L measure would be more precise if we ever track session bankroll. The third sub-part of the original item — deferring the achievement/level-up ask until the celebration sheet is dismissed — is sliced out and left in `docs/todo.md` (rewritten to describe only that gap): it collides with the bot-mode celebration lifecycle and ~3 existing achievement tests, and a mis-wired deferral could strand the pending prompt so it never fires, so I left it for a focused change rather than bundle it here. The original todo item carried no inline ID (GAME items track IDs in commits/cases, not the bullet); prior GAME max is GAME-34.
**Deferred:** MP-35 (matchmaking pairs two humans but game never starts) — investigated but not shipped: root cause spans the client matchmaking-routing state machine (`PublicSearchingViewModel`) and the server auto-start (`startServerDealtTableIfReady` needs 2 *connected* members on socket-connect). ## feat(prog): surface MP-earned achievements as a Home celebration (PROG-13)

**Problem:** Achievements earned during a real-chip multiplayer game were recorded but never shown. A finished real-chip hand renders its result on the felt (the leave-with-winnings countdown), not in a dialog, so the at-table reveal that solo/practice hands get never fires — the only real-chip surface was the `MultiplayerBustDialog`, i.e. you only ever saw an MP unlock if you busted.
**Approach:** Built worker #2's MP-only "pending home celebration" queue. New `AppData.pendingHomeAchievementIds` (account-scoped, cleared in `resetAccountScoped`). At MP hand-end (`PlayPokerViewModel.enqueueUnsurfacedMpUnlocks`) the *surfaced* unlocks (already honouring the silence-pop-ups setting) enqueue **iff** `realChipsAtStake && !humanBusted` — a bust is skipped because the bust dialog already shows them inline (no double-fire), and practice/solo already have the showdown dialog. Home drains it through the existing notification arbiter: new `HomeNotification.AchievementsEarned` (snapshot field `pendingAchievementIds`), reconstructed from the registry into `HomeState.achievementCelebration`, presented on a settled Home and drained (`MarkAchievementCelebrationShown`) on dismiss. The `AchievementCelebrationSheet` moved from `features/room/impl` into `:libraries:ui` so Home and the bot table render the identical DS celebration (no duplication).
**Reviewer notes:** Two judgement calls, both loud here. (1) **Priority:** I slotted `AchievementsEarned` *above* `LevelUp` in the arbiter — the achievement is the concrete thing the player just earned with no other surface, whereas the level-up survives on its watermark and fires on the next settle after the queue drains. Alternative (level-up first) is equally defensible; flip the order in `GetHomeScreenNotification` if you prefer the marquee full-screen moment to lead. (2) **Presentation surface:** a bottom sheet on Home (reusing the bot-mode celebration), not a new routed full-screen like `LevelUpRoute` — it matches how achievements are already celebrated (a sheet) and avoids a new nav route + `List` route-arg NavType landmine. Red-first guard is `PokerScenarioMpTest.mpAchievementEarnedWithoutBust_queuesForHomeCelebration` (+ bust-not-queued + silenced-queues-nothing); Home drain is `HomeViewModelTest.mpAchievements_pendingQueue_presentsOnSettle_thenDrainsOnDismiss` (+ not-until-settled); arbiter priority in `GetHomeScreenNotificationTest`. Process-death *while the sheet is open* re-celebrates on next launch (queue persists until dismiss) — a no-missed-fire bias, better than the level-up's miss-on-crash trade-off. Client `assembleDebug` + iOS `compileKotlinIosSimulatorArm64` + `:apps:server:test` all green. Sentry CARDS-B5 (owner request) resolved.
