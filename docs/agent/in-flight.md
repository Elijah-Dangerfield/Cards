## feat(server): persist GameSession state to room_sessions snapshot table

**Problem:** §B0 P1 — server multiplayer state lived only in `GameSession`'s in-memory `StateFlow`. A server restart mid-hand dropped every active session, players lost their seats / stacks / current betting round, and the architecture-flip decision (2026-05-29, snapshot-only) had no implementation behind it yet. The §B1 reconnect work and the §B3 buy-in / MP-credit items all said "depends on B0," so this was the unblock.

**Approach:** Snapshot-only persistence wired end-to-end. New Flyway `V48__room_sessions.sql` provisions `room_sessions(session_id UUID PRIMARY KEY, room_code TEXT NOT NULL UNIQUE, state_jsonb JSONB NOT NULL, updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW())`; `RoomSessionsTable` mirrors it via the reusable `jsonb(name)` helper the previous worker left behind. New `SessionSnapshotStore` interface + `PostgresSessionSnapshotStore` impl uses the project's `kotlinx.serialization.json.Json` to round-trip `GameState` (same encoder the wire format uses, so round-trip equivalence is already pinned by engine tests). Upsert is two-statement (UPDATE then INSERT-on-zero-rows) inside one Exposed `database.transaction`. Read by code, delete by code, all keyed on `room_code` since §B2's `rooms` table hasn't landed yet — when it does, the column moves to that table and `session_id` FKs to it (a one-line FK migration, called out in the V48 comment).

`GameSession` gains an `onStateChange: suspend (GameState) -> Unit = {}` ctor param invoked **inside the mutex** after every state mutation (start hand, apply intent, request next hand) — the snapshot write must complete before the mutation returns so concurrent intents can't observe out-of-order durable state. Added a `hydrate(state)` API on `GameSession` for the restart-time loader; it bypasses `onStateChange` because re-persisting the snapshot the instant we read it is pointless I/O. Default no-op keeps existing `GameSessionTest` working without ctor churn.

Renamed `InMemoryGameSessionRegistry` → `DefaultGameSessionRegistry` (it's no longer "in-memory" — the in-memory map is a cache backed by the durable store). New `findOrHydrate(code)` API on the registry interface is the post-restart recovery seam — checks the in-memory map first, falls back to `snapshotStore.readByCode`, hydrates a fresh session under the registry mutex on hit. `applyIntent` and `requestNextHand` now route through `findOrHydrate`; `peek` stays in-memory-only (test-shape kept). `end(code)` drops the durable row too. Snapshot write failures log + continue rather than rolling back the in-memory mutation — losing a single un-persisted frame on a server crash is preferable to rejecting a valid intent because the DB hiccupped, and the next successful mutation overwrites the snapshot in full so the DB catches up automatically.

Six integration tests in `PostgresSessionSnapshotStoreTest` against the testcontainer Postgres cover the durable round-trip, single-row-per-session upsert, delete-by-code, and the load-bearing assertion: a fresh registry pointed at the same store *rehydrates the session with the same id, hand number, seats, and betting round* after the original registry is thrown away (the simulated restart). Updated `RoomSocketRoutesTest` + `GameSessionRegistryIntegrationTest` constructor sites and added `RoomSessionsTable` to the schema smoke test.

**Reviewer notes:** Three calls worth pushback if you disagree:
1. **`room_code` column on `room_sessions`** — the todo spec says `session_id UUID PRIMARY KEY` and nothing else. But the registry indexes by 6-char code and §B2 (separate `rooms` table with the code) hasn't landed yet, so I'd have nothing to hydrate against on restart without a `code → session_id` lookup somewhere. Adding the column to `room_sessions` for now keeps B0 self-contained; when B2 lands, the column drops out and `room_sessions.session_id` FKs to `rooms(session_id)` (or wherever B2 puts the link). Alternative: park hydration entirely until B2. Rejected — the §B0 acceptance criterion explicitly demands restart hydration today.
2. **Snapshot persist failures log + continue, don't fail the intent.** "Source of truth" is satisfied operationally because the *next* successful mutation overwrites the snapshot, so the DB catches up on its own. Failing the user's fold because the DB hiccupped is worse UX than losing one un-persisted frame on a crash. If you want strict-fail semantics, the change is two lines — rip the `Catching` wrapper off `persist()`.
3. **Class rename `InMemoryGameSessionRegistry` → `DefaultGameSessionRegistry`.** The old name is now misleading (the in-memory map is a cache, not the source of truth). Three test sites touched. Easy revert if you'd rather defer the rename.

**Deferred:** §B1 reconnect protocol — the snapshot table is the data source it needs but the wire-format work (RequestSnapshot → Snapshot frame translation) is a separate item. §B5 rolling-event-tail stays parked per the decision doc.

## feat(onboarding): wire cards://auth/confirmed deep-link to VerifyEmailRoute

**Problem:** §A P1 remaining — the previous worker shipped the URL-scheme registration + silent auto-verify on resume, but deferred the `NavDeepLink` mapping itself on an open question: `VerifyEmailRoute(val email: String)` required a non-null email arg, so either `cards://auth/confirmed?email={email}` had to ride along (Supabase URL must include it) or the route had to become optional / fall back to session email. Without the mapping, the cold-launch path (user kills app before tapping the link in their inbox, then taps it later) never lands on `VerifyEmailScreen` — Compose nav has no destination registered for the URL.

**Approach:** Picked "make email optional + fall back to current session" over the `?email=` query approach. Three reasons that show up in code review: (1) the Supabase Site URL stays simple — no template variable to manage in the dashboard, just `cards://auth/confirmed`; (2) the session token already carries the email server-side, so a round-trip through the URL is needlessly redundant data; (3) it leaves headroom for an OAuth-confirm variant of the same deep-link later (no email at all in that flow). Concretely: [`VerifyEmailRoute`](features/onboarding/src/commonMain/kotlin/com/cards/features/onboarding/AuthRoutes.kt) now declares `val email: String? = null`; the VM constructor takes `email: String?`, initial state seeds `email = email.orEmpty()`, and an init block fires a new `VerifyEmailAction.ResolveEmailFromSession` whenever the constructor arg is null — that action calls `authRepository.current()`, downcasts to `AuthState.Authenticated`, and copies the session email into state. Resend now reads from `state.email` (not the constructor) and short-circuits if the field is empty, so a deep-launched user with no session email never fires a no-target request. The screen's body Text reads `auth_verify_email_body_no_email` (new resource — "Tap the verification link in your inbox, then return here…") when `state.email.isEmpty()` and falls back to the original templated string otherwise; Resend button is `enabled = !isResending && !isRefreshing && state.email.isNotEmpty()`. Deep-link mapping lands in `OnboardingFeatureEntryPoint.screen<VerifyEmailRoute>(deepLinks = listOf(navDeepLink<VerifyEmailRoute>(basePath = "cards://auth/confirmed")))` — the typed `navDeepLink` overload auto-generates the `?email={email}` query suffix from the route's serializable arg, so a URL with `?email=foo` still binds, but a bare `cards://auth/confirmed` lands with `email = null` and the resolve-from-session path kicks in.

Tests: extended `VerifyEmailViewModelTest` with four new cases — `init_emailNull_resolvesFromSession_andUpdatesState` (Authenticated state with an email → state.email becomes that), `init_emailNull_sessionEmailMissing_keepsEmptyEmail` (anon Authenticated session leaves the field empty so the no-email screen renders), `init_emailProvided_doesNotConsultSession` (route email wins, doesn't get stomped by a parallel session read), and `resend_emptyEmail_noOp_doesNotCallRepo` (the short-circuit guard). The existing 11 tests still pass — `buildVm`'s new `email: String? = sampleEmail` keeps every prior case identical.

**Reviewer notes:** Two judgment calls worth flagging:

1. **Make email nullable vs. query-string carry.** Picked nullable. The query-string approach is the minimal-VM-diff path but means the Supabase dashboard's redirect URL gets a template variable, which is one more place to drift. Nullable + session-resolve keeps URL configuration boring and centralizes the source-of-truth on the auth session. If you'd rather keep the route shape strict, the revert is local: `VerifyEmailRoute(val email: String = "")` instead of `String? = null`, drop the `ResolveEmailFromSession` action, drop the `_no_email` resource. Five-minute revert.

2. **`auth_verify_email_body_no_email` copy.** Wrote it terse — "Tap the verification link in your inbox, then return here and we'll check with our server." Doesn't reference the email address at all (we don't have it). If the human prefers something like "We sent a verification link to your inbox. Tap the link…" that's a one-line resource swap.

Also: the screen-level `LifecycleResumeEffect` fires `AppResumed` on every resume including the deep-link-cold-launch case, so a user who clicked the link, app cold-launches into `VerifyEmailScreen` with a null email, `AppResumed` immediately calls `refreshSession()`, and if `EmailConfirmed` the user lands on Home before the empty-email body ever renders to user eyes. So the no-email body string is mostly a defensive surface for the rare "deep-link to verify but email is genuinely still pending" case. That's the right shape, but worth knowing.

**Deferred:** None. The §A P1 bullet for the deep-link mapping is closed; the four-part todo (URL schemes, NavDeepLink mapping, silent auto-refresh, dropping the "best-effort revival" spec language) is now down to the spec amendment + install_id work, which is tracked under the separate §A P1 install_id bullet.
