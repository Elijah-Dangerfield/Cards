## feat(profile): shrink profile achievement medals to Home size (PROG-7)

## fix(room): reset folded hole-card offset on new deal, not on next turn (GAME-10)

**Problem:** After a silent swipe-fold, the hole cards were flung to `-foldFlightPx` (off the top of the screen) and left there; the only reset was keyed on `swipeFoldEnabled`, which requires `table.isHumanTurn`. So the freshly dealt cards of the *next* hand rendered stuck up top in a "ghost" placement until it was the human's turn again, then snapped down.
**Approach:** Added a second reset `LaunchedEffect(human.holeCards)` in `PlayerArea` that snaps `dragOffsetY` back to 0 on every new deal (the hole cards change identity each hand — the same key already used for `manuallyFacedown`). This decouples the reset from turn state, so the next hand always starts at rest. Left the existing gate-keyed reset in place (it still handles mid-turn spring-back).
**Reviewer notes:** No test — the bug is pure Compose animation state (`Animatable` offset + `LaunchedEffect`), and this module has no Compose UI test harness (`createComposeRule`), only logic/VM tests. Verified by reasoning about the reset condition + the swipe-fold flight path and an `:apps:compose:assembleDebug`. The fix is correct-by-construction: any residual offset from a prior hand is cleared the instant new cards deal.

## fix(auth): offline cold boot reads as "you're offline", not "account needed" (AUTH-11)

**Problem:** An onboarded anon guest who cold-boots offline can't refresh its Supabase session, so the auth gate saw no session and told them "Account needed" — which an onboarded guest reads as "my progress is gone" (Sentry CARDS-6J).
**Approach:** Added `GateReason.Offline` and had `RealAuthGateChecker` inject `AppState`; when an `Account`-gated route is unmet, the session is unresolved, and `appState.isOffline.value` is true, it gates with `Offline` (honest "you're offline, progress is safe, try again online" sheet) instead of `NeedAccount`. Checked *after* the `FinishingSetup` branch so an actively-healing guest keeps its setup copy. `isOffline` is a `StateFlow`, so the check stays a synchronous peek on the navigate path (no suspend). Test-first: `RealAuthGateCheckerTest` now asserts offline+unresolved → `Offline`, and creation-pending+offline still → `FinishingSetup`; the pre-existing online case still → `NeedAccount`.
**Reviewer notes:** This fixes the *message* gap the case is about (misleading copy on gated MP routes). It does **not** make solo bots playable with zero in-memory session offline — solo/practice play isn't auth-gated (`Route(AuthRequirement.None)`), so it already runs offline; the reporter hit the gate on an account-requiring path. If a later cycle wants an offline-restored *live* guest session (for anything that genuinely needs identity offline), that's the deferred half of the acceptance — noted in decisions.md. Compose sheet + copy covered by build; the gate logic has the unit test.
**Deferred:** Persist/restore the guest Supabase session locally for a live-offline identity — the larger half of AUTH-11's "and/or solo bots play works offline" acceptance. Not filed anywhere yet; reviewer please triage whether it wants a backlog item (solo already plays offline, so this is only load-bearing if a future feature needs confirmed identity offline).

## fix(auth): round the native Apple sign-in button to the DS button radius (AUTH-13)

**Problem:** The system `ASAuthorizationAppleIDButton` on the claim/onboarding screens read as a plain rectangle next to the rounder Google button (Sentry CARDS-74). Root cause: `AppleSignInButton.ios.kt` hardcoded `cornerRadius = 16f` with a stale comment claiming `Radii.Button = 16dp` — but `Radii.Button` is now `R800` = 20dp, so the Apple corner was less rounded than every other button.
**Approach:** Added a `Radius.cornerRadiusDp` accessor in the DS (resolves an absolute-corner radius token to its `dp` value via a density-1 measure) and had the iOS Apple button pass `Radii.Button.cornerRadiusDp.value` to the native `cornerRadius` (points ≡ dp for a UIKit view). Now the Apple and Google buttons round from the *same* token and can't drift again. Chose reading the token over re-hardcoding 20f so the next radius change propagates for free.
**Reviewer notes:** iOS-only visual; verified via `:libraries:ui:compileKotlinIosSimulatorArm64`. No unit test — the change is a native corner-radius value with no Compose/logic seam to assert; the Compose fallback already clipped to `Radii.Button.shape` and was left untouched. The `cornerRadiusDp` accessor is only defined for absolute-Dp corners (all `R*` tokens); calling it on `Radii.Round` (percentage) would resolve against `Size.Unspecified` and isn't a supported use — documented in its KDoc.

## feat(mp): leaving a table cashes out synchronously and returns the settled balance (MP-29)

**Problem:** MP money is server-authoritative but the client only learned the settled balance via a separate `sync()` fired at exit, which raced ahead of the server's cash-out commit and returned the pre-settlement balance — and a one-shot `walletReconciled` latch then blocked any retry, so the balance stayed stale ("buy-in still gone after I leave") until the next foreground (CARDS-5R + the 3E/3G/3W/4C/4G/58/5C cluster).
**Approach:** `DELETE /v1/rooms/{code}/me` now cashes out the leaver's stack **synchronously before freeing the seat** and returns `200 LeaveRoomResponse(balance)` (the authoritative post-settlement balance) when a stack settled, else `204`. The settlement decision is extracted into one shared `settleLeaver(...)` helper (`server/game/LeaveSettlement.kt`) that both the REST leave and the socket's `MemberLeft` reap call, so the "defer if all-in in a live hand, else cash out at `stackFor`" rule can't drift; `cashOut` is idempotent so the two firing for the same user settle once. Client: `LeaveRoomOutcome.Success.settledBalance` → `PokerSession.leave(): Long?` → both VMs apply it via `ChipsRepository.setBalance(...)` instead of a speculative sync. Dropped the single-shot reconcile latches (`walletReconciled` in `PlayPokerViewModel` + `LobbyViewModel`); the leave-credit *confirmation* toast keeps a one-shot guard but the reconcile itself may now retry. Involuntary teardowns (match-over / opponents-left / host-closed) keep the `sync()` fallback (now retryable) since they have no REST leave to answer.
**Reviewer notes:** Money change — landed with tests + a loud decision entry (`decisions.md` 2026-06-30) and rejected alternatives. Test-first regression coverage: server `RoomRoutesTest.leave_200_cashesOutSynchronously_andReturnsSettledBalance` (+ the 204-when-nothing-to-settle and idempotent-re-leave cases) over a real `settleLeaver` + `InMemoryTestTableSessionService`; client `RoomRepositoryImplTest.leaveRoom_200_returnsSuccess_withServerSettledBalance`, `PlayPokerViewModelMpLeaveTest.leaveTable_settledBalanceFromServer_appliesDirectly_noSync` (asserts `setBalance` used and `syncCount == 0` — the bug was the racy sync), and `LobbyViewModelTest.leave_realChipRoom_settledBalance_appliesDirectly_noSync`. The existing MP-7/21/14 auto-end sync tests still assert `syncCount == 1` because the fakes return a null settled balance (deferral/failure path), which is the intended fallback. `roomRoutes` grew two params (`gameSessions`, `tableSessions`) — chosen over injecting them into `InMemoryRoomService` so pure room-membership stays decoupled from wallet settlement, matching how `matchmakingRoutes` already wires the same collaborators; verified the whole DI graph via `:apps:compose:assembleDebug` + `:apps:server:test` (full suite green) + iOS compile of the three client modules.
**Deferred:** The involuntary-teardown paths still reconcile via the retryable `sync()` fallback rather than a settled balance folded into the terminal socket frame — filed to `backlog.md` ("Fold the settled balance into the terminal room frame for involuntary teardowns"). Money is safe there; it's a residual pre-settlement-flash window on auto-ends, and the `reconcileWalletAfterGame(settledBalance = …)` param already exists to receive it.
