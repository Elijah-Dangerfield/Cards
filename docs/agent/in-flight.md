# In-flight — Phase 3 workers

## fix(telemetry): drop expected AuthUnready control-flow from Sentry events (ENG-29)

**Problem:** `AuthUnready` is a deliberate typed short-circuit (auth not ready at cold start), but `SentryLogTree` forwarded any error-level throwable straight to `captureException`, so benign `FinishingSetup` / `NeedAccount` signals became Sentry error events on real beta builds (CARDS-9C / CARDS-9M) and masked real errors.
**Approach:** Central filter over the call-site fix. Added an `ExpectedControlFlow` marker interface in `:libraries:core` (with `Throwable.isExpectedControlFlow`), made `AuthUnready` implement it, and taught `SentryLogTree.shouldCaptureEvent` to skip capturing when the throwable is expected control-flow. It still breadcrumbs + buffers locally, so a feedback report keeps the context. One guard protects every future call site, versus chasing each error-level log that might carry an expected short-circuit.
**Reviewer notes:** `SentryLogTree` can't be exercised against the real static `Sentry` object in a JVM unit test (`Sentry.isEnabled()` is false there), so the regression guard tests the extracted `shouldCaptureEvent` decision instead (AuthUnready → false, real throwable/message → true, below-threshold → false). That is the exact branch the bug lived on.

## fix(networking): bind Darwin engine explicitly on iOS HTTP/WS clients (ENG-28)

**Problem:** Fatal iOS crash `IllegalStateException: TLS sessions are not supported on Native platform` (CARDS-94) — first-party `HttpClient { }` factories left the engine to Ktor auto-resolution, which on Kotlin/Native can bind a TLS-incapable native engine; the first HTTPS/WSS flush on a background worker then aborts the process.
**Approach:** Added `platformHttpEngineFactory` (expect/actual) to `:libraries:networking` api — iosMain=Darwin, androidMain=OkHttp, engines exposed as `api` — and routed every first-party iOS client through it: both `NetworkClientImpl` clients (HTTP + the authed WS) and the telemetry `grafanaHttpClient()` OTLP exporter. One shared, explicit engine seam beats sprinkling `HttpClient(Darwin)` per callsite and stops any future engine-less client from regressing (the seam is the single place engine choice lives). Chose Darwin as the iOS binding because it is the only Kotlin/Native engine with TLS.
**Reviewer notes:** The actual crash is iOS-runtime-only and can't be reproduced in the worker sandbox; guard is a per-platform binding assertion (`iosTest` → Darwin, `androidUnitTest` → OkHttp) plus green Android `assembleDebug` and `compileKotlinIosSimulatorArm64`. The case flagged a *possible* stray transitive `ktor-client-cio` on the iOS graph as an alternative cause; a static grep finds CIO only in `:apps:server` (JVM), so the engine-less auto-resolution is the confirmed first-party path — but if a transitive dependency ever drags CIO onto the iOS binary, that's a separate lockdown (see Deferred).
**Deferred:** Auditing the *full* linked iOS dependency graph (not just first-party Gradle files) for a transitive `ktor-client-cio` — needs the iOS binary's resolved klib graph, not doable from source alone. Left as an inline note here for the reviewer to triage; nothing filed yet.
