# In-flight

## fix(lobby): full-screen retry state for a failed room creation

**Problem:** When `rooms.createRoom(...)` failed, the lobby left the user on the "Setting up your table…" spinner with a small red error line and no way forward — the create surface had already popped (CARDS-2E).
**Approach:** Added a `LobbyState.createError` derivation (a Create* error with no room and not mid-create) that drives a new full-screen `CreateErrorContent` in `LobbyScreen` — title + message + a primary **Try again** (re-fires `LobbyAction.CreateRoom`, which the VM can do because it still holds the create args) + a secondary **Go back**. Chose in-place retry over routing back to the popped `PrivateCreateRoute` because the args are already captured and retry is the common intent; the join-error fix (CARDS-28) routes back only because a bad *code* must be re-typed, which doesn't apply to create. Aligns visually with `BlockingErrorScreen`.
**Reviewer notes:** Retry shows the spinner again while in-flight (`createError` goes null when `creating` flips true) then re-renders the error if it fails again — intended. Not exercised by a Compose UI test (none in this module yet); covered by VM-level tests on the `createError` derivation. The "room not found" join treatment stays inline as before — only the create paths get the full-screen state.

## test(integration): pin the two-client same-nonce dedup race over the wire

**Problem:** The last open Round 2 fan-out box in `testing-plan.md` — `twoClientsRace_sameIntent_serverDedupesViaNonce` — had no integration-tier coverage; only single-client nonce idempotency was pinned (unit tier).
**Approach:** Added `NonceRaceTest` + a `GameplaySession.submitWithNonce(intent, nonce)` helper so a test can drive an explicit shared nonce. Realized the race as the **same** acting client resending one nonce twice concurrently, NOT two distinct users: the server records a nonce only for an *accepted* intent (after seat-ownership validation), so a second user's duplicate is a legitimate wrong-seat rejection that never burns the nonce — making "two distinct users, same nonce → both accepted" not a real contract. The same-actor resend is the actual reconnect-resend idempotency case, so that's what the box should mean; documented this reasoning in the test KDoc and the testing-plan note. Verified non-flaky 5x under `--rerun-tasks`.
**Reviewer notes:** I reinterpreted the plan's box wording (it said "both clients ... same nonce") to the same-client resend because the two-distinct-user version is provably flaky against the real server (confirmed: it fails ~2/3 when the non-owning user's frame is processed first). If you'd rather the box stay open for a genuine two-user variant, the realistic one would require the server to dedup *before* actor validation — a server change, not a test. Flagging the wording reinterpretation for your call.

## fix(debug): make the right-edge feedback swipe win inside scroll views

**Problem:** The debug right-edge swipe to open feedback (CARDS-Y) often took several tries inside a scroll view — a nested vertical scroller swallowed the gesture in the Main pointer pass before the edge detector saw it.
**Approach:** Moved `debugRightEdgeSwipe`'s `awaitFirstDown` / `awaitPointerEvent` to `PointerEventPass.Initial`, so the detector observes the raw deltas before any child scroll container consumes them. It still never *consumes* — a predominantly-vertical drag in the edge strip keeps scrolling (the `abs(dx) > abs(dy)` gate only fires the trigger on a leftward travel). Standard fix for "edge-swipe loses to a nested scrollable."
**Reviewer notes:** Debug-only (`enabled=false` in release). No automated test — it's a pointer-pass gesture behaviour and this app module has no Compose UI test harness; needs a device tester to confirm the scroll-view case. Touches Android + iOS identically (the pointer API is Compose-MP common).

## feat(matchmaking): read-only candidates endpoint for the chooser flow

**Problem:** Find auto-joins the first server match; the owner-approved chooser flow (let the user pick which qualifying table to join) had no server surface to list candidates without seating anyone.
**Approach:** Added `RoomService.findPublicCandidates(...)` (the same eligibility predicate + most-humans-first ordering as `findOrJoinPublic`, extracted into a shared private `matchmakingCandidates` helper so the two never drift) and a `GET /v1/matchmaking/candidates?minBuyIn=&maxBuyIn=` route returning `MatchmakingCandidatesResponse`. Chose a separate read-only GET over overloading `find` because the chooser browses before committing — it must not create or seat. The endpoint reuses `find`'s exact validation (range/bounds/affordability fence) and the pre-mutex blocked-pair read. Sliced the todo to client-only remaining work.
**Reviewer notes:** Read-only and side-effect-free — the authoritative debit is still the sit-down escrow when the user picks a table, so the affordability check here is the same advisory fence `find` uses. Candidates include a table the caller is already seated in (per the interface KDoc) since the chooser can show "you're already here"; that falls out of the shared predicate naturally. Tested at both the service tier (`InMemoryRoomServiceTest`: in-range/out-of-range/blocked/private+full/ordering/empty) and the route tier (`MatchmakingRoutesTest`: lists-without-joining/empty/blocked-filtered/400s/401).
**Deferred:** The client chooser screen + `PublicSearchingViewModel` "matches" phase — left as the rewritten `docs/todo.md` bullet (client-only now).
