## fix: replay the terminal room-close to a late subscriber

**Problem:** The B6 hot-flow sweep ("audit remaining MP flows for the late-subscriber symmetry rule") turned up one genuine gap: `RemotePokerSession.roomClosed` was a `MutableSharedFlow(extraBufferCapacity = 1)`, not `replay = 1`. A terminal close fanned out by `collectConnection` before the VM's sibling-launched `roomClosed` collector attaches is dropped — `extraBufferCapacity` with `replay = 0` evicts a buffered value once it has no subscriber, it never replays — so a close racing session bootstrap would leave the user on a Disconnected banner with nothing popping the screen.

**Approach:** Changed `_roomClosed` to `MutableSharedFlow(replay = 1)`. The reason is terminal + idempotent (the VM collects it once to pop the screen), so replaying it to a late collector is exactly right. Added `roomClosed_replayReachesLateCollector` (subscribe *after* the close emits, assert the reason replays) — it fails on the old `extraBufferCapacity = 1` and passes on `replay = 1`, so it both proves the bug and guards the fix.

**Reviewer notes:** Completes (and removes) the "audit remaining hot flows" todo. The rest of the swept flows are already correct: `gameStateFlow`/`connectionState` (session) and `activeRooms` (`RoomRepositoryImpl`) are `StateFlow`s (implicit replay-1, late subscriber always gets the current value); `events` is `replay = 16` with an existing late-subscriber test; `emoteBlasts` is intentionally `replay = 0` (a live reaction must not replay stale blasts); the socket-level `connection`/`gameplayFrames` have their own replay-reaches-late-collector tests. So `roomClosed` was the lone real gap. Full `:features:room:impl` unit suite green; `:apps:compose:assembleDebug` green.

## feat: friend graph — server schema + endpoints (P0)

**Problem:** The friend graph (the load-bearing system behind the friends strip, requests inbox, and recently-played-with add-friend) had no server: tables, endpoints, repository all missing.

**Approach:** Built the unordered-pair model the todo specified. `V61__friend_relations.sql` is one row per `{x,y}` with `user_a` < `user_b` (a DB `CHECK` enforces the canonical order), `state ∈ {requested,accepted,blocked}`. **Key direction call:** the canonical pair can't carry who-did-what, so I added an `acted_by` column (the spec listed only the four base columns) — it holds the request *sender* / the *blocker*, which is what makes "list my inbound requests" expressible ("a `requested` row I'm a member of whose `acted_by` is the other member"). The alternative — two directed rows per pair — breaks the "row unique regardless of direction" requirement the spec explicitly states, so a single canonical row + a direction marker is the only design that satisfies both. `PostgresFriendRepository` canonicalises by comparing the lowercase-hex UUID string, which orders identically to Postgres's `uuid <` operator (so Kotlin and the `CHECK` always agree). Endpoints: `POST /v1/friends/requests` (rate-limited via a new `FRIEND_REQUEST_LIMIT`; a mutual request auto-accepts), `POST /v1/friends/requests/{id}/accept|decline|block` ({id} = the other user's UUID), `GET /v1/friends`, `GET /v1/friends/requests`. Block dominates: it overwrites any existing relation and rejects further requests/accepts. Wired the repo into the DI graph + the `DELETE /v1/me` cascade.

**Reviewer notes:** Two deliberate calls worth a glance. (1) **`acted_by` column** — see above; it's the one schema addition beyond the spec's four columns and the whole inbox/block direction model hangs off it. (2) **Rate limit is per-IP/hour (50/hr), not per-day** — the spec said "requests/day" but every existing bucket in `RateLimits.kt` is per-IP/hour and the file header documents the per-user-vs-per-IP caveat, so I matched the house style rather than introduce a lone daily bucket; 50/hr still caps daily abuse. (3) **Mutual-request auto-accept** — if B requests A while A had already requested B, the second request completes the friendship (returns `accepted`) rather than stacking a second pending row; this avoids a stuck double-request and is the natural outcome, but it's a behavior the spec didn't pin. All three are cheap to change if the reviewer disagrees. Tests: `PostgresFriendRepositoryTest` (11 cases, real Postgres — canonical dedup, lifecycle, mutual-accept, block dominance, per-user delete), `FriendsRoutesTest` (13 cases — outcome→status mapping, JWT gating, malformed-id 400s), `DatabaseSchemaTest` extended. Full `:apps:server:test` green with Docker present (all three suites ran, 0 skipped).

## feat: record recently-played-with opponents server-side (P0)

**Problem:** The recently-played-with shelf (and the friend-request gate that depends on it) had no server record — nothing tracked which humans a user shared an MP hand with, so `RecentlyPlayedWithStrip` was fake and `POST /v1/friends/requests` couldn't be gated.

**Approach:** Piggybacked on the exact hand-completion callback that already feeds `hands_finished` + server-witnessed achievements. `V62__recently_played_with.sql` is a *directed* `(user_id, opponent_id, last_played_at)` table — both directions written per hand, so a user's shelf is a plain `WHERE user_id = me ORDER BY last_played_at DESC` with no canonicalising (chose directed-rows over the friend graph's canonical-pair model because recency is per-viewer and "newest-first for me" falls straight out of the timestamp; the pair model would need a join to figure out which side is "the other guy"). `PostgresRecentOpponentsRepository` upserts two-statement (UPDATE-then-INSERT) like `PostgresSessionSnapshotStore`, bumping `last_played_at` so a re-play dedups to one row. `DefaultGameSessionRegistry.recordRecentOpponents` sources the human set from `HandOutcome.perHuman.keys` (bots are absent there by construction) and records every ordered human pair, best-effort `Catching`. `GET /v1/recent-opponents?limit=N` returns bare ids newest-first — same shape as `GET /v1/friends`; the client resolves profiles. Wired into the DI graph, the `installApp` routes, and the `DELETE /v1/me` cascade (clears both directions).

**Reviewer notes:** The repo also exposes `hasPlayedWith(me, other)` — unused this commit, it's the seam the next commit's friend-request gate consumes (kept here so the repo + its test land together). Bots-excluded relies entirely on `perHuman` never containing a bot id (documented invariant on `HandOutcome`); a `finishedHand_doesNotRecordBots` registry test pins it. Tests: `PostgresRecentOpponentsRepositoryTest` (6 cases, real Postgres — recency order, dedup+bump, limit, per-user scoping, hasPlayedWith, both-direction delete), `RecentOpponentsRoutesTest` (5 cases — serialization, limit default/clamp/explicit, 401 gating), two new `GameSessionRegistryIntegrationTest` cases (both-direction record + bot exclusion), `InMemoryRecentOpponentsRepository` double, `DatabaseSchemaTest` extended.
