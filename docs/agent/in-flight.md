## fix(ui): round dialog bottom corners with emoji bubble

**Problem:** The `docs/todo.md` "dialog emoji bubble: bottom corners render as a straight line" bug — emoji-bubble dialogs render with flat bottom corners. Root cause was `NotchedSheetShape` (shared between dialogs and bottom sheets): its bottom edge is hard-coded square via `lineTo(w, h)` / `lineTo(0f, h)`, with a comment explicitly saying "this is a bottom sheet; the bottom is off-screen anyway." Dialog reuses the same shape and renders all four corners on screen, so the assumption breaks.
**Approach:** Added an opt-in `bottomCornerRadius: Dp = 0.dp` parameter to `NotchedSheetShape` and a matching pair of `arcTo` calls in `createOutline`. Default 0 preserves existing sheet behavior (no caller diff in `BaseBottomSheet`). `Dialog`'s notched-surface call passes `bottomCornerRadius = DialogCardCornerRadius`, the same value already used for the top, so all four corners match. Considered the alternative of branching the shape into two classes (`NotchedDialogShape` / `NotchedSheetShape`) but the only difference is a single parameter; a forked class would duplicate ~90 lines of geometry math for one boolean. Kept as one shape, two callers.
**Reviewer notes:** Geometry change — eyeball the existing `PreviewDialog_ChipBubble` and any other emoji-bubble dialog preview in the Studio pane; bottom corners should now match the top radius. Bottom-sheet visuals must remain unchanged (default param). The math for the two new bottom-corner `arcTo` calls is the standard mirror of the top corners; clamped to half of size.width / size.height so a tiny container can't invert the corners.
**Deferred:** None.

## feat(server): welcome-week daily chip grant on wallet contact

**Problem:** product-spec.md §4.1 promises 500/day × 7 silent welcome-week grants for the first week post-install, with no claim prompt, no streak, no "you missed yesterday" copy. Nothing in the codebase implemented this. The TODO entry described it as "server-side scheduled grant tied to account creation timestamp; client just observes the wallet delta."
**Approach:** Implemented lazily on every wallet contact (GET `/v1/me/wallet`, POST `/v1/me/wallet/sync`) rather than via a separate cron, mirroring the soft-bust-protection pattern that already lives in the same routes. `maybeApplyWelcomeWeek` computes elapsed whole days since `wallet.createdAt` (clamped to `WELCOME_WEEK_DAYS - 1 = 6`) and iterates day 0..lastEligibleDay, applying `WELCOME_WEEK_DAILY_GRANT = 500L` via `WalletRepository.apply` with one stable key per (user, day): `welcome_week_day_{N}_v1`. Replay detection in `apply` collapses already-granted days to a no-op, so the cost past day 6 is at most 7 idempotency-key reads per request — cheap. Ordering: welcome week runs *before* the sync batch and *before* bust protection in `GET`, so chips a user is owed land before their next debit and before any zero-balance bust check (zero-bust + welcome chips is rare but possible if a user spends their starter on day 0). Threaded `Clock` through `walletRoutes(...)`; `Application.kt` wires `component.provideClock()`. **Executive call:** chose lazy-on-contact over a cron because a cron requires cross-user fanout, a scheduling story, and a "where's the cron" failure mode. The two approaches are observationally identical from the user's perspective (the only divergence would be a user who *never opens the app*, in which case chips they can't see don't matter).
**Reviewer notes:** Existing wallet/bust tests would have changed shape if welcome-week ran by default in their setup (every test would see +500 on day 0), so `FakeWalletRepo` got a `welcomeWeekEnabled` flag defaulting to `false` — when off, every day's idempotency key is pre-seeded as already-applied so the route's pass is a no-op. New welcome-week tests opt in via `welcomeWeekEnabled = true` and supply a controllable `walletCreatedAt` + `Clock`. Six new tests cover: day-0-on-first-contact, missed-days-on-skip, seven-day-cap, idempotency-across-repeated-calls, no-user-message-queued, and welcome-applies-before-sync-batch (so a small debit doesn't fail on insufficient chips when the user is owed the welcome). No `:libraries:cards` client constants — the spec calls this "client just observes the wallet delta," and the existing wallet sync pipeline does exactly that. Server-only slice.
**Deferred:** None.
