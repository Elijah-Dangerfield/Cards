## fix(room): defer review ask past celebration sheet (GAME-1)

**Problem:** In bot mode a hand that unlocks a rare+ achievement (or levels the player up) fired the OS review prompt immediately at hand-end, stepping on the achievement-celebration reveal.
**Approach:** `maybeRequestReviewPrompt` now resolves the trigger and, when a celebration sheet will show (bots + surfaced unlocks), stashes it in `pendingReviewTrigger` instead of firing. A new `CelebrationDismissed` action (fired from `AchievementCelebrationSheet` `onContinue`) flushes the stash. When no celebration shows (popups silenced / no surfaced unlock / MP), the ask still fires immediately at hand-end. Considered gating on the trigger alone, but a *common* achievement also renders the sheet while only firing a LevelUp ask, so the deferral keys off "will the sheet show," not the trigger's rarity.
**Reviewer notes:** The level-up haptic still fires at hand-end (inside `resolveReviewTrigger`), only the review *ask* is deferred — that felt right (haptic isn't a visual step-on) but is a judgement call. If a player leaves the table without dismissing the sheet, the stashed ask is simply dropped (LeaveTable has its own SessionEnd ask). Three existing review-wiring tests were rewritten to assert deferral + flush; added `handEnded_unlockWithPopupsSilenced_requestsReviewPromptImmediately` for the immediate path. No QA entry — the OS review prompt is throttled/invisible to a device tester.

## feat(room): fill the seatless spectator's blank player area (GAME-2)

**Problem:** A mid-hand joiner holds no seat, so `PlayerArea` returned early and the action bar collapsed, leaving the bottom half of the felt blank — it read as a stuck/broken table, with only a small "you'll be dealt in next hand" caption up top.
**Approach:** The server/projection side already handles seatless spectating (`waitingToBeDealtIn`, scrubbed seats, next-hand queue — all covered by `searcherJoiningAPlayingPublicTable_...`), so this is client-render-only. In `ActiveTable`, when `table.waitingToBeDealtIn`, render a new `SpectatingSeatPlaceholder` ("You're spectating this hand") in place of the empty PlayerArea + action bars. Seated players (OpponentsRow) + board already render, and the top status caption stays — so the joiner now sees the full table plus a clear reason the bottom isn't their hand. Directional call: filled the void with a centered notice rather than, say, a dashed "your seat" outline or a live seat preview — simplest thing that reads as intentional; reviewer can upgrade the treatment.
**Reviewer notes:** UI-only branch gated on the existing `waitingToBeDealtIn` flag; coverage is the updated `PlayPokerScreenPreview_WaitingToBeDealtIn` preview (no unit test — it's a pure layout branch). Copy run through the app's voice (plain, contraction, no filler). QA sub-bullet added under MP-2.

## fix(onboarding): route a returning guest to Home, no stale level-up (AUTH-28)

**Problem:** An install with a live anonymous-guest session (already level 2) that reached the onboarding route was treated as a new user, dropped through pick-identity/starter-grant, and shown a level-up congrats for progression it already had.
**Approach:** Root cause is `OnboardingViewModel.handleResolveEntry`: it only recognised an authed *non-anonymous* session (the verified-email bounce → PickIdentity) and let a live *anonymous* guest fall through to the Welcome landing, where "Continue as guest" re-onboarded them. Guest creation is deferred (a genuinely new user is Unauthenticated at this point), so a live anonymous session here can only be a prior guest whose `hasUserOnboarded` flag was lost. Added that branch: adopt `hasUserOnboarded=true` and navigate Home, logging `auth_selected returning=true`. Not re-onboarding is what removes the stale level-up (Home's watermark-seed already suppresses a celebration for a level a fresh session already holds; the bug only appeared because re-onboarding churned that state). Considered fixing it downstream in the Home level-up arbiter, but the returning guest should never enter new-user onboarding at all, so the entry router is the right seam.
**Reviewer notes:** Red→green: `init_returningAnonymousGuest_skipsOnboarding_navigatesHome` fails on the pre-fix router (no NavigateToHome) and passes after. `isVerifiedNewAccount()` was folded into the single `authRepository.current()` read in `handleResolveEntry` (only caller). Timing caveat unchanged from the prior code: routing keys off `current()`, so if the anon session is still bootstrapping at ResolveEntry the guest still lands on Welcome — same constraint the verified-email branch already lived with; not awaited to avoid hanging the Welcome landing for real new users. QA `ONB-20` added. Sentry CARDS-AS resolved.
