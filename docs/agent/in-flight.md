## fix(profile): unclip lock badge on locked avatar tiles

**Problem:** Locked avatar tiles in Edit Profile's pack picker had the bottom-right of the 🔒 chip cut off — the badge sat inside the `BoxWithConstraints` that owned the circular `.clip(CircleShape)`, so its corner was carved away with the tile background.
**Approach:** Wrapped `AvatarTile` in an unclipped outer `Box`, moved the existing `BoxWithConstraints` (with the circle clip + background + border + click) inside it, and overlaid the lock badge as a sibling at `Alignment.BottomEnd` of the outer box. The inner circle still clips the emoji + 0.35 alpha overlay so the dim-locked treatment is unchanged. Dropped the previous 4dp inner padding on the badge — it was carving the chip away from the corner specifically to dodge the clip, no longer needed.
**Reviewer notes:** Visual verification was build-only (`:apps:compose:compileDebugKotlinAndroid` clean). The pack picker doesn't currently have its own `@Preview` to eyeball — first locked-pack render on device will confirm.

## fix(home): decouple welcome dialog from wallet hydration

**Problem:** On a fresh install with slow network, the welcome dialog never appeared. `WelcomeGate.payload()` required `chips != null` alongside profile / first-session / not-already-seen, so a delayed `/v1/me/wallet` round-trip silently swallowed the welcome.
**Approach:** Dropped the chips check from `WelcomeGate.payload()`. Chips still ride the gate as a snapshot (logged for diagnostics, included in the payload when present) but no longer block the predicate. Plumbed `Long?` through `WelcomePayload` → `WelcomeDialogRoute` → `WelcomeDialog`. The dialog renders a `ChipRevealPlaceholder` (chip coin + em-dash, same layout as the animated reveal so the dialog doesn't jump) when chips are null; the live `AnimatedChipReveal` is unchanged for the typical case. Added a third `@Preview` for the placeholder state plus three VM tests pinning the new gate semantics — first-ever-session with null chips fires + persists hasSeenStarterWelcome; returning session and fallback profile both don't fire.
**Reviewer notes:** The dialog does NOT live-update if chips hydrate after navigation — the route param is static. Per the todo's "graceful chip placeholder (or fetch chips lazily after open)" framing, the placeholder route is acceptable since the user sees the real balance on Home immediately after dismissal. Live in-dialog observation would require lifting `ChipsRepository` into the dialog destination scope (sibling to the home screen scope today); flagged as a follow-up rather than done here.
**Deferred:** Live chip updates inside the welcome dialog after the route opens with null chips — nothing yet (reviewer please triage). The placeholder is the user-visible state in that narrow window; a live observer in the dialog would need either a small dialog-scoped VM or `ChipsRepository` injected into the entry-point. Worth doing only if device QA shows the placeholder feels long enough to notice.

## feat(networking): add NetworkClient.authedCall helper

**Problem:** Every repo that talked to an authenticated endpoint hand-rolled its own try/catch around `networkClient.authenticatedClient.post(...).body()` (or wrapped it in an ad-hoc `Catching { }`), each with bespoke logging and no shared classification of what kind of failure happened (timeout vs http-status vs unknown). Onboarding new repos meant copy-pasting the pattern.
**Approach:** Added `suspend fun <T> NetworkClient.authedCall(description: String, block: suspend (HttpClient) -> T): Catching<T>` in `:libraries:networking` (new file `NetworkCall.kt`). The helper hands the authenticated `HttpClient` to the block, wraps in `Catching` (preserving `shouldNotBeCaught` semantics so cancellation propagates), and emits a structured warn-level failure log with a classification tag (`timeout` / `http <status>` / exception class name) prefixed by `description`. Migrated `InventoryRepositoryImpl.doSync()` as the reference implementation — POST is straightforward, has existing sync test coverage that exercises both success + failure paths, and the previous repo-local `syncLogger.w("Inventory sync failed; pending rows stay Pending.")` was redundant once the helper started logging failures, so it was dropped. Existing `InventoryRepositoryImplSyncTest` (success cases + the explicit `Network failure → returns Result.failure` case) still passes unmodified.
**Reviewer notes:** Helper is at extension level (not interface method) so adding it doesn't churn every existing fake. No new test file for the helper itself — its behavior is exercised end-to-end via the existing `:libraries:cards:impl:test` sync suite, and the public contract (returns Catching, logs on failure, propagates cancellation via `shouldNotBeCaught`) is one screen of code. Deliberately did NOT add automatic backoff retry — POSTs may not be idempotent, so retry is a callsite decision. Callers compose `withBackoffRetry { authedCall(...) { ... } }` if they want it.
**Deferred:** Migrating the remaining repos (`ChipsRepositoryImpl`, `RoomRepositoryImpl`, `EquipmentRepositoryImpl`, `UserMessageRepositoryImpl`, `IdentityRepositoryImpl`'s networked paths) is mechanical and explicitly framed as follow-up in the updated todo bullet — left there so subsequent workers can opportunistically migrate one at a time as the surrounding area opens up. Not done in this commit to keep the slice tight + reviewable.

## refactor(ui): scale EmojiBubble body gap with bubble size

**Problem:** `EmojiBubbleDefaults.BodyGap` was a hard-coded `Dimension.D400` (10dp). The bubble's `Size` is conceptually a tunable knob (the todo's TopAccessory rework anticipates exposing it per-caller), but the body-gap below didn't scale — a 200dp bubble would still get 10dp of breathing room and crowd whatever sits under it.
**Approach:** Replaced the constant with `fun bodyGapFor(size: Dp): Dp = (size * 0.10f).coerceAtLeast(D300)` on `EmojiBubbleDefaults`. At today's 100dp size this still resolves to 10dp so dialogs/sheets are visually unchanged; if a future caller passes a smaller size the floor catches it, and larger sizes get proportionally more room. The `0.10` fraction matches today's 10dp/100dp ratio so the default case is byte-equivalent. Only call-site (`EmojiBubble` itself) updated to pass `size` through the function.
**Reviewer notes:** Pure-internal refactor — no public API surface changed. `EmojiBubbleDefaults.BodyGap` was only referenced by `EmojiBubble.kt` itself (grepped to confirm), so removing it doesn't ripple. Visual verification was build-only (`:libraries:ui:compileDebugKotlinAndroid` clean); existing dialog/sheet previews unchanged at default size.
**Deferred:** The broader TopAccessory generalization (the parent todo bullet) is intentionally untouched — that's a much bigger refactor of `Dialog` / `BottomSheet` to take a sealed `TopAccessory` instead of an emoji-specific one. Left for a dedicated cycle.

## fix(nav): lift cross-tab nav into Router.switchTab to unstrand tabs

**Problem:** A `router.navigate(ShopRoute(...))` from inside the Profile tab (Edit Profile → "Get in shop") put Shop on top of the Profile-tab stack rather than the Shop-tab stack. After closing the purchase sheet, tapping the Profile tab in the bottom bar did nothing — the bottom-bar's `popUpTo(HomeRoute) { saveState = true }` + `restoreState = true` recipe saved the Profile-stack-rooted Shop under Shop's key and then tried to restore a nonexistent Profile state.
**Approach:** Picked Option 1 from the todo's fix sketch — added `Router.switchTab(route: Route)` and implemented it in `DelegatingRouter` using `graph.findStartDestination().id` as the popUpTo target (matches the bottom-bar's `popUpTo(HomeRoute::class)` semantics without leaking the feature route into the navigation library). Replaced the inline bottom-bar `navController.navigate { popUpTo(HomeRoute::class) { saveState = true }; launchSingleTop = true; restoreState = true }` block in `App.kt` with `router.switchTab(route)`. Routed the two cross-tab callsites I found through it: `ProfileFeatureEntryPoint`'s `onNavigateToShop` (the bug site) and `HomeFeatureEntryPoint`'s `onTapCash` (which had been using `clearBackStack = true`, an even more aggressive footgun that nuked Home's saved state on every chip-badge tap). Updated `NoopRouter` in `FeedbackViewModelTest` to satisfy the new interface method.
**Reviewer notes:** No nav tests exist in `libraries/navigation` — verification was build + `:features:profile:impl:test`. Real-device confirmation needed for the acceptance criteria: Profile → Edit Profile → Get in shop → close sheet → tap Profile tab lands on Profile (not stuck). Same for Home → chip badge → Shop → tap Home returns to Home with state preserved. `switchTab` uses `popUpTo(graph.findStartDestination().id) { saveState = true }`, which is the standard Compose-Navigation recipe — should behave identically to the previous `popUpTo(HomeRoute::class)` since HomeRoute is the start destination once onboarding completes.
**Deferred:** Three onboarding-flow `router.navigate(HomeRoute(), clearBackStack = true)` callsites in `OnboardingFeatureEntryPoint` look superficially similar but are intentionally different — they're the *entry* into the tab system from onboarding, where `clearBackStack` correctly drops the onboarding screens. Left as-is.

## fix(room): defer swipe-fold flight animation until user confirms

**Problem:** On a first-time swipe-fold, the gesture's `onDragEnd` always animated the cards ~400dp off-screen *and* called `onSwipeFold()`, which opened the confirm dialog. Tap Cancel and the dialog dismissed but the cards stayed off-screen because nothing reset `dragOffsetY` — the `LaunchedEffect(swipeFoldEnabled)` reset only fires when the gate flips, and the player is still on-turn after a cancel. Acked (silent-fold) path was fine.
**Approach:** Picked Option 3 from the todo's fix sketch ("don't commit off-screen until confirm") with the "(or sprung back)" variant. Added a `silentSwipeFold: Boolean` parameter to `PlayerArea` threaded down from `PlayPokerScreen` via `ActiveTable`, wired to `state.swipeFoldGestureAck`. When the gesture commits past threshold: if acked → existing flight animation + `onSwipeFold()` (silent fold); if not acked → spring cards back to rest + `onSwipeFold()` (opens the dialog). The dialog is now the visual moment for first-time users; cancel leaves cards already at rest, confirm hands off to the engine's folded-state alpha treatment via the normal Fold intent.
**Reviewer notes:** Gesture visuals aren't unit-testable in commonTest — verification was build + existing `:features:room:impl:test` suite (`PlayPokerViewModelTest.appCacheEmission_mirrorsSwipeFoldGestureAck` and friends still pass). The acked path is unchanged so device behavior for users who've already dismissed the dialog stays identical to today. First-time-user behavior on device is the new state to eyeball.
