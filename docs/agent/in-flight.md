## feat(server): allowlist client-grantable achievements + 403 server-witnessed

**Problem:** `POST /v1/me/grants/achievement/{id}` resolved through `AchievementRewards.mapping` and 204'd anything not in it. Accidentally safe today (only two ids map, none are server-witnessed yet), but the first future server-witnessed achievement added to that map would let any authed client self-grant it.
**Approach:** replaced the single `AchievementRewards` object with a `ClientGrantableAchievements` policy that resolves to `Grant(productId) | ServerWitnessed | Unknown`, and split the route into 200 / 403 / 204 accordingly. The policy is a class with a `Default` companion (production wiring stays a one-liner), and `grantsRoutes` takes it as an injectable param so the 403 branch is testable without polluting prod data. `serverWitnessed` is empty today by design — it's the slot future PvP / league achievements drop into. Also deleted the dead `PlayPokerEvent.ShowAchievementUnlock` (no collector) and the never-fired `HapticKind.AchievementUnlock` / `SoundKind.AchievementChime` enum entries it would have triggered — unlock callouts live in BustDialog / ShowdownDialog by product call.
**Reviewer notes:** `ClientGrantableAchievements` is a class (not object) so tests can build one with `serverWitnessed` entries; `Default` is the prod singleton. The 403 message ("granted server-side; clients can't self-grant it") is reachable but never fired today — first user to see it is whoever ships a server-witnessed achievement and bumps an old client into hitting the route. The dropped enum entries were genuinely unreferenced (grep clean across the repo).

## feat(server): seed starter inventory atomically in profile creation

**Problem:** every `GET /v1/me` re-fired `recordEarnedGrant(felt_default)` so new users had at least one row in My Items — cheap but conceptually wrong (the earned-grant pathway is for achievement rewards, not "you signed up"), and the only starter row was the felt; no default card back, no default emoji-blast pack.
**Approach:** introduced `StarterInventory.productIds` (`felt_default`, `cardback_default`, `emoji_pack_starter`) and seed all three inside `PostgresProfileRepository.findOrCreate` in the same outer transaction as the profile insert, using `insertIgnore` for idempotency. V18 migration adds the two new catalog rows (both `unlock_only = TRUE`) and backfills every existing profile with all three starter rows (`ON CONFLICT DO NOTHING`, so the historical felt_default rows keep their original `purchased_at`). Dropped the `/v1/me` grant block + the now-unused `clock` parameter from `meRoutes`. Client `EmojiPackCatalog` learned the new starter pack's emoji set (👋 👍 🎉 😀) so owning the row actually surfaces emojis in the in-game tray rather than being inventory-decoration. `EmptyInventory` test stub in `MeRoutesTest` now throws on `recordEarnedGrant` so a regression that re-introduces the grant fails loudly.
**Reviewer notes:** picked the starter emoji set (👋 👍 🎉 😀) as a friendly neutral default — none of the existing packs use them, so no overlap. Card-back surface needed no client change (the renderer already falls back to `CardBackStyle.Default` blue for unknown ids, and `cardback_default` matches that fallback). `PostgresProfileRepository` now reaches across to `InventoryTable` directly inside its transaction — this is the path the todo explicitly carved out (decoupling via injection is on the backlog under "ProfileRepository → InventoryRepository import"); for now atomicity wins over cohesion. Test coverage: two new integration tests in `PostgresProfileRepositoryTest` lock in seeding and idempotency.
**Deferred:** seat-bottom emoji-pack-owned indicator at the table tray (only matters once the pack ID list changes again); nothing yet — reviewer please triage.
