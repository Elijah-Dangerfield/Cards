## feat(auth): route the server's 403 ban envelope to a blocking access-denied screen

**Problem:** Server returns `403 {reason, until, appealUrl}` for banned users (shipped previously), but the client never parsed the envelope — a banned account hit `RefreshFailureKind.AuthRejected` via the 403, got booted to the SessionExpired screen, and "Retry" cycled them forever because the session is fine, just denied.
**Approach:** Added a sibling-to-`SessionRejectionBus` `AccessDeniedBus` in `:libraries:networking` (interface + buffered SharedFlow impl). `NetworkClientImpl.handleResponseExceptionWithRequest` now, on a 403, tries to deserialize the saved response body as the locked wire shape (a `reason: String` is the gate; route-level 403s like `not_host` use a different envelope and fail-silent through `Catching`) and signals the bus. `AppViewModel` collects denials and forwards them onto a new `accessDenied: Flow<Denial>` channel; `App.kt` `LaunchedEffect`s on it and pushes a new `AccessDeniedRoute(reason, appealUrl)` with `launchSingleTop`. `AccessDeniedRoute` is `NavigableWhileBlocked` (so it's never blocked) and added to `DelegatingRouter.isBlockingErrorActive` so other navigation gets blocked when it's the top. `AccessDeniedScreen` in `:libraries:navigation:impl` is a `BackHandler { doNothing() }` screen that picks title/body from a small `reason → StringResource` map (banned / suspended / default fallback for unknown reasons) and renders an "Open appeal" button via `Router.openWebLink` only when `appealUrl != null`. Strings live in `:libraries:resources`.

Chose `handleResponseExceptionWithRequest` over `validateResponse` so the body read works off Ktor's saved `ResponseException.response` (single-shot streaming body decoded in `validateResponse` would race the caller's own decoding). Chose a new route + screen over reusing `BlockingErrorRoute` because the route carries machine-readable wire data (`reason`, `appealUrl`), not pre-localized copy — putting copy on the route would defeat the "no copy on the wire" contract.
**Reviewer notes:** WebSocket 403 handshake failures don't flow through this — Ktor's WS handshake exception path is structurally different and the existing room socket already maps 403 to `NotHost` off status. Worth a follow-up to confirm whether a banned user trying to open a WS surfaces a usable error; tagged as out-of-scope for this slice. The 403 body parse hits the Ktor `expectSuccess` failure path *and* the caller's own failure path — they get the same `ClientRequestException` they always did, so route-level 403 handlers (e.g. `RoomRepositoryImpl` mapping 403 → `NotHost` off the status alone) remain functionally unchanged. Tested with a `RecordingBus` + MockEngine covering enveloped 403, route-level 403, and non-403 statuses; the `AppViewModelTest` pins the bus → channel forwarding.
**Deferred:** WS-handshake 403 routing — added an inline note in the new in-flight block; reviewer please triage to backlog if this turns into product work.

## test(integration): play three consecutive full hands to showdown over the wire

**Problem:** Owner review of the `:apps:integration` coverage flagged it as thin — `MatchmakingPlayTest` already plays full hands for the public/server-dealt path, but the friend-game (host-driven via `StartHand` + `RequestNextHand`) path only had a single preflop-fold multi-hand test and no end-to-end "deal → preflop → flop → turn → river → showdown → next hand" loop.
**Approach:** New `MultiHandWireTest.threeConsecutiveFullHands_dealThroughShowdown_chipsConserved` plays three consecutive full hands over the real wire on the heads-up friend-game path: the host taps `StartHand` once, then `RequestNextHand` between hands; each hand is walked passively (check/call) to `BettingRound.Complete`, asserting five community cards (showdown reached, not a preflop fold), button rotation across hands, and per-hand chip conservation. Updated [`docs/testing-plan.md`](../testing-plan.md) Round 2 entry to cite the new companion test. Considered three-player coverage (`seatThreeAndConnect`) but it duplicates the existing `WireSidePotTest` plumbing without testing the host-driven boundary the owner called out; left out to keep the slice tight.
**Reviewer notes:** None — green locally on `:apps:integration:testDebugUnitTest`. The cursor-aware `playPassivelyToCompletion` accumulates buffered snapshots, so the same harness can drive consecutive hands without resetting `GameplaySession`; the test relies on that behaviour.

## test(rooms): add explicit simulateReconnect() helper to FakeRoomSocketTransport

**Problem:** `testing-plan.md` Fake-quality list flagged that the close → reopen pattern in `ReconnectingRoomSocketTest` had to be assembled from two raw helpers (`closeFromPeer()` + `primeSuccess()`), so the production "drop and the next `open()` returns a fresh session" contract wasn't explicit in the fake's API. Production [`ReconnectingRoomSocket`](../libraries/rooms/impl/src/commonMain/kotlin/com/cards/libraries/rooms/impl/ReconnectingRoomSocket.kt) does exactly this every reconnect cycle.
**Approach:** Added `FakeRoomSocketTransport.simulateReconnect()` which bundles `latest?.closeFromPeer()` + `primeSuccess()` and returns the queued next session, naming the contract in one call. Pinned by `ReconnectingRoomSocketTest.simulateReconnect_dropsCurrentSession_andLandsNextOpenOnFreshSession` (drives the real socket through the helper, asserts `openCalls` goes up and `transport.latest` rolls to the simulated session). Existing call sites left untouched — they aren't broken, just verbose; future tests get the explicit helper. Ticked the box in [`docs/testing-plan.md`](../testing-plan.md) Fake-quality list.
**Reviewer notes:** None — green on `:libraries:rooms:impl:testDebugUnitTest`. Chose to leave the existing closeFromPeer + primeSuccess call sites untouched because mechanically rewriting them would balloon the diff for zero behavioural change, and the contract is also visible from any one of them — the helper exists for the next test that needs it.
