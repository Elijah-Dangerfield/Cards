## feat(auth): route VerifyEmail off resolveIsNewAccount; retire walletJustCreated (AUTH-22)

**Problem:** `VerifyEmailViewModel.isBrandNewAccount()` was the last auth path still classifying new-vs-returning from the best-effort `ChipsRepository.walletJustCreated` proxy (which goes false offline and trips on identity churn), instead of the authoritative server `/v1/me` `isNewAccount` signal that onboarding + the Home welcome already use.
**Approach:** Injected `ProfileRepository` into `VerifyEmailViewModel` (dropped the now-unused `ChipsRepository`) and rewired `isBrandNewAccount()` to `profileRepository.resolveIsNewAccount()`, mirroring `OnboardingViewModel`. With that call site gone, `walletJustCreated` had no remaining production reader, so I retired it end-to-end: removed it from the `ChipsRepository` interface + `ChipsRepositoryImpl` (`_walletJustCreated` field and the `response.walletCreated` flip) and from every test fake across `:libraries:cards:impl`, `:features:{home,shop,room,lobby,onboarding}:impl`, `:libraries:billing:impl`, and `:apps:integration`. Switched `VerifyEmailViewModelTest` to drive `FakeProfileRepository.isNewAccount` (the same knob `OnboardingViewModelTest` uses) and deleted the two `ChipsRepositoryImplSyncTest` cases that asserted the retired flip. Left the server-side / sync-response `walletCreated` DTO field untouched (separate wire concern).
**Reviewer notes:** The client sync-response DTO still deserializes a `walletCreated` field that nothing reads now — harmless and intentionally out of scope (the task scoped removal to the client signal only). The DI change needed no manual factory edit: kotlin-inject regenerates `(email: String?) -> VerifyEmailViewModel` and `ProfileRepository` was already in the onboarding graph; confirmed by a green `:apps:compose:assembleDebug`.
**Deferred:** AUTH-22's optional part (b) — a single typed `AuthOutcome` (`SignedUp`/`SignedIn`/`Linked`) from the auth layer — is not done; I rewrote the todo bullet (kept the AUTH-22 ID, dropped to P2) to describe just that remaining polish. The `walletJustCreated` half of its acceptance is now fully satisfied.

## feat(auth): confirm the save when a guest links an identity (AUTH-24)

**Problem:** An anonymous guest who linked Google/Apple/email got zero feedback — OAuth/Apple just `goBack()` to Profile, so nothing told them their chips/XP were now saved to a real account.
**Approach:** Added a routed, celebratory `AccountLinkedRoute(providerLabel)` dialog (`AccountLinkedDialog`, modeled on `WelcomeDialog`) that floats over Profile after a link. `ClaimAccountEvent.Claimed` now carries the `OAuthProvider`; the Profile entry point pops the claim screen and navigates to the dialog in one `router.batch`. Copy is distinct from the sign-up welcome (starter grant) and the silent sign-in bounce: it reassures the user their existing progress is saved and names the provider.
**Scope decision (loud):** I shipped the **OAuth + Apple instant-link** paths and deliberately deferred **email**. Email's identity isn't linked until the user confirms the emailed link, and at the confirm point (`VerifyEmailViewModel` → `NavigateToHome`) the anon-guest-link case is indistinguishable from a returning user with a previously-unconfirmed email signing in, without threading a new flag through `VerifyEmailRoute` + the onboarding VM/entry point (a separate module, materially bigger). Rewrote the AUTH-24 bullet (kept the ID) to describe exactly that remaining email slice. The task explicitly sanctioned this split.
**Second decision (loud):** I did **not** add the dialog to `OnboardingViewModel.finishAppleSignIn`'s anon-guest link branch. There the link advances into the full onboarding flow (PickIdentity → starter-grant reveal), which is its own richer confirmation; interposing a "your account is saved" dialog mid-onboarding would be redundant and break the step flow, and the guest has no earned progress to reassure about yet. Rejected alternative: fire it there too for literal "all three providers everywhere" coverage.
**Reviewer notes:** `AccountLinkedRoute` is a `data class` route with a `String` arg (matches `WelcomeDialogRoute`; not a `data object`, so no iOS graph-build crash). Provider label passed as a plain string (brand proper noun) formatted into the resource copy, same as display names in `WelcomeDialogRoute`. Dialog copy ran through the warm/plain voice; no em dashes.
**Deferred:** Email-link confirmation — rewritten into the AUTH-24 bullet in `docs/todo.md` (reviewer please triage direction: the flag-threading vs. a dedicated `EmailLinkedRoute` on Home).
