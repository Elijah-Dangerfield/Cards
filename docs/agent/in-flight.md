# In-flight (this cycle)

## feat(auth): flush user-scoped syncs on account claim

**Problem:** A guest claiming an account keeps the same `userId`, so `AppEvent.UserChanged` never fires — pending XP/chips/inventory/equipment only flushed on the next foreground.
**Approach:** Added a dedicated `AppEvent.AccountClaimed` event dispatched from `SupabaseAuthRepositoryImpl.emitLocked` when an anon→claimed transition keeps the same id (single choke point, so it covers Apple/Google/email claim paths automatically — chosen over nudging syncs from each claim call site, which would have been N call sites to keep in sync). The progression/chips/inventory/equipment/achievement repositories override `onAccountClaimed` to fire their (idempotent) `sync()`.
**Reviewer notes:** I included `AchievementRepositoryImpl` in the claim re-sync even though the todo only named progression/chips/inventory/equipment — the earned set is server-authoritative and a just-claimed account should reconcile it too; harmless (idempotent) but flag if you'd rather scope it down. `onAccountClaimed` has an empty default in `AppEventListener`, so non-syncing listeners (telemetry, in-app-message) are unaffected.

## feat(profile): featured-badge selection + /v1/me persistence

**Problem:** Player Card Phase 1 — owner picks up to 3 earned badges to feature on the card; needed an additive `featuredBadgeIds` profile field + the selection UI to populate the slot `PlayerCardContent` already renders.
**Approach:** Full-stack additive field. Server: Flyway `V54` adds a nullable `featured_badge_ids` TEXT column storing a JSON array; `PostgresProfileRepository` (de)serializes it; `PATCH /v1/me` caps at 3 + de-dups (order-preserving). Client: threaded `featuredBadgeIds` through `MeDto`/`PatchMeRequest`/`Profile.Authenticated`/`ProfileCache`/`ProfileRepository.update`. UI: a new picker section on the Edit tab (tap earned medals, capped at 3, accent ring + dim-at-cap) wired to `AchievementRepository.observeProgress`; the View tab renders the effective selection. Empty selection = "use default": the card shows the 3 most-recently-earned badges and nothing is persisted until the user explicitly chooses.
**Reviewer notes:** (1) **Decision — no server-side earned-validation.** The route validates only cap + de-dup + non-blank/length, not that the ids are real/earned achievements. The server has no full achievement-id registry to check against and the client only offers earned badges; this matches the play-money "trust client for low-stakes" posture (same as the XP anti-cheat deferral). Tighten when stakes rise. (2) The at-table `PlayerProfileSheet` self-card still passes `featuredBadges = emptyList()` (the room seat doesn't carry them) — wiring the self's featured badges into the room surface is deferred; the Edit-Profile View tab is the surfacing target the todo named. Surfacing *opponents'* featured badges is explicitly Phase 2. (3) **Fixed a pre-existing broken test:** `EditProfileViewModelTest` didn't compile on develop (a prior Player-Card commit added `equipment`/`progression` repos to the VM ctor without updating the test) — added the missing fakes + the new `achievement` fake, plus ~13 other `ProfileRepository` fakes across the repo gained the new `update` param.

## feat(progression): full-screen level-up celebration on Home

**Problem:** No celebratory moment when the user levels up — the level number just ticks over in the header.
**Approach:** New `LevelUpCelebration` DS component in `:libraries:ui` (teal-skinned `RotatingDial` burst framing the new level number + warm line + Continue, scale/fade entrance + a `LongPress` haptic on land). Detection is **derived, not event-fired** (per decisions.md 2026-06-06): a `combine(observeProgression, appCache.updates)` in `HomeViewModel` compares the derived level against a new `AppData.lastCelebratedLevel` watermark. `watermark == 0` is the unset sentinel → silently seed to current level (no celebration); `current > watermark` → surface the overlay for the current level (net level shows once on a multi-level jump); Dismiss advances the watermark to the celebrated level. Overlay is rendered inside `HomeScreen` (Home-only — never at the poker table) atop `HomeScreenContent`.
**Reviewer notes:** (1) Derivation-from-watermark is robust across the table→home trip + process death — exactly why decisions.md chose it over a hand-end event. (2) **Account-switch hydrate race:** `resetAccountScoped` zeroes the watermark; on switch-in the progression flow emits the wiped (level-1) state first, seeds the watermark to 1, *then* the authoritative sync hydrates the higher level. Because the very first observed level is the seed, the silent-seed catches whatever level is current at that emission — `levelUp_switchIntoLeveledAccount_seedsToCurrent_noCelebration` pins that the *settled* higher level seeds silently. If the wiped-then-hydrated ordering ever flips so the level-1 emission seeds first and the hydrate looks like a "level up," that'd be a spurious one-time celebration on switch; I couldn't reproduce it with the unconfined scheduler but flag it as the one edge to watch. (3) The celebration deliberately has no shared queue with `InAppMessageManager` / the at-table achievement sheet — different surfaces, per decisions.md; promote to a shared client celebration queue only when client celebrations multiply. (4) Continue *or* a scrim/anywhere tap dismisses (celebratory "tap to continue").

## feat(progression): XP Boost (2× XP) time-window consumable

**Problem:** No way to grant/run a temporary 2× XP boost — the decisions.md consumable existed only on paper.
**Approach:** Modeled the boost as a **time window**, not an owned count (per decisions.md): a new `AppData.xpBoostExpiresAtEpochMs` + `XpBoostRepository` (`observe`/`status`/`activate`/`multiplier`) that set-or-*extends* the window on re-activate. `ProgressionRepositoryImpl.awardForHand` reads `xpBoostRepository.multiplier()` and doubles every award **before** it hits the ledger (so the boosted XP is what syncs to the server, not a client-only display trick). A teal `XpBoostBadge` DS component renders a live `mm:ss` countdown under the Stats XP hero and self-hides on expiry. Persistence + offline-friendliness come free from `AppCache` (no server round-trip — the boost is pure local XP math).
**Approach (slice):** Shipped the full mechanic + activation surfaces (a QA-menu "Activate 2× XP boost" trigger; the level-up reward table gifts it — see the next commit). **Deferred the user-facing chip-priced *shop purchase*** — that's a shop-product + buy-flow surface, rewritten as the remaining todo. Chose to slice there because the buy path is a distinct surface (ShopViewModel + a new product), whereas the mechanic/grant path is what everything else (level-up gift, future chest) depends on.
**Reviewer notes:** (1) The boost multiplies **hand XP only** (the `XpCalculator` path), not one-off `applyAchievementXp` grants — matches the decision's "XpCalculator doubles awards" wording; flag if you'd rather it blanket-double all XP. (2) `XpBoostBadge` ticks off `Clock.System.now()` once a second (same pattern as `StatsScreen`'s `EventRow` earned-ago) — fine for a display countdown. (3) Boost is account-scoped (reset in `resetAccountScoped`) since it's a purchased per-user consumable. (4) `multiplier` is an `Int` (2 or 1) so XP stays integral — no rounding drift.

## feat(progression): grant level-up rewards on level-cross

**Problem:** Levels carried no prize — "certain level-ups give a reward" existed only in decisions.md.
**Approach:** A static `LevelRewardTable` (`LevelReward.Chips` / `LevelReward.XpBoost`) + a `LevelUpRewardGranter` (`AutoInit`, modeled on `FoundingMemberBadgeReconciler`) that watches `observeProgression()`, and on a level-cross grants each crossed level's rewards exactly once: chips via `ChipsRepository.addChips(idempotencyKey = "levelup_<level>")` (ledger-deduped), boost via `XpBoostRepository.activate()`. A new `AppData.highestLevelRewarded` watermark — **separate** from the celebration's `lastCelebratedLevel` — gates re-grants; `0` is the unset sentinel that seeds silently so a fresh install / switch / reinstall never retro-grants. Drive-by: promoted `xpAtStartOfLevel` from a private `QaMenuScreen` helper to public `Level.kt` (the granter test + the QA menu now share it).
**Approach (slice + direction):** Shipped chips + XP-boost rewards; **the reward-table *content* (which levels, how much) is a directional placeholder I picked** — sparse + front-loaded (chips at 3/5/7/15, chips+boost at 10/20) so early levels feel rewarding without minting chips forever. Tune freely; it's static client content by design. Deferred **cosmetic rewards** (the achievement-reward grant path) and **the celebration revealing the prize** (the grant is currently silent — chips/boost just appear); rewrote the todo to those two gaps.
**Reviewer notes:** (1) **Idempotency layering:** the watermark advances per-level (not once at the end) so a crash mid-multi-level-jump only re-touches the in-flight level; chip grants are *also* key-idempotent at the ledger, so a re-touch can't double-pay. The XP-boost grant is **not** idempotent (re-activate extends the window) — only the watermark guards it, so a crash between granting a boost and persisting that level's watermark could extend a boost twice. Negligible for a play-money boost; flagged as the one non-idempotent edge. (2) Grant is decoupled from the celebration by design (decisions.md: "the prize is theirs the moment they level, independent of seeing the celebration") — hence the separate watermark. (3) Pre-launch posture: no backfill logic — a fresh world seeds silently and grants forward.

## feat(progression): reveal granted prizes in the level-up celebration

**Problem:** The level-up grant was silent — chips/boost just appeared in the wallet; the full-screen celebration showed only the new level number, never "here's what you earned."
**Approach:** Threaded the crossed-level rewards into `LevelUpCelebration` (`:libraries:ui`) as a new "You earned" surface panel. The DS component stays out of the economy domain: it takes a list of display-only `LevelUpReward(emoji, label)`; `HomeScreen.toDisplay()` maps domain `LevelReward` → localized rows. `HomeViewModel` computes the reward set from the *celebration's* crossed range `(lastCelebratedLevel, currentLevel]` via `rewardsForLevel`, aggregating to at most two rows (chips summed, boost de-duped) so a multi-level jump reads as one tidy payout. Cleared alongside the overlay on dismiss.
**Reviewer notes:** (1) The reveal derives its reward set from the celebration's `lastCelebratedLevel` watermark range, while the *grant* derives from the separate `highestLevelRewarded` watermark — they seed identically and track the same crossings, so the reveal mirrors what was granted. If the two watermarks ever diverged (they don't today), the reveal could show a row the granter handled at a different boundary; both read the same static `LevelRewardTable`, so the prize identity can't be wrong, only its level-attribution. (2) Chip rows are summed across the crossed range rather than shown per-level — a deliberate presentation call (one "+N chips" reads cleaner than a stack). (3) The reveal is decoupled from the grant by design (the prize is already in the wallet by the time the overlay shows); this commit only surfaces it. (4) Cosmetic reward kind is still unmodeled — rewrote the todo to that single remaining gap.
