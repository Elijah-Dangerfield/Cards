## feat(auth): route the server's 403 ban envelope to a blocking access-denied screen

**Problem:** Server returns `403 {reason, until, appealUrl}` for banned users (shipped previously), but the client never parsed the envelope — a banned account hit `RefreshFailureKind.AuthRejected` via the 403, got booted to the SessionExpired screen, and "Retry" cycled them forever because the session is fine, just denied.
**Approach:** Added a sibling-to-`SessionRejectionBus` `AccessDeniedBus` in `:libraries:networking` (interface + buffered SharedFlow impl). `NetworkClientImpl.handleResponseExceptionWithRequest` now, on a 403, tries to deserialize the saved response body as the locked wire shape (a `reason: String` is the gate; route-level 403s like `not_host` use a different envelope and fail-silent through `Catching`) and signals the bus. `AppViewModel` collects denials and forwards them onto a new `accessDenied: Flow<Denial>` channel; `App.kt` `LaunchedEffect`s on it and pushes a new `AccessDeniedRoute(reason, appealUrl)` with `launchSingleTop`. `AccessDeniedRoute` is `NavigableWhileBlocked` (so it's never blocked) and added to `DelegatingRouter.isBlockingErrorActive` so other navigation gets blocked when it's the top. `AccessDeniedScreen` in `:libraries:navigation:impl` is a `BackHandler { doNothing() }` screen that picks title/body from a small `reason → StringResource` map (banned / suspended / default fallback for unknown reasons) and renders an "Open appeal" button via `Router.openWebLink` only when `appealUrl != null`. Strings live in `:libraries:resources`.

Chose `handleResponseExceptionWithRequest` over `validateResponse` so the body read works off Ktor's saved `ResponseException.response` (single-shot streaming body decoded in `validateResponse` would race the caller's own decoding). Chose a new route + screen over reusing `BlockingErrorRoute` because the route carries machine-readable wire data (`reason`, `appealUrl`), not pre-localized copy — putting copy on the route would defeat the "no copy on the wire" contract.
**Reviewer notes:** WebSocket 403 handshake failures don't flow through this — Ktor's WS handshake exception path is structurally different and the existing room socket already maps 403 to `NotHost` off status. Worth a follow-up to confirm whether a banned user trying to open a WS surfaces a usable error; tagged as out-of-scope for this slice. The 403 body parse hits the Ktor `expectSuccess` failure path *and* the caller's own failure path — they get the same `ClientRequestException` they always did, so route-level 403 handlers (e.g. `RoomRepositoryImpl` mapping 403 → `NotHost` off the status alone) remain functionally unchanged. Tested with a `RecordingBus` + MockEngine covering enveloped 403, route-level 403, and non-403 statuses; the `AppViewModelTest` pins the bus → channel forwarding.
**Deferred:** WS-handshake 403 routing — added an inline note in the new in-flight block; reviewer please triage to backlog if this turns into product work.

## test(rooms): pin WS handshake awaits auth-ready before firing

**Problem:** Round 5 of `testing-plan.md` listed "WS handshake during auth refresh" as open with a callout that "the auth bootstrap was the source of one real iOS bug." The contract is that `KtorRoomSocketTransport.open` → `authedWebSocketSession` MUST call `awaitAuthReady()` before any TLS / TCP work hits the wire, so the request timeout doesn't tick during a slow cold-boot auth bootstrap (see the comment on `authedCall` in `NetworkCall.kt`). The contract was implicit — easy to regress by reordering the helper's pre-flight.
**Approach:** Added `KtorRoomSocketTransportTest.open_suspendsUntilAuthReady_thenFiresHandshake` next to the existing URL-construction tests. A new `GateableAuthNetworkClient` test fake holds `awaitAuthReady()` on a `CompletableDeferred`; the test launches `transport.open` while the gate is held, drives the scheduler with `runCurrent()`, and asserts the MockEngine recorded zero requests — proves the handshake didn't sneak past the await. Then the gate releases, the open completes, and the test asserts exactly one `wss://` upgrade was attempted. Chose `runTest(StandardTestDispatcher())` over the test class's default (`runTest`) so the pre-release "no request fired" assertion is meaningful — the default unconfined-style dispatcher would otherwise eagerly drain past the await. Chose to pin at the `KtorRoomSocketTransport` seam (where `:libraries:rooms:impl` already has MockEngine + WebSockets test deps) rather than expanding `:libraries:networking`'s test deps just to test the helper in isolation; the transport is the production caller of `authedWebSocketSession` so the contract reaches its real consumer.
**Reviewer notes:** None — green locally on `:libraries:rooms:impl:testDebugUnitTest`. The test pins ordering, not the response: the engine deliberately returns 500 once the gate releases (no real WS server in the unit test), so `transport.open` ultimately returns failure. That's beside the point — what matters is that *no request fired before* the gate released and *exactly one fired after*. If the helper were reordered to issue the WS upgrade before awaiting, the pre-release assertion would catch it.

## test(integration): client backgrounded mid-hand resyncs on resume

**Problem:** Round 5 of `testing-plan.md` listed "Client backgrounded > 30s during opponent's turn" as open — on resume, the client's `connection` collector must reconnect, `gameplayFrames` must re-sync, and no stale pre-background state must show. The existing `ChaosPlayTest.clientDropsMidHand_reconnects_and*` cases cover a transient drop (reconnects allowed), not a sustained offline window during which the *opponent acts and the server state moves*.
**Approach:** Added `ChaosPlayTest.idleClientBackgrounded_opponentActs_idleResumesAndResyncsToLiveState`. Heads-up table, host deals; the non-acting client `dropAndBlock`s its socket (sustained offline — `FaultInjectingTransport.blockReconnects = true`); the acting opponent folds and the server completes the hand while the idle client is offline; the idle client clears `blockReconnects` (foregrounds) and its real reconnect machinery + the production socket's `replay = 1` latest-snapshot buffer converge it on the same `(handNumber, post-action stacks)` the opponent saw. Asserting the resynced view matches the opponent's completed snapshot — not the dealt-but-pre-fold view — is what pins "no stale state shown". Chose `dropAndBlock` over `dropActiveConnections` because the latter reconnects within milliseconds and doesn't model the sustained backgrounded case the testing-plan item calls out; chose the fold path because heads-up that's the cleanest way to move the server state from the opponent's side alone (a check/call needs two actors, which would require the idle client to come back to act and defeats the test).
**Reviewer notes:** Ran 5× green + non-flaky locally on `:apps:integration:testDebugUnitTest`. The 30s clock in the testing-plan item description is the *opportunity* a real OS suspend gives the server to move, not a literal `delay(30_000)` the test needs to wait — the harness already pumps the opponent's action through immediately while the idle client is blocked, which is the same shape the seam needs to survive. Doesn't exercise the `connection` *collector* on a `LobbyViewModel` (no VM is constructed) — the existing `SetupJourneyTest.droppedClient_reconnects_andPresenceIsRestored` already pins that path; this one focuses on the in-hand `gameplayFrames` resync. The presence-grace window is 5min by default in the harness, well above the test's sub-second offline window — so we're testing reconnect, not seat-forfeit.
