# In-flight

## fix: send a real room leave when a player leaves an MP table

**Problem:** `PlayPokerAction.LeaveTable` never told the server the player left — it only fired the bot-mode review prompt — so a player who left an MP game kept their seat/membership on the server (found in the 2026-06-19 playtest).
**Approach:** Added `PokerSession.leave()` (remote impl fires the durable `roomRepository.leaveRoom(code)` via a lambda the factory wires in; local-bots no-ops). The VM calls it on `LeaveTable` parented to `AppCoroutineScope`, not `viewModelScope`, because the screen pops the VM the instant it fires the action and the leave must still reach the server (AGENTS.md "fire-and-forget actions outlive the screen"). Chose a lambda over injecting `RoomRepository` + room code into the session so `RemotePokerSession` stays transport-decoupled.
**Reviewer notes:** This ships the "leaver actually leaves" half only. The other two parts of the original todo (remaining players see the seat disappear in-game; last-human-left → dialog → Home) both need the server to fold/remove the seat from the in-progress `GameSession` state on leave — leaving the room frees the *membership* row but not the *game* seat, which overlaps the B3 forfeit-then-spectator policy. I rewrote the todo bullet to describe that remaining gap rather than deleting it.

## feat: grant one-shot per-hand MP achievements server-side

**Problem:** The `serverWitnessed` per-hand MP achievement ids existed (and the client grant route already 403s them) but nothing on the server ever granted them — only the count-based ids (`FIRST_HAND_MP`/`HANDS_100_MP`) fired. The per-hand-shape ids gated on signals the hand-finished callback didn't carry.
**Approach:** Widened `GameSession`'s `onHandFinished` to emit a `HandOutcome` (per-human `PlayerHandOutcome`: `won` / `stackMultiple` / `bustsDealt` / `potTotal`) built from each seat's start-of-hand stack (newly captured in `startHandLocked`) vs. its final stack. Added `ServerWitnessedAchievements.evaluateHand(userId, outcome)` (default no-op) and implemented the four **one-shot** grants idempotently via the existing `recordEarned` + wallet-ledger chip path: `FIRST_BUST_DEALT_MP`, `DOUBLE_UP_MP` (≥2×), `TRIPLE_UP_MP` (≥3×), `POT_5000_MP` (won a ≥5000 pot). The two cumulative ids (`BUST_DEALT_5_MP`, `WIN_BY_FOLD_10_MP`) need a durable per-user counter — deliberately left out to avoid a schema migration this cycle; todo rewritten to scope just those.
**Reviewer notes:** Two directional calls worth a look. (1) **Bust attribution** — I credit `bustsDealt` to *every* winner of a hand where an opponent finished at 0 chips; in a multiway side-pot situation that can over-credit a winner who didn't actually take the busted player's stack. Fine for a play-money one-shot, but if you want it exact it needs per-pot eligibility tracking. (2) **Chip reward amounts** are my pick (1000 / 1000 / 2000 / 1500), mirroring the "MP achievement → chips, not a borrowed SP cosmetic" precedent set by `HANDS_100_MP`; adjust if the economy wants different numbers. Also: `handStartStacks` is in-memory, so a hand that *began* before a server restart yields `stackMultiple = 0.0` and skips the double/triple grant until it fires on a later hand (noted in code; acceptable pre-launch). All server tests green.

## feat: lift the XP-per-level curve onto remote app-config

**Problem:** The XP-per-level curve (`100 × N²`) was a compile-time constant in `Level.kt`, so the level economy couldn't be retuned without shipping a build — and unlike the reward table (already on app-config), display and grant had no shared, server-tunable source.
**Approach:** Added a `@Serializable LevelCurve` (`{ xpPerLevel: Long[], baseXp, exponent }` — optional front-loaded ladder + quadratic tail; default reproduces `100 × N²` exactly) on app-config at `progression.levelCurve` via `LevelCurveConfigValue : JsonConfigValue<LevelCurve>`, exposed through `ProgressionConfig.levelCurve()` (mirrors the reward-table seam from 2026-06-17). `Level.kt`'s three derivation funcs took an optional `curve = DefaultLevelCurve` param so every existing caller compiles unchanged. Threaded the **authoritative** paths — `LevelUpRewardGranter` (grant-on-cross) and `AchievementRepositoryImpl` (the persisted `CURRENT_LEVEL` counter) — onto `progressionConfig.levelCurve()`. Sliced out the **display** sites deliberately (see below) — they stay on the bundled default for now, so a server override doesn't yet move the *shown* level.
**Reviewer notes:** The optional-param-with-default design is what keeps this low-risk: display sites still compile and behave identically on the bundled curve; only the two paths where a wrong level corrupts persisted state or mis-grants read config. Tests pin the threading (`LevelUpRewardGranterTest.derivesLevelFromTheConfiguredCurve_notTheBundledDefault` — 50 XP is level 1 on the default curve but levels up under the override) + the curve math + the config round-trip. Android + iOS compile; `:libraries:cards(:impl)` + `:features:home:impl` tests green.
**Deferred:** Threading the configured curve through the ~10 display sites (recommended via a `LocalLevelCurve` `staticCompositionLocalOf` at the app root — DS `LevelPill` and several screens compute level inline from raw XP, so leaf-DI is wrong) + the server-side grant reconcile — rewrote the `docs/todo.md` "Stats & progression" bullet to scope exactly that remaining gap.

## feat: grant the cumulative MP achievements server-side

**Problem:** The two cumulative per-hand MP ids (`BUST_DEALT_5_MP` at 5 lifetime busts dealt, `WIN_BY_FOLD_10_MP` at 10 pots taken without a showdown) were the last `serverWitnessed` ids with no grant path — the one-shot ids landed in `1e43341e` but the cumulative ones needed a durable per-user tally the server didn't keep. This finishes the set (every `ClientGrantableAchievements.serverWitnessed` id is now granted server-side).
**Approach:** Rather than stand up a second ledger I **enriched the existing finished-hand ledger** (`hand_finished_events`, V60 adds `busts_dealt INT` + `won_by_fold BOOL`), so the cumulative tally is a `SUM(busts_dealt)` / `COUNT(won_by_fold)` over the same dedup'd rows the count already reads — one write per hand, the `(user_id, idempotency_key)` PK still collapses replays so a re-observed hand never double-counts. Added `wonByFold` to `PlayerHandOutcome`, derived in `GameSession.buildHandOutcome` from the `HandEnded` event's `HandWinner.byFold` (authoritative — the stack delta can't tell a fold-win from a showdown win). `evaluateHand` now queries the cumulative tally (guarded so the read is skipped once the id is earned) and grants `BUST_DEALT_5_MP` / `WIN_BY_FOLD_10_MP` idempotently via the same wallet-ledger path.
**Reviewer notes:** Two judgement calls. (1) **Single-ledger vs. second table** — I chose to widen `HandsFinishedRepository`/`hand_finished_events` rather than add a counter table; the todo's hint suggested a separate "counted-events table", but the finished-hand row already represents "user X finished hand Y", and tagging it with that hand's outcome shape is cohesive and avoids a second write/dedup boundary. Easy to split later if the repo's scope feels overloaded. (2) **Chip amounts** are my pick — `BUST_DEALT_5_MP` = 2000 (EPIC, matches `TRIPLE_UP`), `WIN_BY_FOLD_10_MP` = 1000 (RARE) — sized to the existing per-hand grant scale set in `1e43341e`; adjust if the economy wants different numbers. Bust over-credit on multiway side-pots is inherited from `buildHandOutcome` (the per-hand `bustsDealt` it sums), same caveat `1e43341e` flagged. Full `:apps:server:test` green incl. the V60 migration under testcontainers; the fold-win derivation is pinned end-to-end in `GameSessionRegistryIntegrationTest` (a folded hand credits exactly one `wonByFold`).
