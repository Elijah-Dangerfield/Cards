## feat(auth): blocking session-expired screen with retry + logout

**Problem:** A server-rejected session showed an error snackbar and silently bounced the user to onboarding — losing their place and offering no in-place recovery. The todo wanted a blocking screen modeled on `BlockingErrorScreen` with Retry (recover in place) + Logout (tear down to onboarding), anonymous-aware.
**Approach:** Added a `SessionExpiredRoute` (NavigableWhileBlocked) + a stateless `SessionExpiredScreen` (BackHandler-swallowing, bottom-bar hidden via `Screen`) driven by a new `SessionExpiredViewModel` (SEAViewModel) in `:libraries:navigation:impl`. Retry calls `AuthRepository.retry()`; on `Authenticated` it restores `hasUserOnboarded=true` and emits `SessionRestored` (entry point pops the screen, user lands back where they were). Logout calls `signOut()`, clears `hasUserOnboarded`, emits `LoggedOut` (entry point routes to onboarding, clearBackStack). Anonymous logout goes through a confirm dialog ("Lose your progress?"). `App.kt` now pushes the route (launchSingleTop, stack intact) instead of navigating-to-onboarding + snackbar; `AppViewModel` no longer clears `hasUserOnboarded` on the expiry edge (the screen owns that now, so cold-boot of a persisted-but-dead session lands on the blocking screen rather than onboarding).
**Approach call:** Put the screen + VM in `:libraries:navigation:impl` (already depends on `:libraries:identity`) rather than a feature module, since that's where the existing `BlockingErrorScreen`/error routes live and where `App.kt` already routes ambient errors. Added a thin dep on `:features:onboarding` api (route-only) for the logout destination. Alternative — a dedicated `:features:auth` screen — rejected as overkill for a route that App.kt drives directly.
**Reviewer notes:** Retry recovery hinges on `AuthRepository.retry()` re-resolving the persisted session; if the underlying refresh path can't recover a server-rejected token in-session (vs. only an offline→online flip), Retry will keep failing and the user must Logout — acceptable, but worth a device check. The screen swaps the Retry button label for a `CircularLoadingIndicator` while retrying. 3 VM tests added (retry-success / retry-fail / logout); 4 screen previews (claimed / retrying / retry-failed / guest). The 4 old `session_expired_*` snackbar strings are repurposed for the screen body; the claimed/guest body copy was rewritten to fit the retry/logout framing.

## fix(server): deal in a queued joiner when one seat survives (CARDS-24)

**Problem:** A human matched into an in-progress public table was queued for the next hand but never dealt in — they sat out while existing seats kept playing (B7 / Sentry CARDS-24).
**Approach:** Root cause was the server-dealt advance gate in `ServerBotDriver.maybeAdvanceBotTable`: it required ≥2 *currently seated* players with chips before calling `requestNextHand`. A mid-hand joiner lives in `GameSession.pendingJoiners` (not in `state.seats`), so when the table dropped to a single seated survivor (the only opponent busts or trims out) the gate skipped the boundary and `requestNextHand` never fired — `pendingJoiners` are only folded into the deal there. Fix: exposed `GameSession.pendingJoinerIds` and counted the not-yet-seated joiners toward the gate, so one survivor + one waiting joiner now advances and deals the joiner in. The advancer is still always a current seat-holder (a bot, or the lowest-seat human on a server-dealt table).
**Reviewer notes:** The pending-joiner count is a lock-free read of `pendingJoiners.keys` — `requestNextHand` re-checks the real occupant count under the mutex before dealing, so the driver only needs an approximate "should I bother advancing" signal; a stale count at worst triggers a harmless `requestNextHand` that rejects on the <2 guard. Regression test confirmed red without the driver fix, green with it. The related CARDS-25 (server-dealt all-human stall) and CARDS-16 (1H+NB stall) were already fixed; this closes the remaining mid-hand-join slice of B7.
