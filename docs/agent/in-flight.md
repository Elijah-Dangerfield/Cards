# In-flight (this cycle)

## feat(auth): flush user-scoped syncs on account claim

**Problem:** A guest claiming an account keeps the same `userId`, so `AppEvent.UserChanged` never fires — pending XP/chips/inventory/equipment only flushed on the next foreground.
**Approach:** Added a dedicated `AppEvent.AccountClaimed` event dispatched from `SupabaseAuthRepositoryImpl.emitLocked` when an anon→claimed transition keeps the same id (single choke point, so it covers Apple/Google/email claim paths automatically — chosen over nudging syncs from each claim call site, which would have been N call sites to keep in sync). The progression/chips/inventory/equipment/achievement repositories override `onAccountClaimed` to fire their (idempotent) `sync()`.
**Reviewer notes:** I included `AchievementRepositoryImpl` in the claim re-sync even though the todo only named progression/chips/inventory/equipment — the earned set is server-authoritative and a just-claimed account should reconcile it too; harmless (idempotent) but flag if you'd rather scope it down. `onAccountClaimed` has an empty default in `AppEventListener`, so non-syncing listeners (telemetry, in-app-message) are unaffected.

## feat(profile): featured-badge selection + /v1/me persistence

**Problem:** Player Card Phase 1 — owner picks up to 3 earned badges to feature on the card; needed an additive `featuredBadgeIds` profile field + the selection UI to populate the slot `PlayerCardContent` already renders.
**Approach:** Full-stack additive field. Server: Flyway `V54` adds a nullable `featured_badge_ids` TEXT column storing a JSON array; `PostgresProfileRepository` (de)serializes it; `PATCH /v1/me` caps at 3 + de-dups (order-preserving). Client: threaded `featuredBadgeIds` through `MeDto`/`PatchMeRequest`/`Profile.Authenticated`/`ProfileCache`/`ProfileRepository.update`. UI: a new picker section on the Edit tab (tap earned medals, capped at 3, accent ring + dim-at-cap) wired to `AchievementRepository.observeProgress`; the View tab renders the effective selection. Empty selection = "use default": the card shows the 3 most-recently-earned badges and nothing is persisted until the user explicitly chooses.
**Reviewer notes:** (1) **Decision — no server-side earned-validation.** The route validates only cap + de-dup + non-blank/length, not that the ids are real/earned achievements. The server has no full achievement-id registry to check against and the client only offers earned badges; this matches the play-money "trust client for low-stakes" posture (same as the XP anti-cheat deferral). Tighten when stakes rise. (2) The at-table `PlayerProfileSheet` self-card still passes `featuredBadges = emptyList()` (the room seat doesn't carry them) — wiring the self's featured badges into the room surface is deferred; the Edit-Profile View tab is the surfacing target the todo named. Surfacing *opponents'* featured badges is explicitly Phase 2. (3) **Fixed a pre-existing broken test:** `EditProfileViewModelTest` didn't compile on develop (a prior Player-Card commit added `equipment`/`progression` repos to the VM ctor without updating the test) — added the missing fakes + the new `achievement` fake, plus ~13 other `ProfileRepository` fakes across the repo gained the new `update` param.
