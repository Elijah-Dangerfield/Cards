## fix(progression): anchor level-up celebration watermark in the granter (PROG-3)

**Problem:** After a solo hand, the level-3 reward granted but the full-screen level-up celebration never presented — user dropped straight to Home. Reported as "randomly not seeing the level up screens," i.e. intermittent (CARDS-4V).
**Approach:** Root cause is a seeding race between two independent `observeProgression()` watermark observers. `LevelUpRewardGranter` (AutoInit, observes early) seeds `highestLevelRewarded`; `HomeViewModel`'s celebration gate seeds `lastCelebratedLevel`. If the gate's first emission lands AFTER a level-up earned this session, its `watermark == 0` branch seeds straight to the new level and silently eats the celebration. Fix: the granter — the single reliable early observer of the pre-session level — now anchors BOTH watermarks in its seed step (seeding `lastCelebratedLevel` to the current level only when it too is unset). Any real mid-session crossing then surfaces on Home. Rejected collapsing the two watermarks (they're deliberately separate for exactly-once grants) and a fixed level-1 floor (would re-blast on account switch — breaks the existing `seedsToCurrent_noCelebration` invariant). Test-first: red `LevelUpRewardGranterTest` (seed must set both watermarks), green after the fix; plus a `HomeViewModelTest` case where the gate first observes the leveled-up XP with the watermark pre-anchored and still celebrates. Added the telemetry the case flagged — a once-per-decision `level-up celebration enqueued / skipped` Info line, gated by the gate's distinctUntilChanged so it's never per-emission. Decision logged (decisions.md 2026-06-27). QA entry added (PROG-1 in QA.md).
**Reviewer notes:** The todo's "achievement-earn celebration if it shares the trigger" clause: it does NOT share this path — achievements surface on Home's "Recent unlocks" shelf, not the full-screen level-up watermark route — so it's untouched by this fix and not in scope here. The race could in principle still bite if the gate truly observes before the granter (the gate's own `0`-seed remains as a fallback), but the granter is AutoInit and observes at app start, so it wins by construction; not separately reproduced.

## fix(room): split next-hand refusals so a stale tap doesn't show the rebuy toast (MP-22)

**Problem:** In heads-up-vs-bot, a backgrounded user tapped a stale-snapshot "Next hand"; the server rejected with `current hand not complete`, but the client collapsed *every* next-hand refusal into `NextHandUnavailable` → the terminal "Waiting for your opponent to rebuy or leave" toast — wrong (both stacks healthy, nobody busted) and a dead no-op until they left.
**Approach:** Two fixes. (1) The session now classifies the refusal: the server's one canonical can't-deal reason (`not enough players with chips for next hand`) → `NextHandRefusal.CannotDeal` → the existing rebuy notice (MP-14); every other reason (incl. `current hand not complete`) → `NextHandRefusal.Transient` → a new quiet `NextHandResyncing` event + "Catching up with the table, try that again in a moment" hint. There is no client resync frame — the live snapshot `StateFlow` *is* the resync — so Transient is honestly a "the table will catch up, retry" hint, not a fake re-request. (2) Button gating: the winner no longer gets a tappable "Next hand" while a rebuy-grace countdown is active (the table can't deal); the existing `MatchOverCountdownBanner` shows instead, so they never tap into a refusal. Added the telemetry the case asked for: a once-per-refusal `refusal <reason> → <event>` line in both the session (classification) and the VM (event mapping). Test-first: red `RemotePokerSessionTest` (transient must classify Transient), red MP integration + scenario-harness tests (transient must emit Resyncing not Unavailable), green after the fix.
**Reviewer notes:** The classification keys off the server's free-text error string (`CANNOT_DEAL_ERROR` constant mirrors `GameSession.requestNextHand`). The wire carries free-text errors today, so this string is the one coupling point — if the server ever changes that copy, a transient would mis-classify as CannotDeal (safe failure: a healthy table briefly showing the rebuy hint), and vice-versa. A typed refusal code on `IntentAck` would remove the coupling — flagged as a follow-up, not done here (out of scope for the client-side fix). The button-gating reuses the MP-14 `matchOverCountdown` (winner role = `localPlayerIsBusted == false`) as the "table can't deal" signal; this is correct for the heads-up bust case the bug describes. Renamed `PokerSession.nextHandUnavailable: SharedFlow<Unit>` → `nextHandRefused: SharedFlow<NextHandRefusal>` (only `RemotePokerSession` + the VM + test fakes consumed it).
**Deferred:** Server-side typed next-hand refusal code on `IntentAck` (removes the free-text-string coupling) — reviewer please triage; not added to backlog yet.
