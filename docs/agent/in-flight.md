## feat(home): explain friend-via-play rule on social empty states

**Problem:** Zero-friend users had no signal that friending is gated on having played together — `RecentlyPlayedWithStrip` and `FriendsStrip` both auto-hid in the all-empty state, leaving the user with no path to the friend graph. The todo flagged this as load-bearing for V1.x social.
**Approach:** `RecentlyPlayedWithStrip` always renders now: with tiles when there are recent opponents, and with an explanation paragraph + two inline pill CTAs ("Friend Game", "Quick Match") routed to the existing `onFriendGame` / `onQuickMatch` callbacks when empty. `FriendsStrip` also renders even in the fully-empty state, with a brief one-line echo that points the user to the recently-played-with shelf (where the full rule + CTAs live), so the two strips don't repeat the same paragraph. Updated `HomeScreen` to thread the existing friend-game / quick-match callbacks through to the strip; previews cover empty-state for both. **Sliced the todo:** the item was P0 because of Home; rewrote the bullet down to a smaller P1 follow-up for the Profile social section once that surface exists (it doesn't today, the todo explicitly said "if it exists"). Rejected: showing inline empty states elsewhere — the rule belongs where the user is shown they have zero friends, which is Home.
**Reviewer notes:** Spec voice rule "no begging" was explicitly overridden by the locked rule on this item ("Zero-friend users need to know how to get there"). The copy stays terse and instructional rather than urgency-bait — open to a copywriter pass. The two CTA pills route to the same callbacks the Take-a-seat cards above use, so a worried-it's-redundant reviewer should note that those cards are far above on the page; by the time a user scrolls past the empty-state explanation, the cards are off-screen.

## feat(ui): edge-to-edge LazyRow primitive + apply to Home strips

**Problem:** Home's horizontal carousels (FriendsStrip, RecentAchievementsStrip, RecentlyPlayedWithStrip) lived inside the page's horizontal screen padding, so the first/last tiles aligned flush with the screen-content edge — no "scroll for more" affordance, and tiles couldn't clip past the edge to hint at overflow.
**Approach:** Added `EdgeToEdgeRow` in `:libraries:ui/components/` — a `LazyRow` wrapper that uses `Modifier.layout` to grow its measurement budget by the standard horizontal screen inset on each side, then re-applies that same inset as `contentPadding`. The result: first item still visually aligns with surrounding page content, but the row reaches the physical screen edges and items can scroll into / off the edge. Swapped all three home shelves to `EdgeToEdgeRow`. Rejected: making every screen Column stop applying horizontal padding (too disruptive for one cycle, would touch dozens of screens); making the primitive take a configurable inset (the standard `screenHorizontalInsets` is the contract — diverging callers should drop back to raw `LazyRow` rather than threading a knob through the primitive).
**Reviewer notes:** The escape-via-Modifier.layout trick assumes the parent column applies `screenContentPadding` with the standard `Dimension.D500` inset (which every `Screen { }` caller does). If a future screen uses a non-standard horizontal page padding, `EdgeToEdgeRow` would land misaligned — the KDoc on the function flags that escape valve. The poker table's `OpponentsRow` and the in-game `EmojiTray` are *not* converted — they're inside the table chrome, not standard page padding, and have their own specialised scroll affordances.

## feat(room): add personality radar to bot profile sheet

**Problem:** The tap-an-opponent sheet for bot seats had only the derived archetype label ("Tight aggressive" / "Maniac") and a one-line description — no at-a-glance shape distinguishing visually how one bot differs from another. The todo asked for a 4-axis spider/blob.
**Approach:** Added a generic `RadarChart` + `RadarAxis` primitive in `:libraries:ui/components/` (filled polygon, three context rings, axis labels — no chart-library dependency, just Canvas + paths) and a `radarAxesFor(personality)` mapper in `BotPlayingStyle.kt` that yields the four axes (Tight, Aggro, Bluff, Patient). Bluff is rescaled from its 0..0.4 source range to 0..1 so it occupies the full ring rather than collapsing toward the center; Patient is `1 − aggression` (the todo explicitly allowed this as the 4th axis, and the resulting quad shapes for the five roster bots are visually distinct — pinned by `radarAxes_eachRosterBotProducesUniqueShape`). The playing-style section in `PlayerProfileSheet` was lifted out of `ListSection` into a side-by-side block so the radar sits next to the label/description rather than below.
**Reviewer notes:** Picked Patient = 1 − Aggression over inventing a fourth `BotPersonality` field. Tradeoff: the quad shape is by construction symmetric along the aggro/patient diagonal, so a future "4 truly independent" axes design would need a fresh data attribute. I think that's the right call for V1 — the goal is "this bot looks visually distinct from that bot at a glance", which is met today, and the alternative bloats a `:libraries:bots` type that's used everywhere. RadarChart label-font is Caption.C300, which renders well at the 112dp default size; an 80-90dp footprint also works for the side-by-side layout. Added `:libraries:ui` to commonTest deps of features/room/impl since `radarAxesFor` returns `List<RadarAxis>` — same pattern as the other test-classpath additions noted in that build.gradle.kts.

## feat(room): tenure section on tap-an-opponent profile sheet

**Problem:** The tap-an-opponent profile sheet had a playing-style block + difficulty tier + settings, but no sense of *how long this seat has been here*. The todo asked for "Playing since {createdAt}" + "{N} hands at the table" — useful framing for both bot tenure ("we've been at this 47 hands deep") and the human's own profile glance ("Playing since May 2026").
**Approach:** Added `handsAtTable: Int` + `playingSinceEpochMs: Long?` to `SeatView`. In solo bot sessions `handsAtTable = gameState.handNumber` for every populated seat (every seat has been at the table since hand 1 — same answer for human + bots until MP room-membership rows arrive). `playingSinceEpochMs` only fills for the local human seat from `Profile.Authenticated.createdAt.toEpochMilliseconds()`; remote-human + bot tenure stays null because there's no real source for it today. New `SeatTenure.kt` builds the section's `ListSectionItem`s — month-and-year resolution for the join date ("Playing since May 2026"), and pluralized "1 hand at this table" / "23 hands at this table" for the count. Empty list = section is hidden, so empty seats and pre-first-hand state stay clean. Sheet renders the new "At this table" `ListSection` between the playing-style block and the bot-difficulty tier. Rejected: synthesising a fake "playing since" for bots (would be a session-start timestamp, which is misleading once users learn the bots persist across sessions); and a separate inline pair of `Text(...)` rows (the `ListSection` shape matches the surrounding sheet vocabulary so the row keeps DS consistency with Difficulty + Settings).
**Reviewer notes:** Month-and-year deliberately avoids the day-of-month because the user doesn't need that level of precision — "Playing since 14 May 2026" reads as accountant-precise. Pinned by `SeatTenureTest` which asserts both formatting helpers and the row-omission contract (no hand count + no tenure source = section hidden). The "{N} hands at the table" supporting copy is split bot vs human ("Hands they've shared with this table." / "Hands you've shared with this table.") — small touch but keeps the surface readable both directions. `handsAtTable` plumbed via `TableUiState.Companion.fromGameState` (the one canonical projection site) so MP sessions that wire a different source later will plug in there.

## feat(room): bot-mode full-bleed achievement celebration sheet

**Problem:** The inline `AchievementUnlockedCallout` row inside the showdown / bust dialog gave the same single-line "🎁 Also unlocked · {label}" treatment in both modes — and the same row got buried under the XP bubble + board + showdown rows, so an unlock against the bots never felt like a moment. The todo asked for the bot-mode unlock to take over a focused sheet *after* the hand-result dialog dismisses, with a stacked variant when a single hand earns multiple achievements, while MP keeps the inline row (fast feedback in the middle of a live game).
**Approach:** New `AchievementCelebrationSheet` in `:features:room:impl` — a `BottomSheet` with a 🎉 chip-gold drag-handle bubble that stacks one card per earned achievement (big icon, name, description, XP/chip reward summary, and `cosmeticRewardFor(id)?.label` + the "from the {name} achievement" attribution when the unlock grants inventory). Multi-unlock cascades via a per-card 90 ms staggered fade-in + scale-in entrance. Sequencing lives entirely in `PlayPokerScreen` — `var celebrationActive` is set on dialog dismiss when `xpMode == BOTS && recentlyEarned.isNotEmpty()`, deferring `RequestNextHand` until the sheet itself is dismissed; MP dismiss path is unchanged. `PlayPokerState.xpMode` was added, initialised from `sessionFactory.xpMode`, and threaded into `ShowdownDialog` / `BustDialog` so the inline `AchievementUnlockedCallout` is now gated to MP mode only. Rejected: a Dialog (worse fit — the celebration is a takeover *moment*, the sheet's drag-to-dismiss + scrim reads more like "page sitting on top of the hand result" than a centred modal); and a separate queue of N modals when multiple achievements fire same hand (the todo's explicit ask was a single stacked sheet — N modals feels punitive on a first-game new user).
**Reviewer notes:** Picked rarity-driven `PokerPalette.ChipGold.copy(alpha = ...)` accents over a per-rarity color ramp because the celebration is the moment — the existing rarity differentiation in the achievements grid is enough, and competing palettes inside a celebration card would dilute the "gold = unlock" semantics. The 90 ms stagger is empirical (feels like a cascade, not a wait) — if real-device timing reads slow, halving it would still cascade. The MP inline path is preserved verbatim including the existing inline-callout previews; one preview's xpMode flipped to `MULTIPLAYER` to keep demonstrating that legacy shape. VM-side test pins `state.xpMode == sessionFactory.xpMode` so the screen branch is correctness-guarded. Cosmetic preview is text-only ("Comeback Kid card back") because there's no rendered-art primitive for the card back or title pill on-hand today; the todo's "felt / card-back / title pill preview" is a future polish pass once those render-anywhere primitives exist.

## feat(achievements): add MP bust-dealt siblings + server 403 guard

**Problem:** The `AchievementMode.MULTIPLAYER` enum value existed but no MP achievement was tagged with it, and the server grant route's `serverWitnessed` set was empty — meaning a client posting any MP-only id would 204 (graceful skew) instead of 403 (deliberate refusal). When Phase 4.2 server-authoritative grants land, a malicious client could race the server by self-posting.
**Approach:** Added `FIRST_BUST_DEALT_MP` / `BUST_DEALT_5_MP` enum entries + registry rows with `AchievementMode.MULTIPLAYER`, backed by a new `BUSTS_DEALT_MP` custom-counter key that the local engine never increments (its grant pathway is server-only, post-Phase 4.2). Wired both ids into `ClientGrantableAchievements.Default.serverWitnessed` so the grant route returns 403 today, locking out client self-grants the moment those ids leave the empty-counter stub state. Tests pin registry shape, MP counter staying at 0 while the BOTS counter accumulates, and the 403 path on both ids.
**Reviewer notes:** Names "First scalp" / "Headhunter" + chip reward on the 5-bust (500 chips) match the rarity bump (RARE / EPIC) over their bot equivalents — the spec note "the prestige of busting a real human is materially different" was the cue for the higher tier. The MP siblings live next to the bot ids in registry order so the grid renders them adjacently. Comment on `serverWitnessed` was kept because the "why 403 not 204" branch is non-obvious to a future reader.
