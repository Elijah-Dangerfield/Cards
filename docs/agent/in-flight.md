## fix(mp): converge matchmaking on in-range buy-in (MP-15)

**Problem:** A "Find a Room" searcher whose chosen buy-in range straddled no canonical tier minted a fresh empty table instead of joining an existing one with the same range — both players stranded on the searching screen.

**Approach:** Root cause was `BuyInTier.within`: when the range bracketed no canonical tier it returned the nearest canonical *outside* the range, but the candidate filter matches existing rooms by `room.buyIn in min..max`, so a created table's out-of-range buy-in could never be re-joined by the next identical search. Fixed at the source by clamping the nearest-canonical result into `[min, max]` so a created table always sits at a stake the searcher's own range accepts. Chose this over making the candidate filter tier-aware (match on `room.buyIn == within(min,max)`) because clamping keeps the existing in-range filter semantics intact and yields the property players expect anyway — you're never seated outside the range you picked. In-range clamps are always legal stakes (the route validates the range to `MIN_BUY_IN..MAX_BUY_IN`, and `RoomSettings.forBuyIn` floors blinds for small stacks).

**Reviewer notes:** Updated the existing `buyInTier_within…` unit test, which asserted the old out-of-range behaviour (`within(100,500) == 1000`). Added a service-level convergence regression (`[3000,4000]` two-searcher → one table). The narrow behaviour change: ranges that straddle no canonical tier now create a table at a clamped in-range stake rather than the raw canonical — intentional, that's the fix.
**Deferred:** Single-item cycle by design — the rest of `docs/todo.md` failed the confidence gate for a solo worker, not for lack of time. MP-13 (chip-conservation) and BILL-1 (IAP redeem) are money-flow / server-authoritative ledger work — the "hard to undo" category. MP-14 needs a genuine product call on the match-over *trigger* (rebuy-grace timeout vs explicit end) plus a brand-new match-over protocol on the live MP socket; the cleanest trigger (loser leaves) already resolves cleanly via `RoomClosed`, so the unbuilt part is exactly the part that needs the product decision. PROG-1 is a Room-schema migration plus a rewrite of the live achievement-unlock path where the server-vs-local counter split is a judgement call (most custom counters — comeback, good-fold, all-in, pot ratios — are inherently client-side cross-hand state with no `PlayerStats` equivalent); too risky to slice cleanly in one commit without eyes on the split. AUTH-1 + GAME-3 are Studio-eyeball cosmetic tweaks I can't verify headless. MP-16 needs a runtime repro/traces. ENG-2 has an explicit human-call blocker (detekt 2.0-alpha pin for Kotlin 2.3). Nothing put in backlog — all already tracked in `docs/todo.md`.

## fix(profile): show default felt/card back as equipped (ITEM-1)

**Problem:** A fresh account's default felt + card back render no "Equipped" badge on the My Items grid — defaults are seeded into inventory but the server never writes an equipment row, and the grid derives equipped state purely from the equipment table.

**Approach:** Added the implicit-default fallback in `MyItemsViewModel.ownedItems` (the case file's preferred client-only fix). A default cosmetic now counts as equipped when no other item in its slot carries an explicit equipment row. New `isDefaultCosmetic` / `DEFAULT_COSMETIC_PRODUCT_IDS` helpers live in `CosmeticCategory.kt` next to `cosmeticSlotFor`, mirroring the server's `StarterInventory` default ids. Chose this over seeding server-side default equipment rows: the rendering layer (`PlayPokerViewModel`) already falls back to `EquippedFelt.Default` when nothing non-default is equipped, so the table was never broken — only the badge was — and a client-only fix needs no migration and keeps "default = implicit equip" as one rule the surface owns (which `Equipment.kt`'s doc already states).

**Reviewer notes:** Explicit ids (`felt_default`, `cardback_default`) rather than a `_default` suffix match, so a future `felt_default_blue` cosmetic wouldn't be wrongly treated as the slot default; add new defaults to `DEFAULT_COSMETIC_PRODUCT_IDS` + `StarterInventory` together. Verified by two new `MyItemsViewModelTest` cases (default equipped on fresh account; non-default explicit equip retires only its own slot's default) + green client build.
