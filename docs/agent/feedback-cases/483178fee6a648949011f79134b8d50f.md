## Working theory
The claim UI (`RankDetailSheet` "Claim your account", the Save-your-progress surfaces) gates on `AuthState.Authenticated.isAnonymous`. `ClaimAccountViewModel.ClaimWith` sends `Claimed` only on `LinkIdentityOutcome.Success`, which is returned from `linkOAuthIdentity` only after `completeOAuthRedirect` resolves the parked deferred. `completeOAuthRedirect` already contains a known-and-fixed hazard (documented in-code): on the `Link` path it forces `gateway.refreshSession()` because a bare GET /user leaves `is_anonymous=true` in the cached JWT and the app stays "anonymous." So on current develop the state *should* flip. That the owner still saw "sign in and claim" points at a residual gap, most likely one of: (a) the reporter's build predates the `refreshSession()` fix (release string is unbumped across builds — Sentry can't date it, so this must be confirmed against the build sha), or (b) a screen cached the pre-link `isAnonymous` and didn't recompose off the new `AuthState` emission, or (c) the `Link` redirect didn't route back through `completeOAuthRedirect` (deep-link `cards://login-callback` not delivered), so no emit happened yet the browser had already attached the identity — leaving the user "claimed at Supabase, anonymous in-app." Needs a code investigation. P1: it defeats the entire account-claim flow and risks a user believing progress is saved when the local session is still anonymous.
