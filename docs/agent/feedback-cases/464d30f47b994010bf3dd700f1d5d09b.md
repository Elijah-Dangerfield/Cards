## Working theory
The "Finishing setup" pill is `AuthReason.FinishingSetup`, emitted by
`AuthGateImpl.blockedReason` whenever `AccountCreationState` is `InProgress`/`Failed`
(`creationDegraded`). On iOS TestFlight build 821 the Supabase client's own Ktor
`HttpClient` is resolving to a **TLS-incapable native engine (CIO)**, so every
`POST /auth/v1/signup` throws `TLS sessions are not supported on Native platform`
(caught as `NetworkError`). Guest minting therefore never succeeds → creation stays
degraded → the banner is permanent, and deleting the account then relaunching just
kicks off another failing mint, so the banner "comes back" exactly as the user
describes. Root cause: `SupabaseClientFactory.provideSupabaseClient` leaves the Ktor
engine to auto-detection (its KDoc: "The Ktor engine is auto-detected … because we
have both engines on the classpath") — the precise fragile auto-resolution ENG-28
eliminated on the first-party clients by binding `Darwin` explicitly
(`platformHttpEngineFactory`). ENG-28 never covered the Supabase client. Fix: pass
`httpEngine = Darwin` (via the platform engine factory) into
`createSupabaseClient { }`, and/or complete the backlog "audit the linked iOS klib
graph for a transitive ktor-client-cio" item so auto-resolution can't pick CIO.
High confidence — the client evidence is unambiguous and reproduces across sessions.
