## Working theory
**Updated after reading the current (post-PR #84) seat code.** The gold ring is *overloaded* and that's the likely cause, not a state leak. In the new `OpponentSeat.kt` (added in PR #84, landed 2026-06-29 — one day before this report) the gold ring renders in two distinct cases (`OpponentSeat.kt:128-165`):
- `seat.isActing` → a **pulsing** gold "to act" ring (untimed bot/solo), and
- `aggressor = !outOfHand && !handComplete && seat.lastAction.isAggressive()` → a **solid** gold "aggressor" ring that persists for a seat whose last action was a bet/raise/all-in **until the hand completes or that seat folds**.

Both are gold. So after a bot bets/raises, its solid aggressor ring stays on through the rest of the street(s) even though it's no longer that bot's turn — which reads exactly as the reporter's "the gold ring… stays there… supposed to only be there during your turn." This is (as of PR #84) intended behavior, not a stuck-state bug; the earlier stale-bot-decision-skip theory doesn't hold up against the current derivation, which is cleanly `seat.isActing` / `seat.lastAction`-driven.

Two build possibilities (same undatable-release-string caveat as PROG-5): (a) reporter was on a pre-06-29 build with a genuine stuck-ring state bug that the PR #84 rewrite already fixed, or (b) reporter is on the post-rework build and is seeing the aggressor ring. Either way the actionable item on current develop is **legibility**: make the aggressor ring visually distinct from the to-act ring (different color/style, or drop/soften it) so a bettor's ring doesn't read as a stuck turn indicator. Reframe from "ring fails to clear" to "gold ring is overloaded (to-act vs aggressor)." Design/legibility call → P2.
