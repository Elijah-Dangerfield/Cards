## Working theory
The client turns a definitive server rejection into a transient "retry" and shows a reassuring pending-success. `BillingRepositoryImpl.redeem` (`libraries/billing/impl/.../BillingRepositoryImpl.kt`) posts via `networkClient.authedCall`, whose Ktor client has `expectSuccess` on — so a 400 throws `ClientRequestException` at `client.post(...)` (line 59) BEFORE the `when(response.status){ HttpStatusCode.BadRequest -> RedeemOutcome.Rejected }` branch (lines 78-80) can run. The throw is caught by the surrounding `Catching`, and `result.getOrDefault(RedeemOutcome.Unavailable)` (line 88) returns **Unavailable**. So `DefaultPurchaseChipPackUseCase.grant` takes the `Unavailable` branch (line 130) → `Failed(REASON_REDEEM_UNAVAILABLE)` + "left uncredited / retrying next launch", the transaction is left unfinished and re-redeemed every launch, and the shop shows "chips on the way / payment went through" (transient/pending) instead of the honest `receipt_rejected` failure dialog. The `BadRequest → Rejected` branch is effectively dead code. Fix: make redeem not throw past the status `when` for 4xx (disable expectSuccess for this call, or catch `ClientRequestException` and map its `response.status` — 400 → Rejected). Reproduce test-first (a fake 400 receipt_rejected must yield `RedeemOutcome.Rejected`, not `Unavailable`). Pairs with BILL-11 (the server-side cause of these 400s).
