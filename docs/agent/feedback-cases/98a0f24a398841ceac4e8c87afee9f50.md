## Working theory
`PublicSearchingViewModel.handleAction(JoinCandidate)` → `joinAndWatch(code)` joins the picked table, then calls `watchRoom(code)` and keeps the phase at `SearchPhase.Searching` (the radar) until the server flips the room to `RoomStatus.Playing`. There is no distinct pre-game lobby state in the public-search flow: a candidate you explicitly picked and joined drops you back onto the same "searching" radar UI, which reads as a bug ("I joined a table and got the search screen again"). Fix is a product/UX call: after `JoinCandidate` succeeds, present a joined-table/lobby state (seated players + waiting-for-deal) distinct from the still-hunting `Searching` radar, rather than reusing the radar. Confidence high on the cause (`features/rooms/impl/.../PublicSearchingViewModel.kt` lines ~160-164, 320-351); the exact desired UI is a directional call for the worker.
