## Working theory
The client collapses *every* server "next hand"/action refusal into `PlayPokerEvent.NextHandUnavailable`, which toasts `room_next_hand_unavailable` = **"Waiting for your opponent to rebuy or leave"** (string built for the MP-14 heads-up "opponent busted to 0 with no rebuy" case). Here nobody busted: the user backgrounded the app, their socket flapped, and they tapped on a *stale snapshot* (hand 3 acting=0) while the server had already moved the hand to Complete → the server rejected with `current hand not complete`. The client mislabels that transient race as "opponent must rebuy," so the user sees a terminal-sounding toast on every tap (and nothing happens) until they give up and leave. Fix: distinguish the server's refusal reasons — `current hand not complete` is a transient "hand still resolving / resync" state that should trigger a snapshot re-request, not the MP-14 opponent-rebuy copy, which should fire only when the server actually reports the opponent busted with no rebuy. Owner's UX direction (better than fixing the copy alone): don't render a tappable "Next hand" while the table can't deal one — when continuation is blocked by a busted opponent deciding to rebuy/leave, show the waiting player the *same rebuy-grace countdown* the busted player sees, and only reveal "Next hand" once continuation is possible, so the player never taps into a refusal. Telemetry gap: the client logged the server `intent_ack` refusal but not which user-facing event/toast it mapped to — add a single per-refusal `refusal <reason> → <event>` line (not in a loop) so the mapping is queryable next time. Heavily entangled with the background/reconnect snapshot-desync; button-gating + the refusal→event mapping are the testable fixes. P1.
