## Working theory

`GuestSessionHealer.healIfStranded` decides `stopForRecovery` **before** it consults `appState.isOffline`. The ladder at `GuestSessionHealer.kt:133-153` reads `stranded != null -> stopForRecovery(...)` first, and only the later `mint` arm checks offline — so being offline is treated as a reason not to *create* an account, never as a reason not to *destroy* one. Its two sibling components in the same package (`AuthReResolver.kt:53`, `StrandedIdentityDetector.kt:64`) both gate on offline first; the healer is the outlier.

Underneath that, the auth layer has thrown away the information needed to tell the two cases apart. `RealSupabaseAuthGateway.currentStatus()` maps `SessionStatus.RefreshFailure -> AuthGatewayStatus.RefreshFailure(cause = null)`, discarding the cause; `SupabaseAuthRepositoryImpl.resolveAndEmitLocked()` then burns all 5 attempts in a tight loop with no delay and no timeout, and `settleUnauthenticatedLocked()` emits `Reason.None` — byte-identical to "fresh install, no session ever existed". The repo already owns the right classifier, `RefreshFailureClassifier.classifyRefreshFailure`, whose own docstring says booting on a maybe is destructive; its only caller is the token path, not this one.

The damage is real and permanent, not cosmetic. `markSessionUnrecoverable` → `onSessionRejected` calls `gateway.signOut()` → `SecureSessionManager.deleteSession()`, which clears storage **and `mirror.clear()`** — the anonymous-session mirror whose entire purpose is to prevent stranding. `ProfileRepositoryImpl.resolveFallbackLocked` then sees `Reason.SessionExpired` and calls `profileCache.clear()`, writing `ProfileRecord.empty()` and nulling `localId`, the stable fallback UUID that local-only state is keyed off. And `SessionExpired` is sticky, so the recovery screen's "Try again" re-resolves against the files that were just deleted and fails forever; the only exit is Logout, which the copy itself warns clears chips, XP and history for good. Reconnecting does not undo it.

So: a guest who cold-boots on any captive portal or dead-but-connected WiFi can permanently lose their account, and the app tells them the auth server rejected them when it never spoke to it. The user's own steer ("ideally we just let them okay offline") is the right product answer.

Test coverage confirms the gap rather than closing it: `GuestSessionHealerTest.skip_whenOffline` sets `offline = true` but leaves a `Profile.Fallback`, and `stopsForRecovery_insteadOfMintingOverACachedAccount` supplies a cached authenticated profile but leaves `offline = false`. No test covers offline **and** a cached profile — the production case. `ProfileRepositoryImplTest.sessionExpired_dropsTheGhost_…` actively pins the cache wipe as correct, on the assumption the reason is always server-confirmed.

One caveat for whoever picks this up: reordering the `isOffline` check fixes this incident (the flag was true in time here) but is not sufficient on its own, because `AppStateImpl` starts `initialValue = false` — optimistically online — so on a faster cold boot the flag may not have resolved when `heal("coldBoot")` runs. The durable fix is to preserve the `RefreshFailure` cause through the gateway and refuse to settle a transient failure as a dead session.

Secondary, same root: the 95-second session and "it took a long time to get into the app" are the serial 5 s per-request timeouts plus the ~30 s auth resolve, all of which run to completion before the UI settles. Parked as a backlog one-liner, not part of this todo.
