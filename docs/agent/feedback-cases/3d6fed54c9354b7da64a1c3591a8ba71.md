## Working theory
Email confirmations are enabled, so a net-new `signUp` returns with NO active session (account created, awaiting email confirmation). The onboarding router treats this "signed-up, pending-confirmation" outcome as a returning sign-in and lands the user on the **"Welcome back"** screen instead of a **"check your email to confirm"** interstitial — and pops the signup back-stack, so back/swipe are dead (trapped). AUTH-21 handled the *already-registered fake-success* case and AUTH-22 added `resolveIsNewAccount`, but neither covers the *confirmation-required net-new* path landing on Welcome back. Fix: route a net-new email signup with confirmation pending to a dedicated "verify your email" screen that (a) tells the user to check their inbox, (b) keeps a working back path to the landing page, and (c) resumes into the app once the confirmation deep link lands (see AUTH-26 for the deep-link half). Confidence high on the symptom + delivered-email evidence; the exact router branch needs the code (OnboardingViewModel / VerifyEmail routing).
