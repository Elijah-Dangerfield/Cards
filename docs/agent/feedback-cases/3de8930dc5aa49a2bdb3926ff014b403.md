## Working theory
Confirmed root cause in `features/rooms/impl/.../PublicSearchingViewModel.kt`: the candidates re-poll (`armCandidatesPoll`, `CANDIDATES_POLL_INTERVAL=5s`) only runs while `phase == SearchPhase.Choosing`. When the initial `findCandidates` comes back empty, `CandidatesLoaded` calls `fallThroughToSearch()` → `beginSearch()`, which seats the user into their own fresh table via `POST /find` and only watches that one room's socket. From then on the VM never browses `/candidates` again, so a public table created by anyone else after fall-through is never discovered — the two solo searchers sit in two separate waiting tables forever. The reporter's own hypothesis ("searching isn't actually a live listening mechanism") is exactly right. Fix: keep polling `/candidates` (or have the server match the second `find` into the first waiting table) during the genuine-wait phase, not just the chooser, so two people who start searching seconds apart land in the same room. Confidence high; cause confirmed from server timeline + VM code.
