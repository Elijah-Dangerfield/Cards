## Working theory
`BuyInTier.within(min, max)` provably never returns a stake outside `[min, max]` (BuyInTier.kt:48-55), so a table opened at 1,000 means the client sent a range *spanning* 1,000 — i.e. the fixed default band 500-2,000 (`DEFAULT_BAND_MIN/MAX` in PublicFindScreen.kt), the exact figures the owner saw. The owner believed the range was ~0-500. Two plausible mechanisms, both in PublicFindScreen: (1) the slider scale is linear over 100..100k (wallet-capped), so the default thumbs at 500/2,000 sit in the leftmost ~2% of the track and *read* as "zero to 500-ish" even though the chips above say 500/2,000; (2) `range` is remembered as fractions keyed on `remember(effectiveMax)` — when the wallet balance resolves after the user has already dragged, the key changes and silently resets the selection to the default band. Either way the search honestly ran at 500-2,000 → snapped to the 1,000 tier. Fix direction: preserve user selection across balance load (re-map chips, don't reset), and make the low-stakes region readable (non-linear scale or tier-snapped chip presets) so thumb position, chip labels, and the searched band can't disagree.
